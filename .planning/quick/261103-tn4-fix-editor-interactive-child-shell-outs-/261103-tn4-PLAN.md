<objective>
Stop the TUI's own input reader from competing with an interactive child for the tty. Today vim, launched from the TUI, needs nearly every key pressed twice.

Root cause, verified against crossterm 0.29 `src/event/stream.rs` (CONTEXT, "Root cause"). `src/event.rs` reads input through crossterm's `EventStream`, and that type runs a background std thread looping `poll_internal(None, ..)`, which reads tty bytes. The editor block in `src/main.rs` never stops it, so that thread and the editor race for every keystroke. Dropping the stream only flags the thread and never joins it, so dropping is not a deterministic fix either.

The fix follows CONTEXT "Fix mechanism" and "Shared helper / call sites". An app-owned reader thread polls and reads crossterm with a short timeout. Its `suspend()` blocks until the thread is parked, outside any poll or read. One shared helper orders the steps: suspend reader -> release terminal -> child -> reclaim terminal -> resume reader. The editor shell-out runs through that helper. Regression tests drive the same helper, and the CONTEXT "Regression test" section requires that they fail when the helper does not suspend the reader.

Purpose: the editor receives every keystroke. Keystrokes meant for the editor are no longer swallowed by the TUI and replayed as TUI commands.
Output: new library module `src/input.rs` with tests, the rewired `src/event.rs`, `src/tui.rs` and `src/main.rs`, and corrected `.planning/codebase/ARCHITECTURE.md` entries.
</objective>

   - `pub fn spawn<S: InputSource>(source: S, tx: UnboundedSender<Action>) -> std::io::Result<InputReader>` uses `std::thread::Builder::new().name("gsdmm-input")`.
   - Thread loop. At the top of each iteration, take the lock. While the mode is Suspend, set `parked = true`, `notify_all`, and wait on the condvar. On Stop, return.
