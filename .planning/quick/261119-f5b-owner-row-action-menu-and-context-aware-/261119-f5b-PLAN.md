## Solutions considered

**A. Context-aware footer only.** The footer lists the selected row's actions from a shared model
(`[v]run /gsd-verify-work 16  [x]settle  [o]pen  [A]ck  [y]copy`); Enter keeps expanding.
UX trade-off: smallest change and no muscle-memory break, and it fixes today's three untruthful footers
(`[Enter]expand` on a check line where Enter opens the viewer; `[y]copy`/`[Enter]expand` on folds that
only refuse; `[x]settle` hidden below 137 columns in the inbox, Owner block footer names no action at all).
But at 80 columns the footer must cut 2-4 hints, every refusal reason stays invisible, there is nowhere to
show "applies but blocked right now", and it does not give the owner the Enter context menu he asked for.

**B. Footer (A) + Enter opens a which-key action menu (CHOSEN).** Enter on a group/debug row opens a small
bordered overlay anchored at the row: one line per action with its key, a label and the command or target
(`> v      run             /gsd-verify-work 16`), blocked entries dim with `(reason)`, `v` preselected
when runnable. j/k + Enter or the letter executes; Esc/q close. Enter on a check/file line still opens
the viewer; Enter on the fold line still opens/closes the fold; Space toggles everywhere; Right/l expand,
Left/h collapse (both keys are swallowed on rows today, so nothing collides).
UX trade-off: complete and discoverable (every action and every reason is one keypress away), fits 80x24
(at most 7 entries + 2 border rows), and lets the footer stay short at 80 columns because the menu holds
the long tail. Cost: Enter-expands muscle memory changes (mitigated: Space, Right/l and an "expand" entry
in the menu, all documented) and about 25 tests that press Enter to expand switch to Space.

**C. Inline action strip under the selected row** (chips, Left/Right to pick, Enter to run).
UX trade-off: actions visible in place without a popup, but it costs a body row in an Owner block that has
about 6 body rows at 80x24, re-flows every row below on each cursor move (breaks the identity-based scroll
math `follow_offset` in `src/ui/screens/owner_block.rs` and the inbox `scroll_for`/`scroll_to_item`),
makes Left/Right mean chip-pick on rows but fold-step on the fold line (so they cannot also expand/collapse),
and duplicates the footer.

**Choice: B.** It is the only option that satisfies both "truthful and fitting at 80 columns" and "nothing
hidden": the footer may drop low-priority hints at 80/100 because the menu always lists every applicable
action with its command or its reason. A cannot show reasons or the long tail; C pays in vertical space,
scroll stability and arrow-key ambiguity. B also matches the owner's stated expectation, at a fixed small
cost (one overlay, one Enter rebind on group rows only).

## Menu (normative)

- State: `menu: Option<ActionMenu>` on `InboxScreen` and on `DetailScreen`; `ActionMenu` holds the target
  identity (alias + `GroupKey`) and the selected `ActionId`. Entries are recomputed from `row_actions`
  every frame and every key, never snapshotted. Each host records the cursor row's on-screen rect in a
  `Cell<Option<Rect>>` during render (the anchor).
- Overlay: `Clear` + `Block::bordered()` titled ` Actions `, bottom title ` [Enter]run  [Esc]close `.
  Width = longest entry + 4, clamped to `[30, min(area.width - 2, 76)]`; height = entries + 2. Placed
  below the anchor row, flipped above when it does not fit, clamped to the frame; centered when no anchor
  was recorded. Drawn LAST (after the footer) so it is on top.
- Entry line: marker (`> ` selected, two spaces otherwise; ASCII, like the Owner block cursor), key
  label padded to 6 (`v`, `x`, `o`, `A`, `y`, `g`, `Space`), label padded to 16, then the detail; a
  blocked entry shows `({reason})` instead of the detail and is DIM. Selected entry BOLD + Cyan (the
  `SettlePhaseScreen` precedent). All project-derived text through `shown`; lines cut with `fit_cells`.
- Labels (shared, host-independent): `run`, `settle`, `open`, `acknowledge`, `copy checklist`,
  `go to project`, `expand` / `collapse`. Details: v the command (live session: `focus the live
  session, type CMD`); x `whole phase, asks first` / `this check, asks first`; o `{file basename},
  read-only`; A `{file basename} via gsd-core, asks first`; y `as gsd-meta-manager inbox prints it`;
  g `{alias}: Phases tab, same group`; Space `checks and source file`.
- Order v, x, o, A, y, g, Space. Preselected: v when R, else the first R entry.
- Keys while open (intercepted at the very top of the host's `handle_key`, before every other arm):
  j/k/Down/Up move over R entries only (clamped); Enter runs the selected entry; a plain letter
  (`is_plain_action_key`: no Ctrl/Alt) or Space that names an entry runs THAT entry, R or B (a B entry's
  hotkey prints its reason); Esc and q close; every other key is swallowed (digits, `1`-`4`/`a`, Tab,
  `?`, `g` in the Owner block, arrows, h/l).
- Run = `self.menu = None;` then `return self.handle_key(code, KeyModifiers::NONE, ctx)` through the
  host's own `Screen::handle_key`, i.e. the exact path a typed key takes. Popups that draw a fresh host
  as backdrop therefore never show the menu.
- Validity: if, when a key arrives, the target no longer resolves (refresh dropped it), the cursor is no
  longer on it, or (detail) focus left the Owner block / the Phases tab, the menu is dropped silently and
  the key is handled as if no menu were open. Render draws the menu only while it resolves.
- Mouse: `DetailScreen::handle_mouse` returns `ScreenAction::None` while a menu is open (no tab switch,
  no phase selection under it); the inbox has no mouse handler. No click selects an entry.
