# Quick 260926-1t1 — 4a: detail-view navigation model

<objective>
Give the detail view a tab-bar focus level above the tab content, and make every key follow one rule. `↓`/`Enter` go down a level, `↑`-at-top and `Esc` go up one level, `←`/`→` move between siblings on the current level, and `q` leaves. Sub-tabs get arrows and `[`/`]`. The tab each digit opens remembers its last sub-tab. Focus is shown by text as well as colour. The footer, help popup and docs are rewritten to match.

Purpose: `Enter` on Sessions no longer resumes a session the moment you arrive. The sub-tab boundary becomes navigable by arrow. The Esc/q split gives "back one level" and "leave" separate keys, as the TUIs surveyed in UX-RESEARCH §2 do.

Output: level-aware `handle_key`, focus styling, footer and help in `src/ui/screens/detail.rs` and `help.rs`; the per-project sub-tab memory in `mod.rs`; README and GETTING-STARTED docs.

**Decision IDs.** D-01..D-08 are the eight locked "USER-DECIDED BEHAVIOUR" items from the planning context, in order:

- D-01: the tab-bar level and the Esc/q split.
- D-02: Sessions Enter.
- D-03: `←`/`→` inside content.
- D-04: `[`/`]`, `m`, the digits and the sub-tab memory.
- D-05: Tab is unchanged.
- D-06: visible focus and Backlog alignment.
- D-07: footer and help.
- D-08: the Sessions double border and the strip gutter.

Each task cites the IDs it implements.

**Scope fences (task 4a only).** Do NOT build the Phases waves pane, `Enter` on Phases, mouse handling, the Agents wave ribbon, any change to `render_pipeline_tab`, or a `DetailFocus::Pane` variant. Those belong to 4b and later tasks. Leave the plug-in points: a doc comment that reserves `Pane` on the enum, the `DetailRegions` rects, and the shared `focus_block` helper.

**Inferred decisions (the human is unavailable; each one is marked for audit):**

- **[inferred I-1]** `←`/`→` inside a tab WITHOUT sub-tabs switch tab as today and land focus on the TAB BAR. This happens even at the clamped end, where no tab changes. This confirms UX-RESEARCH §3.2 ("landing at T"). The decisive reason: if the arrow landed in content, a `→` walk that reached Sessions would enter its sub-tabs and get stuck at the clamped Agents end.
- **[inferred I-2]** At the tab bar the only keys handled there are `←` `→` `↓` `j` `Enter` `Space` `↑` `k` `Esc` `q`. `?` and `Tab` are focus-neutral: they act as today and leave focus alone. EVERY other key (digits, `D`, `[`, `]`, `m`, `e`, `x`, `n`, `/`, `g`, `G`, PgUp/PgDn, …) first moves focus to Content, then runs exactly as it does in content. So no existing shortcut costs an extra keypress, and focus follows where the action happened. Digits landing in content (D-04) falls out of this rule.
- **[inferred I-3]** `Space` at the tab bar descends like `Enter`, with no action. It shares Enter's arm today, and on Queue it would otherwise mark an item done from the tab bar.
- **[inferred I-4]** `q` leaves from any level WITHOUT first popping inner levels. Inner state (an open pane, an Archive depth, a Config dropdown) stays in the view cache, just as any exit leaves it today. Re-opening the view shows it again, and focus resets to Content.
- **[inferred I-5]** `k` behaves like `↑`; they share one arm today, and §3.2 pairs them. "First row" is an exhaustive per-sub-view predicate:
  - For the scroll views (Roadmap box view, Browse/Archive file view), "scrolled to the top" counts as the first row.
  - An open Backlog pane or an open Config dropdown never counts, so `↑` never leaves a pane (§3.2, P column).
  - On Git, `↑` at row 0 goes to the tab bar and leaves the commit pane as it is.
- **[inferred I-6]** The active tab is bracketed at EVERY level. D-06's "bracketed (not colour-only)" overrides §3.4's "no brackets at C", so the active tab can be read in a text scrape at any level. The framing is width-neutral: the brackets replace the `Tabs` widget's 1-cell pads, which are set to empty, and inactive labels carry a space on each side. So `TAB_BAR_*_CELLS`, `tab_titles` and every tier test stay unchanged.
- **[inferred I-7]** "Content dimmed" at the tab bar is ONE `frame.buffer_mut().set_style(content_area, fg DarkGray)` after the content render. It is uniform across all eleven sub-views and needs no per-tab code.
- **[inferred I-8]** The `▸` + cyan border cue marks a focused PANE. In 4a that is the Backlog content pane; in 4b it will be the waves pane, through the same `focus_block` helper. It is not retrofitted onto every tab's content block. Tab bar versus content is already carried by the reversed label plus the dimming, and a `▸` on a region that is the only focusable one adds no information.
- **[inferred I-9]** The Backlog pane follows §3.2's P column: `←` closes it (back to the list), `→` does nothing, `↑` never leaves it, and `Esc`/`Enter` close it as today.
- **[inferred I-10]** `backlog_expanded` stays the single source of truth for the Backlog pane. A second focus flag that had to agree with it would be a bug waiting to happen. `DetailFocus` has only TabBar and Content in 4a.
- **[inferred I-11]** The sub-tab memory is per project and in memory only, like `detail_sub_view_per_project`. It is keyed by tab index and written by EVERY arrival, including the Roadmap shipped-row jump to Milestones.
- **[inferred I-12]** The strip hint reads `←/→ switch`. At the tab bar it is dimmed along with the rest of the content.
- **[inferred I-13]** The Driver footer (`driver_footer_spans`) is left unchanged. Its three forms are width-measured and pinned, and its `[Esc]back` is still accurate as "back one level".
- **[inferred I-14]** The content footer keeps the digit token, renamed `[1-8/D]jump` (flag-off `[1-8]jump`), so Shift+D stays discoverable from every tab. That is the 260917-fko D2 / 18-09 property the existing footer tests pin.
- **[inferred I-15]** `[`/`]` on a tab with no sub-tabs, other than the Roadmap list view, is a no-op.
- **[inferred I-16]** The empty Sessions state keeps one border, titled ` Sessions (0) `.
- **[inferred I-17]** Both render paths (`render`, `render_main_only`) reset and refill `DetailRegions` each frame, so the rects never mix two frames.
</objective>
