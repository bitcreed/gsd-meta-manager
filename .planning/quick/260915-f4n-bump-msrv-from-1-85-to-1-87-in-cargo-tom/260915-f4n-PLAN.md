<objective>
Make the declared MSRV of 1.87 ENFORCED rather than merely documented.

**Read this before starting — the task title describes work that is already done.**
The premise "bump MSRV from 1.85 to 1.87 in Cargo.toml" was measured against the repo
before planning and does not hold:

- `Cargo.toml:5` already reads `rust-version = "1.87"`. It landed in commit **41a7b3f**
  (`chore(15-01): raise MSRV to 1.87 and add the transport dependencies`). `git log -S`
  confirms the string `rust-version = "1.85"` has **never** existed in `Cargo.toml`.
- There is **no** `rust-toolchain.toml` and no `rust-toolchain` file. Nothing to bump.
- Every user-facing doc already states 1.87 and was checked correct as written:
  `README.md:61,186`, `CONTRIBUTING.md:23`, `docs/DEVELOPMENT.md:10`,
  `docs/GETTING-STARTED.md:13,150`, `docs/TESTING.md:14`, `src/journal/redact.rs:218`.
- `CLAUDE.md:99` mentions 1.85, but that is a true statement about the **notify** crate's
  own MSRV in a sources bullet, not this project's floor. It is correct and is NOT edited.

What genuinely has not caught up is enforcement. The only workflow, `.github/workflows/release.yml`,
installs `dtolnay/rust-toolchain@stable` and nothing else. So the crate is compiled, tested,
linted and **published to crates.io** having never once been built on 1.87. The floor is an
unverified claim: today's local toolchain is 1.98.1, and any post-1.87 feature that crept into
the source or into a dependency would ship to users as a broken install with no signal here.

This plan measures the floor for real, then wires that exact measurement into CI as a gate on publish.

Purpose: a version number in a manifest that nothing tests is documentation, not a contract.
Output: an `msrv` job in `release.yml` that `publish` depends on, plus a recorded local measurement.
</objective>

against the committed `Cargo.lock`, which is what a consumer resolving this crate gets.

<task type="auto">

  <files>.github/workflows/release.yml</files>
  <action>
Add a second job named `msrv` to `.github/workflows/release.yml`, and make the existing
`publish` job depend on it with `needs: msrv`. The `needs:` edge is the load-bearing part —
without it the job runs alongside publish and gates nothing, which is the most common way
this exact pattern is shipped broken.

The `msrv` job:

- `runs-on: ubuntu-latest`
- `actions/checkout@v4` (match the ref style already used in this file)
- `dtolnay/rust-toolchain@1.87.0` to install the floor toolchain. This ref was verified to
  exist against the action's repository before planning (both `1.87` and `1.87.0` branches
  are published); use the fully-qualified `1.87.0` form. No `components:` are needed — the
  job compiles, it does not lint.
- `Swatinem/rust-cache@v2`, matching the existing job.
- A step named for the floor-agreement check that asserts the installed toolchain equals the
  manifest's declared floor. This is the key link and must NOT be skipped: read
  `rust_version` via `cargo metadata --no-deps --format-version 1 | jq -r '.packages[0].rust_version'`,
  read the installed compiler's version via `rustc --version`, and fail the job with a
  `::error::` annotation if the manifest floor is not the version actually installed.
  Compare on the `MAJOR.MINOR` components so that `1.87` in the manifest matches a `1.87.0`
  toolchain. Without this step, a future bump of `Cargo.toml` leaves CI silently certifying
  a floor the project no longer claims.
- The compile step, running the command Task 1 proved green — byte-identical to it, including
  the `--all-targets` and `--locked` flags (or the narrowed form, if Task 1 took branch (a)).

Keep the file's existing conventions: two-space indent, job-level `name:` strings, the
top-level `permissions: contents: read` untouched, and the tag trigger untouched. Do not

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner -> crates.io | The `publish` job holds `CARGO_REGISTRY_TOKEN`; anything running in that workflow is inside the blast radius of a publish credential. |
| Third-party GitHub Action -> workflow runner | `dtolnay/rust-toolchain` executes attacker-controllable-if-compromised code in the same workflow as the token. |
| static.rust-lang.org -> developer machine | Task 1 downloads and executes a toolchain binary locally. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-f4n-01 | Elevation of Privilege | `msrv` job co-resident with `publish` in release.yml | medium | mitigate | The `msrv` job declares no `env:` and receives no secret; `CARGO_REGISTRY_TOKEN` stays scoped to the `publish` step that already had it. Adding a job does not widen secret exposure because Actions secrets are step-scoped via `env:`, and the new job sets none. |
| T-f4n-02 | Tampering | `dtolnay/rust-toolchain@1.87.0` (mutable branch ref) | medium | accept | A version-named branch is mutable, so this is not a content pin. Accepted because it is the posture the file already has (`@stable`, `actions/checkout@v4`, `Swatinem/rust-cache@v2` are all mutable refs) and because pinning one of four actions to a SHA while the other three float buys no real reduction. Recorded as a follow-up: SHA-pin all four actions in one pass, which is a coherent change this quick task is not scoped for. |
| T-f4n-03 | Spoofing | rustup toolchain download in Task 1 | low | accept | rustup verifies the downloaded toolchain against signed channel manifests over TLS; no additional control added. |
| T-f4n-04 | Tampering | `cargo metadata` reading `rust_version` inside the msrv job | low | mitigate | The value is compared against `rustc --version` and only ever used to fail the job; it is never interpolated into a shell command position where a crafted manifest value could execute. Quote the expansion. |
| T-f4n-SC | Tampering | package-manager installs | n/a | n/a | This plan adds **no** npm/pip/cargo package. No dependency is introduced to `Cargo.toml`; the only download is a rustup toolchain, which is not a package install. The Package Legitimacy Gate therefore does not apply. |
</threat_model>
