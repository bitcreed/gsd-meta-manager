## Inferred decisions (record each as INFERRED in the SUMMARY)

- I-1 Stages and detection. `Launched` at Yes. `Recorded` when the fingerprint (modified
  time + length from `std::fs::metadata`, after canonicalizing the project's `.planning/`
  and the file and requiring the file inside it, the same containment as
  `owner_actions::read_owner_file`) of any of the entry's source files differs from the one
  taken just before the launch; checked when a reparse of that project lands
  (`Action::ProjectStateLoaded`, which every watcher event under `.planning/` leads to,
  including the deduped ones via the tick's `flush_pending_reparses`). A file that was
  readable and now is not counts as changed. `Done { since }` when no group of the fresh
  digest with the entry's lane, workstream and phase still lists an item with one of the
  entry's stored `(id, name)` pairs, AND the stage is `Recorded` after this refresh's stat
  (one write that records the only check goes Launched -> Done in one refresh). Settled
  checks gone while no source file changed: the entry is dropped silently, no `✓` claimed.
  Only evaluated while the alias holds a digest (an unreadable digest keeps the entry).
  `(id, name)` pairs, not ids alone: unnumbered items carry positional ids (`#v1`) that a
  refresh can reuse for another item.
- I-2 Linger and redraw. `LINGER = 2 s` from `Done.since`; the existing 250 ms
  `Action::Tick` drops expired entries (visible 2.0 to 2.25 s). While any entry exists and
  the top screen is the inbox (`"inbox"`) or the detail view (`DetailScreen::NAME`), each
  tick sets `needs_redraw` so the spinner and the timer move; no new timer, no redraw
  elsewhere.
- I-3 Where the state lives. A new `AppContext.settle_pending: settle_pending::PendingSettles`
  (Default), in memory only. Not in `inbox_view` (`i` on the dashboard resets that) and not
  on `ProjectState` (its `PartialEq` drives `Updated:`). Alias-keyed, so
  `App::prune_driver_maps` retains registered aliases and the exhaustive destructure in
  `every_per_alias_map_is_pruned` classifies and asserts it.
- I-4 Keying. An entry matches a row by facts, never by index or `GroupKey` equality: same
  alias, the row key's `lane`, `scope_label`, `workstream` and `phase` equal the entry's, and
  the row's `RowSrc.files` share at least one file with the entry's files. So an entry
  survives refreshes and shows on both hosts (an inbox merged UAT+VERIFICATION row, kind
  `entry`, and the Owner block's per-file rows). A single-check entry's files are only the
  file of the group holding that check, so it badges only rows holding that file. When
  several entries match a row, the latest registered wins. A new Yes on the same alias whose
  `(id, name)` set overlaps an existing entry's replaces that entry.
- I-5 Badge text. Launched/Recorded rungs, longest that fits first:
  R1 `{spin} settling… {words} · {stage} {m:ss}`, R2 `{spin} settling… {stage} {m:ss}`,
  R3 `{spin} settling… {m:ss}`, then R3 cut with `fit_cells`. `{stage}` is `launched` or
  `recorded`. `{words}`: phase scope = the outcome (`won't do`, `defer permanently`,
  `move to phase M`); check scope = `{noun} {number} ` before it (`test 2 won't do`).
  Done: `✓ {short} skipped` for Won't do and Deferred permanently (`short` =
  `SettleTarget::short()`: `test 2` / `phase 01`; GSD records both as `result: skipped`),
  `✓ moved to phase M` for Move (the owner's literal). `{m:ss}` = whole minutes, colon,
  two-digit seconds since Yes (`0:12`, `75:03`). `{spin}` = ASCII frames `|`, `/`, `-`, `\`
  picked by `(elapsed_ms / 250) % 4`. `✓` is `glyphs::CHECK` followed by a space; `…` is the
  TYPOGRAPHY escape `\u{2026}`; ` · ` is `owner::OWNER_SEP`. The registry has no ASCII
  fallback mode (it is a pending todo), and ASCII spinner frames need none, so no glyph is
  added to `glyphs::ALL`. Every value drawn goes through `detail::shown`.
- I-6 Placement, 80 columns. On a matching row the phrase, extras, age and command cells are
  not drawn; the badge starts at the host grid's phrase column (inbox:
  `Grid::checks_x() + checks_w + 2`; Owner block: `2 + TAG_W + 1 + phase_w + 2 + name_w + 2 +
  checks_w + 2`) and runs to the row end; a BLOCKED row's tally is cut there. If even R3
  does not fit, the start moves left until R3 does. One line, never wraps. The narrowest
  region the inbox grid leaves at 80 columns is phrase floor 12 + 2 + age 11 = 25 cells,
  which is exactly R2 with a four-cell timer.
- I-7 Styles. Settling badge DIM; done badge not dimmed, `✓` Green; the lingering row
  itself DIM. The inbox cursor row's style (`owner_block::cursor_style`) is patched onto its
  badge as well; the Owner block's `mark_cursor_row` already patches the whole line.
- I-8 Lingering rows are drawn only, in both hosts: never a cursor stop, never expanded, no
  key reaches them (so `v`, `A`, `x` can never act on a recorded row). They are snapshots
  taken at Yes: the inbox's current (unfolded) rows and the Owner block's current rows that
  match the entry. One is drawn while its entry is `Done` and no current row has its key; it
  sits where the host's own order puts it (inbox: the `sort_groups` comparator, extracted as
  a named fn; Owner block: the `current_sources` lane sort key) with its section title when
  its section has no other row; it is left out of the column grid so nothing reflows; the
  lane filter applies to it. A row in an open inbox fold gets the live badge but no
  lingering copy. When the cursor's row leaves, the cursor moves on exactly as today.
- I-9 Single checks: the badge goes on the group row (always visible, naming the check); the
  check line inside an expansion is not marked.
- I-10 Launch paths. A new-session Yes registers only when the launch started: the status
  equals `launched_status(plan)` or reports `opened in` a GUI terminal (the
  `multiplexer::launch_with` success forms; its failures are `Failed to launch: ...` and
  `... no terminal emulator found (set $TERMINAL)`). A live-session Yes always registers:
  the paste happens outside the app, and a never-pasted command keeps its timer.
- I-11 Edits outside the core: settle_popup.rs gets one changed line in `confirm`; help.rs is
  not touched (the badge adds no key); docs/GETTING-STARTED.md is not touched (it does not
  describe settling); README's settle paragraph gains the badge description.
- I-12 The fingerprint is taken before the launch, so a write that lands fast cannot be
  missed.
- I-13 `src/ui/screens/settle_pending.rs` joins `SETTLE_FILES` in tests/owner_settle_guard.rs,
  so "the settle modules write nothing and spawn nothing" covers it.
