## Inferred decisions (for audit — human unavailable)

- **I-1, comparison rule.**
  - The in-sync range runs from GSD_CORE_SYNCED_VERSION (1.14.0: the oracle pin and the latest npm release) to GSD_CORE_SYNCED_TREE_VERSION (1.15.0: the synced tree), inclusive.
  - Above the ceiling: Warning. Below the floor: Info. Semver precedence applies, so 1.15.0-rc.1 is in range and 1.14.0-rc.1 is Older.
  - Why not compare against 1.15.0 alone: 1.14.0 is the newest published release, so every npm user would see an "older" note for being on the latest version. 1.14.0 is also what the conformance oracle certifies.
  - When a future sync sets both constants equal, the range collapses to that single version.
- **I-2, new constant `GSD_CORE_SYNCED_TREE_VERSION = "1.15.0"`.** This is needed because no constant carried 1.15.0. It sits beside the existing pair and is named so that the declaration grep in install-conformance-oracle.sh cannot match it. It is not hand-invented: it was measured from `git show upstream/release-1.15.0:package.json`.
- **I-3, which install counts as "effective".**
  - It is the first candidate whose `gsd-core/VERSION` is a regular file, which is upstream's own install-exists signal (install.js:11320).
  - A garbage VERSION still wins and reports Unrecognised. Falling through would misreport which install GSD would actually load.
  - The resolver's shim-existence check and this VERSION check can disagree only on a broken install.
- **I-4, one shared candidate list.**
  - The gsd-tools resolver becomes a projection of `install_candidates`, so the gsd-tools resolver now honours `CLAUDE_CONFIG_DIR`, which replaces `~/.claude` rather than adding a candidate.
  - This matches upstream `gsd-run-resolver.md` and closes gtm's recorded follow-up.
  - It is a behaviour change, and a reversible one. Its trust level is the same as HOME/CODEX_HOME.
- **I-5, override semantics follow the installer.** An override counts only when non-blank after trimming, and a leading `~` is expanded, because the installer is what wrote the files being located. The resolver previously treated only an empty CODEX_HOME as unset; whitespace-only and literal-`~` values now behave like the installer.
- **I-6, the `<root>/gsd-core` candidate.**
  - It is included for resolver parity and labelled `project-local (root)`. Only Cline local installs land there, and a gsd-core checkout has no VERSION.
  - The other 14 runtime homes are not probed, as before.
- **I-7, PATH-only installs.** A PATH-only `gsd-tools` with no VERSION file is not version-detected and reads as not found. Resolving npm-global package.json via symlinks was judged out of scope, and running gsd-tools is forbidden.
- **I-8, surfacing.**
  - Per project, the version goes on the Config tab's top border (right-aligned), not in the detail header. The header's right side already carries the status message, and the Config tab is where gsd-core config is edited.
  - Border titles change no layout, so mouse hit-testing is unaffected.
  - The dashboard indicator appears only on Newer. It is an in-memory scan, and it is invisible otherwise, so existing renders stay unchanged.
- **I-9, startup message placement.** It is set after the initial synchronous load and before auto-registration. A rarer "Auto-registered" message may replace it within the 3 s window, and the persistent indicators still carry the information.
- **I-10, never echo garbage.** An unparseable VERSION is never displayed, which removes the escape-injection surface from project-controlled files. Labels come only from enums, validated semver, and constants.
- **I-11, README single source.** Exactly one README paragraph spells the three values. The `### Compatibility` section refers to it, so a sync has a single README place to update and the test pins it.
- **I-12, detection lives in parse_project_state.**
  - It therefore runs on every load and refresh. It is off the render path via spawn_blocking, and synchronous only at startup, before the loop, like the other startup scans.
  - A GSD upgrade is picked up at the next reparse. `~/.claude` is not watched.
  - Workstream sub-states also carry a detection, which is unused. The `parse_project_state_with` seam exists so tests inject roots.
- **I-13, detail-view help and key tables.** No key is added, so they are unchanged unless the executor finds them describing the Config border.
- **I-14, semver is hand-rolled (~40 lines)** instead of adding the `semver` crate. That avoids a new dependency and the package-legitimacy gate. Only release-vs-installed precedence is needed.
