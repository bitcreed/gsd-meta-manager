<objective>
The TUI opened a Claude session in a **gnome-terminal** window while the user was sitting
inside **tmux**, on a machine whose real default terminal is **ptyxis**. Two independent
defects, both in `find_terminal()` (`src/ui/screens/detail.rs:518`):

1. **No tmux branch exists.** Both launch sites — the Sessions-tab resume (`detail.rs:1893`)
   and the `n` new-session key (`detail.rs:2325`) — call `find_terminal()` and never look at
   `$TMUX`. The repo already drives the running tmux server in
   `src/terminal_switch.rs::switch_to_session`, but that is wired only to the *focus-switch*
   action (`normal.rs:158`, `normal.rs:554`, `detail.rs:1405`), never to launching.
2. **No system-default discovery.** `find_terminal()` tries `$TERMINAL`, then a hardcoded
   `["kitty","alacritty","gnome-terminal","xterm"]`, returning the first that exists. On the
   user's machine that lands on gnome-terminal purely by list order.

Purpose: make "open a session" appear WHERE THE USER IS (their tmux server) and, when they
are not in tmux, in the terminal their desktop actually designates as default — without
weakening any of the three security controls that guard these two spawn sites.

Output: a pure, injected-probe decision function plus a fail-closed tmux window opener in
`terminal_switch.rs`; a rewritten discovery path and two new argv builders in `detail.rs`;
three existing pins UPDATED TO KEEP GUARDING over a larger surface, and new pins for the
tmux path.
</objective>

<decisions>

These are LOCKED. They were settled before planning; do not re-litigate them, and cite the
id in the code comment that implements each one.

**D-01 — tmux OUTRANKS `$TERMINAL`.**
Order is: inside tmux → tmux window; otherwise `$TERMINAL` → `xdg-terminal-exec` →
`x-terminal-emulator` → hardcoded fallback list.
Rationale to record in the code: `$TERMINAL` expresses which *GUI emulator* the user prefers,
not *where the session should appear*. It is commonly exported globally from a shell profile,
so it is rarely a per-invocation intent. If it outranked tmux, every user with `$TERMINAL` set
would keep hitting exactly the reported bug.
**Residual, to be written down honestly and NOT fixed:** a user sitting inside tmux can no
longer force a GUI window by setting `$TERMINAL`. Do **not** add a new environment variable or
a config key to recover that. `$TERMINAL` is not lost — the tmux branch falls through to it
whenever `$TMUX` is unset, no tmux server is reachable, or the `tmux new-window` call fails.

**D-02 — discovery order, with the reason each rank is where it is.**
- `xdg-terminal-exec` is the reference implementation of the freedesktop Default Terminal
  Specification. On the target machine
  `gsettings get org.gnome.desktop.default-applications.terminal exec` is
  `'xdg-terminal-exec'`, and `xdg-terminal-exec --print-id` prints
  `org.gnome.Ptyxis.desktop:new-window` and **exits 0**.
- `--print-id` is therefore a cheap SYNCHRONOUS capability probe: it reports whether the
  launcher can resolve a terminal *before* we commit to spawning it. Use it. A bare `spawn()`
  fails asynchronously, after which we could never fall through.
- `x-terminal-emulator` (Debian alternatives) ranks **below** it and that ordering is
  load-bearing: on the target machine `/usr/bin/x-terminal-emulator` →
  `gnome-terminal.wrapper`, i.e. it points at exactly the wrong answer. Probed first, the
  reported bug would persist.

**D-03 — the tmux program vector is guaranteed to be ≥ 2 elements by a leading literal `env`,
and `open_new_window` refuses anything shorter, fail-closed.**
`man tmux`, verbatim: *"the new-window ... and respawn-pane commands allow shell-command to be
given as multiple arguments and executed directly (without 'sh -c'). This can avoid issues
with shell quoting."* A shell-command given as a **single** argument still goes through
`sh -c`. The new-session vector would naturally be the single element `claude` — landing
exactly on that edge and reintroducing an interpreter into a path CR-01 cleared.
Chosen fix: every tmux program vector begins with the literal `env`.
- `env` is **not** a command interpreter. It has no program-string mode: it consumes argv
  elements, applies leading `NAME=VALUE`/option words, and `execvp`s the first non-option word
  with the remainder passed through **unparsed**. No byte of the fused `--resume=` element can
  be reinterpreted by it. (This is the same structural reading of `env` the envelope's
  `resolve_program` already uses.)
- It makes ≥ 2 true **by construction** for every vector, present and future, rather than by a
  rule each caller must remember.
- It also fixes the first element to a literal that provably does not start with `-`, so
  tmux's own option parser stops there instead of consuming part of our vector.
- Rejected alternative: pad with a `claude` flag. No `claude` flag is provably inert, so that
  trades a structural guarantee for a behaviour change.

**D-04 — bare `ptyxis`; `launch_terminal_argv` stays PINNED AT TWO.**
Do **not** add a `terminal_leading_options()` helper and do not prepend `--new-window`.
`ptyxis` is reachable only from the last-resort fallback list, i.e. only when
`xdg-terminal-exec` is absent — which is rare, since `xdg-terminal-exec` is how ptyxis gets
designated as the default in the first place. The cost of the simpler option is a
window-vs-tab difference, not a wrong argv. The benefit is that the third pin
(`launch_terminal_argv_carries_no_untrusted_element_and_is_pinned_at_two`) keeps its exact
property — no third element, therefore no untrusted element — instead of being loosened.
**Residual to document at the `ptyxis` row:** bare `ptyxis` may open a tab in an existing
instance rather than a new window, and a single-instance GUI application may not honour the
`current_dir` of the client process. `gnome-terminal` (already in the list, backed by
`gnome-terminal-server`) is the same class, so this is a pre-existing property of the fallback
list rather than something ptyxis introduces.

**D-05 — the source-derived guard is PRESERVED by hoisting named consts, and STRENGTHENED.**
`the_separator_table_covers_every_candidate_find_terminal_probes` (`detail.rs:8608`) greps the
source text of `fn find_terminal()`, splits on the first `[`, and asserts exactly 4 candidates.
Restructuring discovery breaks that parse. Hoist the two lists into named consts and have the
guard parse THOSE by name. Its essential property — the table is derived from source text, so
it cannot drift from the code — survives, over a larger surface.
Strengthening (do this, it is not optional): today the guard's
`matches!(separator, "-e" | "--")` passes for *any* string, because
`terminal_program_separator` returns `-e` by default. That makes the "a candidate added
without a separator decision fails this" claim false. Replace it with a two-way check against
an authored expectations table inside the test: every parsed name must have a row, every row's
name must have been parsed, and the resolved separator must equal the row's.

**D-06 — factor only what is genuinely common.**
`switch_to_session` and the new launch share exactly one thing: the question "are we inside
tmux". Factor `in_tmux()` and have both read it. Do **not** merge the `tmux list-panes` and
`tmux new-window` invocations behind a shared runner — they share nothing but the binary name,
and forcing that would be artificial sharing.

</decisions>
