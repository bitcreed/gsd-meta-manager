<inferred_decisions>
The human is unavailable. These four were decided from the codebase and are flagged for
later audit.

- **ID-01 — Help lives at the definition site, not in a lookup table.** `push()` gains a
  required `help` parameter, so the help text sits on the same source line as the key it
  describes and the compiler refuses a new option that has none. A `HashMap<&str, &str>`
  keyed by config key would compile fine while silently missing an entry.
- **ID-02 — Always-visible help pane, not a toggled one.** `?` is already bound to the
  global help screen at `src/ui/screens/detail.rs:5200`, so a help toggle would collide with
  the key a user would reach for. An always-on pane also costs no discovery.
- **ID-03 — String-kinded keys with conventional values keep `ConfigValueKind::String`.**
  `workflow.context_guard_mode`, `statusline.state_format`, `phase_naming`,
  `phase_id_convention` and `claude_orchestration.execution_backend` each have a small set
  of values GSD actually accepts, but they are read through `str_l` and edited through the
  text-input popup. Promoting them to `Enum` would change the edit affordance and could
  refuse a value a newer GSD accepts. Their known values are named in the summary prose
  instead, and `choices` stays empty for them.
- **ID-04 — The help pane yields to the list on a short terminal.** Below a height floor
  the pane is not drawn at all, so the option list keeps the full area.
</inferred_decisions>
