<diagnosis_do_not_relitigate>
The root cause is CONFIRMED. Do not re-investigate it; implement the fix.

Both failing tests spawn the driver and then call `live_within` (line ~270), which polls
`liveness::is_run_alive` (`src/driver/liveness.rs:187`). That delegates to `probe`, which is
nothing but `cmdline_names_run(pid, run_id)` — a read of `/proc/<pid>/cmdline` checking it
carries both `gsd-meta-manager` and the matching `--run-id`.

**The kernel populates `/proc/<pid>/cmdline` at `execve` time**, within microseconds of
`spawn()` — long before the driver has established its envelope, taken its lock, written
`run.json`, or emitted one journal record. `live_within` therefore returns `true` almost
instantly and the assertions then read artifacts that do not exist yet. That is exactly the
recorded tell: a FAILING run finishes in ~0.53s, a PASSING run in ~6.1s. The fast runs are
the ones where the assertion won the race against the writer.

Two facts that make the fix safe:

- `run.json` is written ATOMICALLY (`src/journal/writer.rs:513-571` builds a `NamedTempFile`
  and `.persist()`s it onto `paths.run_json`), so polling for presence cannot observe a torn
  file.
- `reader::tail_lines` (`src/journal/reader.rs:140-147`) returns **`Ok` with zero lines when
  the file does not exist**. A journal wait that tests `is_ok()` would therefore return true
  immediately and fix nothing. It must test that a record actually PARSED.

M1 (a system-wide `/proc` scan seeing a sibling binary) is not the mechanism here:
`reconcile_all` iterates the registry's projects and reads each project's own
`.planning/runs/` tree off disk, and every test owns a private `TempDir` root. M3
(`isolate_envelope_root`'s process-wide `set_var`) is a real hazard but is not these two
panics: both are "the artifact is not there yet", which is M2. Neither M1 nor M3 is claimed
closed by this task, and neither is known to be live.
</diagnosis_do_not_relitigate>
