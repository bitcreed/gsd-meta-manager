<objective>
Remove the run-id length limit that the macOS `sun_path` limit (103 bytes) puts on the default driverctl socket when the base is a stock `$TMPDIR`. Do it portably and without changing any socket path that resolves today.

Chosen scheme (decided from existing artifacts; human unavailable) `[inferred — audit]`:
- Keep the D-21 name `<run-id>-<sha256(canonical run dir)[:8]>.sock` whenever it fits the platform limit, so every working Linux and macOS path stays the same and Phase 27 D-21 still holds.
- When it does not fit, fall back to a fixed-length name `<16 hex>.sock` (SHA-256 over run id, NUL, canonical run dir; first 8 bytes) in the SAME private `gsdmm-driverctl` directory. The run-id-dependent part is then a constant 21 bytes, so any base up to 65 bytes works under the 103 limit (a stock `/var/folders/.../T/` is 49 bytes; the result is 86 bytes).
- Not chosen, with reasons:
  - "Always hash": it would rename every Linux socket, contradict the D-21 text and hide the run id from `ls`. None of that is clearly better.
  - "Shorter base dir": the only short candidates are shared directories like /tmp, which D-21 / serve.rs fact 4 forbid (squatting).
- This also fixes Linux run ids of 63 to 80 characters under `/run/user/<uid>`, which are refused today (107 limit). That makes things strictly better without changing any existing path `[inferred — audit]`.

Purpose: `driver launch --unsandboxed` on macOS (D-31, re-assessed in quick 261021-0jg) no longer refuses ordinary `<yyyymmdd>-<slug>` run ids. Today it does, and there is no `--sock` override.
Output: updated src/driverctl/serve.rs (pure path function + wiring + tests), one real-binary test in tests/driverctl_serve.rs, an updated `--sock` help text in src/cli.rs, and appended Phase 28 records.
</objective>
