# Quick 260927-t3s: `g` switches the 7:Cfg tab between project and global settings, and the scope is always visible

<objective>
On the detail view's 7:Cfg tab, pressing `g` switches between editing this project's settings (`.planning/config.json`) and the user's global GSD defaults (`~/.gsd/defaults.json`). The active scope must be visible at all times.

**What already exists (verified at planning time).** The codebase already models both scopes:
- `DefaultsEditTarget { Project, Global }` in `src/ui/screens/mod.rs` (~364).
- `ProjectViewCache.defaults_user_config`, loaded from `config_json::load_user_defaults()`.
- `entries_for_cache` (project config layered over the global defaults, with a ` *` marker on inherited values).
- `persist_active_config`, which writes to the target's file.
- A `d` key arm that flips the target.

What is missing:
1. The key the user asked for.
2. An indicator that is always on screen. Today the only cue is the block title: ` Config Settings ` against ` Global Defaults (~/.gsd/defaults.json) `, plus a transient status message.
3. A way to test "writes land in the active scope's file" without touching the operator's real `~/.gsd/defaults.json`. `persist_active_config` calls `user_defaults_path()` (which reads `$HOME`) at write time. That is why existing tests carry comments like "Nothing mutating follows: Global persists to the real ~/.gsd/defaults.json".

**Decision IDs.** D-01..D-03 come from the user's request, in order:
- D-01 (locked): in 7:Cfg, `g` switches editing from project settings to global settings, and back.
- D-02 (locked): it must always be clear whether project or global settings are being edited.
- D-03 (user suggestion, evaluated and adopted, see I-3): a two-tab strip `[Project] | [Global]` that `g` switches between.

Purpose: the user wants to edit global GSD defaults from the Config tab without guessing which file an edit goes to.

Output: the `g` key, a scope strip, a clearer title, footer and help entries, clickable scope labels, and a global-defaults path seam that makes the writes testable. Tests cover all of it.
</objective>

<inferred_decisions>
Inferred decisions (for audit). The human was unavailable, so each of these was decided from the code and the planning artifacts:

- **I-1 — "Global" means `~/.gsd/defaults.json`.** That is what the codebase already models: `DefaultsEditTarget::Global`, `defaults_user_config` and `config_json::user_defaults_path()`. It is also the file gsd-tools layers under project config. No new config concept is introduced.
- **I-2 — `d` stays as an alias.** It keeps working but only the help popup names it. The precedent is `m` after quick 260926-1t1 (D-07/D-08): it stayed a working alias, the strip and footer stopped advertising it, and the help popup documents it. Removing `d` would break muscle memory for no gain. The footer advertises only `[g]`.
- **I-3 — The scope indicator is a two-label strip, not a title-only cue.** This adopts the user's suggestion (D-03). Rationale:
  - (a) The same screen already uses a strip for Docs (` [Files] │ Milestones   ←/→ switch`) and Sessions (` [Sessions] │ Agents`), built by `two_sub_tab_strip`. The Config strip reuses that visual language and adds nothing new.
  - (b) A strip shows both scopes, so the global option can be discovered from project scope. A title only shows the current scope.
  - (c) It gets its own row above the list. Every popup (chooser, text prompt) is laid out in the area below it, so the strip stays visible while a value is being edited, which is the requirement D-02 is hardest on.
  - (d) The bracketed, reversed active label reads in a monochrome terminal and in a text scrape, so a test can assert it.
  - Cost: one row of height. Accepted.
  - The block title is kept and made symmetric (I-13), so the scope reads twice: which scope in the strip, which file in the title.
- **I-4 — Global gets its own highlight colour.** The active `[Global]` label is magenta, bold and reversed. The active `[Project]` label keeps the shared cyan, bold and reversed. Magenta matches the existing magenta ` *` marker for values inherited from global. Colour is only a secondary cue; the brackets are the primary one.
- **I-5 — Arrows and brackets do not switch scope.** On Config, `←`/`→` and `[`/`]` keep switching tabs as they do today. The scope is not a `DetailSubView`, so `sub_tab_pair` stays the single definition of "this tab has sub-views" and needs no change. The strip's hint reads `g switch` where the other strips read `←/→ switch`.
- **I-6 — The project strip explains the ` *` marker.** Its hint ends with `* = inherited from global`. The marker has never been explained anywhere on screen, and this legend is the cheap way to show project-over-global precedence (the coordinator said: only if cheap). Global scope has no fallback, so its strip omits the legend.
- **I-7 — The global path is resolved once and stored in the cache.** It is resolved into `ProjectViewCache.defaults_user_path` at arrival and on `r` reload. `persist_active_config` writes to that resolved path instead of calling `user_defaults_path()` itself. So the path that was loaded is the path that gets written, and tests can point it at a TempDir. A cache that never arrived (every `ctx_on_config_row` test fixture) holds `None` and writes nothing in global scope. No test can touch the real `~/.gsd`.
- **I-8 — The scope labels are clickable.** Quick 260926-dyf D-04 made every strip label on this screen a click target. A strip that looks the same but ignores clicks would be inconsistent. A click SETS the scope (idempotent) rather than toggling it, so the double-click that `App` delivers after a single click is a no-op.
- **I-9 — `g` is guarded like today's `d`.** It is inert while a chooser is open (`defaults_editing.is_some()`). It is text while a value or the filter is being typed, because the existing intercept order in `handle_key` already routes those keys to the input.
- **I-10 — Scope is per project and in memory only, as today.** It lives in the per-project view cache, survives tab changes within the session, and is never written to disk.
- **I-11 — Footer token and status messages.**
  - The footer token is `[g]` followed by ` project/global  `, replacing the old `[d]` token.
  - Status messages:
    - `Editing project config (.planning/config.json)`
    - `Editing global defaults (~/.gsd/defaults.json)`
- **I-12 — Only literal paths are drawn.** The UI shows `~/.gsd/defaults.json` and `.planning/config.json` as static text. The resolved absolute path (it contains the username) never reaches a cell.
- **I-13 — The project title is renamed for symmetry.** ` Config Settings ` becomes ` Project Config (.planning/config.json) `, to match the existing ` Global Defaults (~/.gsd/defaults.json) `.

**Key collision check for `g` on the Config tab (current_view == Defaults). Result: no collision.** Checked against `src/ui/screens/detail.rs` `handle_key` (~3113) and `src/app.rs`:
- The Config text-edit intercept and the filter-typing intercept (~3153) run first, so `g` there is text.

- `App::handle_key` intercepts only Ctrl+C before the screen.
- The only existing Config letter keys are `/`, `x`, `r`, `d`, and Enter/Space.
