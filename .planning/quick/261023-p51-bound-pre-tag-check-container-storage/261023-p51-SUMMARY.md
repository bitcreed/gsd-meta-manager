**2. [Plan premise incorrect] `du -sb` of an empty volume is 0, not >0**
- The plan assumed an empty volume measures more than 0 bytes so `cap=0` needs no special case. On this overlay mount an empty volume measured 0 B, so with cap 0 an empty volume reports KEPT (nothing to wipe) while any non-empty volume is wiped. Behaviour is still "wipe both on every run" wherever there is anything to wipe. Left as is; the `10#` / verdict logic is unaffected.

## Inferred decisions [INFERRED — audit]

- GB means 10^9 bytes; the cap is per volume.
- `0` wipes every run (non-empty volume); empty/unset means the default 20.
- Cap accepts 1-9 decimal digits only, read as base 10 (`08` valid).
- `PRE_TAG_CONTAINER_CLEAN` accepts `0`, empty/unset (off) or `1` (on); anything else is exit 2.
- `--clean` without `--container` rejects a TAG (exit 2).
- Volumes are created inspect-then-create (podman errors on existing names; docker ignores labels on existing ones).
- `CARGO_INCREMENTAL=0` on the inner run, mirroring release.yml's dtolnay/rust-toolchain.
- The label-scoped image prune leaves the BuildKit builder cache untouched (no label filter exists).
- The post-run size report is non-fatal (WARNING, never changes the exit status).
- A failed removal during `--clean` exits 1 and blocks any run.
- One-time manual removal of the legacy unlabelled image by exact ID.
- Default-cap sanity rule evaluated: not triggered, default stays 20 GB.
- Podman verified by smoke only (no full podman container run).
- Storage left CLEAN at the end, not re-warmed (release step 2 `cargo update` would invalidate it anyway).
- Executed on `master` in the main working tree as the orchestrator directed (sequential), bypassing the default-branch guard because `dev` is the configured base branch and the orchestrator explicitly assigned `master`.
