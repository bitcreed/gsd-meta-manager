# Quick 260927-gi9: Roadmap lane gutter computed over visible rows only

<objective>
Fix the Roadmap tab's lane gutter so that folded milestones stop reserving gutter width.

Today `layout_list` in `src/ui/roadmap_graph.rs` calls `assign_lanes` over the full unfolded slot sequence. It drops hidden rows only afterwards; the code comment says folding happens after layout so that rows outside a fold never move. So when v1 … v2 are folded into the shipped summary, v2's phases (8..13) have hidden rows, but their lanes into v3's phase 14 are still active on the visible v3 band row and on 14's merge connector. v3's content gets pushed right by six or seven columns.

The fix: filter the slot sequence down to the visible slots BEFORE lane assignment, so lanes exist only for what is drawn and visible rows pack into the leftmost columns.

Purpose: the user reported the wasted gutter (pasted screen in the task description) and asked for a lane layout computed over what is visible.

Output: a one-site production change in `layout_list` plus doc-comment updates, and regression tests in `roadmap_graph.rs` and `roadmap_view.rs`. The failing tests are committed first, like quick 260926-kes.

**Decision IDs.** D-01..D-07 are the user's request, in order. They are locked scope:

- D-01: compute the lane layout over the visible rows. Lanes that exist only for folded phases are dropped, and visible rows pack into the leftmost columns.
- D-02: edges from folded phases into visible phases (v2 → 14's merge) must not reserve one column per hidden lane. Collapse them: drop them, or at most a single stub. Pick the cleanest and record the choice.
- D-03: this applies to every fold: the shipped summary and named milestone bands.
- D-04: the unfolded layout stays byte-for-byte unchanged.
- D-05: mouse hit-testing and row-to-column math stay consistent with the gutter width.
- D-06: TDD. The failing-test commit lands first. It includes a render test with folded milestones asserting the compact phase-column position, and an unfolded-unchanged test.
- D-07: gates are `rtk proxy cargo test --no-fail-fast` (only the git-version witness in `src/envelope/policy.rs` may fail) and `cargo clippy --all-targets`. Never pipe raw test output through grep or awk.

**Inferred decisions (for audit).** The human is unavailable. Copy these into the SUMMARY under "Inferred decisions". Number execution-time additions E-1, E-2, …

- **[I-1] Edges with a hidden endpoint are dropped entirely; there is no stub.** This covers both directions: hidden → visible (v2 → 14) and visible → hidden (a visible phase whose dependent is folded).
  - How it works: `assign_lanes` already builds `children` only for edges whose parent and child both have a position in the sequence it walks. Feeding it the visible sequence therefore drops those edges with no change to its body.
  - Why drop rather than stub: it matches how external dependencies (phases not in the list) already render, which is with no lane. A stub would still cost a column, and it would need a new glyph or row kind. The folded band row plus the detail pane's Needs/Unblocks lists already tell the user the edge exists.
  - Consequence: a visible phase whose only parents are hidden is laid out as a root (lowest free lane, never the previous phase row's lane).
- **[I-2] No bridging edges are drawn, and the transitive reduction is not recomputed over the visible subgraph.** A chain visible → hidden → visible draws no lane between the two visible phases. Recomputing the reduction or synthesising bridge edges would put lines on screen that do not match the roadmap's declared-and-reduced edges. It is outside the requested fix.
- **[I-3] Everything except rows and lanes stays computed over the full graph.** That covers PhaseFacts, `start_now`, bands, `max_wave`, `notes`, and the full-sequence `order`/`pos` used for list order. Folding remains a view concern for facts, so the detail pane, `h`/`l` edge walks and `unfold_for` behave exactly as before.
- **[I-4] The old fold-stability invariant is given up.** Previously, toggling a fold never moved rows outside it. Now toggling a fold may move the lanes of rows outside the fold; that is the direct consequence of D-01. The unfolded layout is byte-identical because, when nothing is hidden, the visible sequence equals the full sequence, so `assign_lanes` receives identical input.
- **[I-5] The existing test `folding_a_band_hides_its_rows_but_not_the_lanes_elsewhere` encodes the old behaviour.** It asserts that M4's band row keeps 13's fork lane to the folded phase 16. It is rewritten and renamed to the new expectation in the RED commit (golden G3), not deleted.
- **[I-6] No production change in `roadmap_view.rs` or `detail.rs`.**
  - The gutter width comes from the model: `RoadmapView::columns` takes the max visible lane cells, floored at `MIN_LANE_CELLS`.
  - The fold-marker rects come from the drawn spans (kes I-3).
  - Row clicks map by row index through `RoadmapModel::target_at`.
  - So a narrower model narrows the gutter and moves the hit rects with it. The tests prove this instead of adding code. Grep confirmed nothing outside `roadmap_view.rs` and `roadmap_graph.rs` does gutter math.
- **[I-7] The fixture is synthetic: CROSS_FOLD.** It mirrors the reported shape: shipped v1 with no listed phases, and shipped v2 whose six independent phases 8..13 all feed v3's 14, plus v3 14..19 and "Milestone 6: Web frontend" with 20. The checked-in `ttbook` fixture was not used because its v2 is not shipped.
</objective>
