<objective>
Close the two Phase 28 security follow-ups recorded in `.planning/phases/28-sandboxed-driver-launcher/28-SECURITY.md` ("Follow-ups", lines 87-90).

1. **Sibling run dirs are writable from inside the sandbox.** Only the current run dir is ro-bound (`src/launcher/sandbox.rs:274-280`). The rest of `<project>/.planning/meta-manager/drivers/` comes in through the read-write project bind, so a driver can rewrite another run's LOG.md, state.json or DIRECTION.md. Fix: in the pure profile builder `bwrap_argv`, mount an empty tmpfs over the drivers dir directly after the project bind. Then re-establish the run's own binding exactly as today: the ro-bind of the run dir, then `/dev/null` over `launcher.lock` and `DIRECTION.lock`.
2. **`src/launcher/auth.rs` doc comments overclaim.** They say the refresh token is never held in this process's memory, but `host_access_token` parses the whole credentials file. Correct them.

**Decisions** (the human is unavailable; inferred choices are marked for audit):
- **Hidden, not read-only** `[inferred — audit]`. The Phase 30 Driver tab reads other runs from the TUI, outside the sandbox, so the driver has no reason to see sibling runs. Hiding also stops a driver from reading other runs' goal text.
- **Exact-parent guard** `[inferred — audit]`. The tmpfs is emitted only when `run_dir.parent()` equals `project.join(DRIVER_RUNS_REL)`. Production always meets this: `validate_run_dir` (`src/driverctl/serve.rs:187-239`) refuses any run dir that is not directly under the canonical drivers dir, and every launcher entry point validates before it builds `LaunchPaths`. A looser rule (a tmpfs over whatever the parent happens to be) could hide the whole checkout or a source subtree in a hand-built spec. When the guard does not match, the profile is exactly today's.
- **Plain writable `--tmpfs`, same as the home `TMPFS_MASK_DIRS`** `[inferred — audit]`. Anything the driver writes into it exists only in the sandbox's mount namespace and never reaches the host. The live probe asserts this from the host side.

Purpose: a sandboxed driver can no longer tamper with, or read, any other run's directory, and every existing guarantee for its own run dir is unchanged.
Output: a hardened `bwrap_argv`, pinned by unit and golden tests; a live probe proving siblings are hidden; an accurate auth doc; the SECURITY follow-ups marked resolved.

Out of scope: any Phase 30 file (nothing under `.planning/phases/30-*`, no Phase 30 source). No change to `run.rs`, `serve.rs`, the master prompt, or any other part of the mask lists.
