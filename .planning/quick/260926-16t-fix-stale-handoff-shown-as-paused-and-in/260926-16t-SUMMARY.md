# Quick 260926-16t: Stale HANDOFF shown as Paused; phase counts disagree - Summary

A HANDOFF that is behind STATE.md (by phase, or by more than an hour of `last_updated`) is now ignored in the parser, so no badge, needs-human flag or `Paused:` banner shows for it. The dashboard `k/n phases` cell, the Roadmap header (full and compact) and the active band count now all come from one function, `ProjectState::phase_progress()`. For ttbook it returns 5/6 everywhere; before the fix the dashboard said 4/6 and the header said "5 of 11".

## Root causes

- **BUG A (stale handoff shown as paused):** `detect_handoff` (src/state_reader/mod.rs:447-494 before this change) returned `paused=true` for any non-empty HANDOFF. `parse_project_state` copied that result verbatim at mod.rs:708-711 and never compared it with STATE.md. All consumers read `paused` / `pause_context`:
  - the badge (normal.rs:273)
  - `needs_human` (screens/mod.rs:1542)
  - the Paused banner (detail.rs:4257)
- **BUG B (counts disagree):** the two screens read different sources.
  - The dashboard read `completed_phases/total_phases` (normal.rs:869). Those numbers are overridden by ROADMAP's `## Progress` table, which lags the disk.
  - The header read `model.done/model.total` (detail.rs:1660, roadmap_graph.rs:899-900). That counted every node, including 5 build-phase placeholders from future milestones, which is how it reached 11.

## Rules implemented

- **Stale handoff:** `handoff_staleness(handoff_phase, handoff_written, state_phase, state_last_updated)` in src/state_reader/mod.rs.
  - R1 `PhaseBehind`: the handoff phase is lower than `state_md_phase_number`.
  - R2 `StateNewer`: STATE.md `last_updated` is later than the handoff's written time + 3600 s.
  - R1 is reported when both rules hold. A missing input disables only its own rule.
  - When a handoff is stale: `paused=false`, `pause_context=None`, and `stale_handoff=Some{phase, state_phase, written, reason}`.
- **Phase count:** `phase_progress()` counts `roadmap_entries()` (phases then planned phases, deduped by `phase_key`), filtered by `in_current_milestone`.
  - Scope: the active milestone's phases plus unbanded ones; with no active milestone, only unbanded ones.
  - Done: `phase_is_done` (disk `>= Executed`, or the checkbox when there is no directory or no entry).
  - When the scope is empty, it falls back to `(min(completed, total), total)`.
- **UI:** the detail header shows a DarkGray + DIM line such as `  Stale HANDOFF ignored (phase 12, 1d old) - STATE.md is at phase 13` (or `... - STATE.md updated since`) where the Paused banner would be. The help legend now reads `paused - a current (non-stale) HANDOFF`; no help test pins the width, so the full wording fits.

## [inferred] decisions (as implemented, for audit)

- H-1 / H-2: R1 compares against STATE.md's declared `current_phase` only. It does not use `active_phase_number()`.
- H-3: the written time is JSON `timestamp` (RFC 3339, converted to UTC). If that is missing or unparseable, the file mtime is used. HANDOFF.md always uses mtime. Invalid JSON also uses mtime.
- H-4: the grace is `HANDOFF_STALE_GRACE_SECS = 3600`.
- H-5: the JSON `status` field is ignored.
- H-6: JSON `phase` may be a string or a number. It goes through `extract_phase_id`, then `PhaseNum::parse`. `"04"`, `"18.1"`, `"Phase 12"` and `12` are all tested.
- H-7: staleness is decided once, in `parse_project_state`. A current handoff and an invalid-JSON handoff behave exactly as before.
- H-8: the dashboard shows nothing for a stale handoff. The detail header shows the dimmed line. The phase part or the age is left out when unknown, and the parentheses are dropped when both are unknown.
- C-1..C-5: implemented as planned. The header wording is still `{k} of {n} phases done`, and `roadmap_summary_line` no longer takes `model`.
- C-6: `is_milestone_complete` still reads the bookkeeping. A comment now says why.
- C-7: `ListNode.done` (from `phase_is_done`) now drives the band and model done counts. The markers, glyphs and `start_now` are unchanged.
