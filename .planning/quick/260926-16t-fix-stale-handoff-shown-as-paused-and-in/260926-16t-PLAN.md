# Quick 260926-16t: Stale HANDOFF shown as Paused; Roadmap header vs dashboard phase counts disagree

<objective>
Fix two bugs observed on the registered project ~/projects/python/ttbook (READ-ONLY fixture, never modify it):

BUG A: a stale HANDOFF is shown as Paused. The Roadmap header shows "Paused: Dispatch /gsd-discuss-phase 12 ..."
while STATE.md says `current_phase: 13`, `status: executing`, `last_updated: 2026-09-25T22:34:52.070Z`.
ttbook's HANDOFF.json has `"phase": "12"`, `"status": "ready"`, `"timestamp": "2026-09-24T21:30:00-05:00"`
(file mtime 2026-09-24 20:49 -05:00).

BUG B: the counts disagree. The Roadmap header says "5 of 11 phases done" and the dashboard row says "4/6 phases".

Purpose: the dashboard must be trustworthy at a glance (core value). Today a stale handoff raises the pause badge
and the red needs-human flag. Two screens also give different progress numbers for the same project.

## Root causes (verified, file:line)

BUG A: `detect_handoff` (src/state_reader/mod.rs:447-494) returns paused=true for ANY non-empty HANDOFF.json/.md.
`parse_project_state` copies that verbatim (mod.rs:708-711) and never looks at STATE.md. The consumers all read
`ProjectState::paused` / `pause_context` and nothing else:
- the dashboard pause badge, src/ui/screens/normal.rs:273
- `needs_human`, src/ui/screens/mod.rs:1542, which also drives the red flag and the /h filter
- the Roadmap-header Paused banner, src/ui/screens/detail.rs:4257-4275

Because they all share that one input, deciding staleness once in the parser fixes every consumer at the same time.

BUG B: the two counts come from different sources.
- Dashboard `4/6`: src/ui/screens/normal.rs:869 shows `completed_phases/total_phases`. The ROADMAP `## Progress`
  table overrides the STATE.md frontmatter here (src/state_reader/mod.rs:557-558, then 642-647). ttbook's table has
  6 rows and 4 of them are `Complete`. That bookkeeping lags: phase 12 has 25/25 SUMMARYs,
  12-VERIFICATION.md `status: passed` and a complete 12-UAT.md, yet its row still says "In Progress".
- Header `5 of 11`: src/ui/screens/detail.rs:1660 (and the compact form at 4239) shows `model.done/model.total`
  from src/ui/roadmap_graph.rs:899-900. That is every node in the list, including:
  - the 6 GSD phases 8-13
  - the 5 `#### Build phase 14-18` placeholders of FUTURE milestones 3-5 (`planned_phases`)
  So total = 11. Done = marker `+` count = 8, 9, 10, 11 plus 12, which is disk >= Executed per `PhaseMarker::decide`
  (mod.rs:413-418). That gives 5.
- Is the "11" source itself buggy? Partly by design. v1's phases 1-7.1 sit in the shipped `<details>` block as
  NON-bold `- [x] Phase 1: ...` lines, and `checklist_re` (src/state_reader/roadmap_md.rs:160-164) requires
  `**Phase`, so they are not parsed. The shipped summary row compensates through `declared_phase_count`. This parser
  gap is NOT the cause of 11, which is current milestone 6 plus future placeholders 5. It is out of scope; leave it.

A read-only probe across all 14 registered projects (planner scratchpad) showed the bookkeeping is not even
consistently milestone-scoped. cdr-configurator's Progress table is whole-project (19/19) while its active milestone
has 10 phases. The bookkeeping also lags the disk: usbee 3/4 vs disk 4/4, wordoclock 5/6 vs 6/6, shopify 0/3 vs 2/3,
ttbook 4/6 vs 5/6.

## Decisions (human unavailable; every one is [inferred] and meant for later audit)

HANDOFF staleness (BUG A):
- [inferred] H-1: a handoff is STALE if either rule holds.
  - R1 (PhaseBehind): the handoff's phase is numerically LOWER than STATE.md's declared `current_phase`
    (`ProjectState::state_md_phase_number`).
  - R2 (StateNewer): STATE.md frontmatter `last_updated` is LATER than the handoff's written time plus a grace of
    1 hour.
  - R1 wins the reported reason when both hold.
- [inferred] H-2: R1 compares against STATE.md's declared number only, NOT `active_phase_number()`. The disk frontier
  can legitimately lead a phase whose plans are executed but still being verified, and a handoff for that phase is
  still current. GSD advances `current_phase` deliberately.
- [inferred] H-3: the handoff written time is the JSON `timestamp` field (RFC 3339) when present and parseable.
  Otherwise it is the HANDOFF file's mtime. HANDOFF.md always uses mtime.
  - Evidence for preferring the declared timestamp: cdr-configurator's HANDOFF.json was touched after the fact
    (mtime 2026-04-28), later than its STATE.md (2026-04-22). Its declared timestamp is 2026-04-18. The handoff is
    genuinely stale: it asks to plan phase 18.1, which is `Complete` on disk. Only the declared timestamp catches it.
- [inferred] H-4: the 1-hour grace absorbs same-session STATE writes and hand-written timestamps that drift by tens
  of minutes. ttbook's JSON timestamp is 41 min AFTER its own mtime. The real stale gaps seen are 20 h, 4 d, 1 month
  and 4 months.
- [inferred] H-5: the JSON `status` field is ignored. GSD's pause-work template always writes `paused`, and ttbook's
  `ready` is coordinator-specific.
- [inferred] H-6: the phase is read from JSON `phase` as either a string or a number. It is normalised with
  `roadmap_md::extract_phase_id` and then `phase_num::PhaseNum::parse`, so `"04"`, `"12"`, `"18.1"` and
  `"Phase 12"` all work. An unparseable phase disables R1 only.
- [inferred] H-7: the decision is made once, in the parser. When a handoff is stale:
  - `paused = false`
  - `pause_context = None`, so the stale next_action is never shown anywhere
  - the new `stale_handoff: Option<StaleHandoff>` is set
  Current and invalid-JSON handoffs keep today's behaviour exactly. Invalid JSON has no phase or timestamp, so only
  mtime-based R2 can apply.
- [inferred] H-8: presentation. The dashboard shows nothing for a stale handoff: no badge and no flag. The detail
  header, where the Paused banner sits, shows one DarkGray+DIM line, for example:
  - `  Stale HANDOFF ignored (phase 12, 1d old) - STATE.md is at phase 13` for R1
  - `  Stale HANDOFF ignored (phase 21, 31d old) - STATE.md updated since` for R2
  Omit the `phase N` part or the age when unknown. The file stays visible as a cleanup hint, but it no longer claims
  to be the current state.
- Real-world effect (verified by probe): all four registered projects that show paused today have stale handoffs
  under H-1:
  - ttbook: R1, 12 < 13
  - usbee: R2. Its STATE is 4 months newer and its status is `complete`.
  - gsd-meta-manager: R2. The handoff is round-9 of phase 21 and STATE is 1 month newer.
  - cdr-configurator: R2, per H-3.

Phase counts (BUG B):
- [inferred] C-1: ONE definition, `ProjectState::phase_progress() -> PhaseProgress { done, total }`, used by:
  - the dashboard cell
  - the Roadmap header, both the full and the compact form
  - through the shared per-phase predicate, the Roadmap band counts
- [inferred] C-2: scope is the CURRENT milestone's roadmap entries. The entries are `phases` then `planned_phases`,
  deduped by `phase_key` with the GSD phase winning, exactly as `roadmap_model_for` lists them. They are filtered by
  the Roadmap's own band rule:
  - with an active milestone `a` (`roadmap_md::active_milestone_index`), a phase is in scope when
    `milestone_index_of(p)` is `a` or None
  - with no active milestone, a phase is in scope when `milestone_index_of(p)` is None. Those phases are the
    synthetic/unbanded ones and, in a roadmap without milestones, all of them.
  ttbook gives 8-13, total 6. Future placeholders 14-18 belong to milestones 3-5 and are excluded.
- [inferred] C-3: a phase is done when its implementation is finished. That means disk status >= `Executed`, or the
  ROADMAP checkbox when the phase has no directory or no disk entry. This is the exact done-half of
  `PhaseMarker::decide`, extracted into `phase_is_done` so there is one threshold.
  - It counts the CURRENT phase too, so a finished milestone reads n/n rather than n-1/n.
  - Why not "verification passed": that would show cdr-configurator 3/10 for a shipped milestone, because older
    phases lack VERIFICATION files.
  - Verification state stays visible through the existing badges.
- [inferred] C-4: fallback. When the scope is empty (no parsable roadmap phases: picsync, aiFlowAgent, hitchmatch,
  bitcreed.us), use the bookkeeping `(min(completed_phases, total_phases), total_phases)`, so those rows are unchanged.
- [inferred] C-5: the header keeps its wording, `{k} of {n} phases done`. The milestone label directly before it
  names the scope. No whole-project count is added, because the band rows and the shipped summary row already carry
  per-milestone counts.
- [inferred] C-6: `is_milestone_complete` (normal.rs:886-890) stays on the bookkeeping `completed_phases >= total_phases`.
  "Milestone Complete" is GSD's own statement about closing a milestone, not a count, and switching it would flip
  status cells for milestones whose last phase awaits verification (for example wordoclock).
- [inferred] C-7: band counts use the same predicate through a new `ListNode.done` flag. Without it, the active band
  would disagree with the header whenever the current phase is itself executed. This repo's phase 19 is exactly that
  case.
- Expected dashboard numbers after the fix (probe):
  - ttbook 5/6
  - cdr-configurator 10/10
  - usbee 4/4
  - wordoclock 6/6
  - shopify-orderly-rescue 2/3
  - gsd-meta-manager 10/12
  - mailbot, sentriq and daily-vow are unchanged, and so are the fallback projects
