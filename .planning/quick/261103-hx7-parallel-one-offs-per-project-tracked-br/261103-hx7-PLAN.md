This builds on quick 261103-f5y (one-off dispatch) and 261103-gt1 (stream, inbox, viewer, spend). It adds:
- any number of concurrent one-offs per project,
- the run's branch tracked in the user's repo as `gsd-oneoff/<run-id>`,
- a merge-based landing whose conflicts a short sandboxed resolver agent session resolves,
- a multi-run Driver-tab UI,
- one sandbox hardening fix (mask the app's data and config roots wherever they live),

Purpose: one live one-off per project blocks parallel small work, and a run that falls behind its target can only be discarded. This plan lets several run at once, keeps their work visible as branches, and lands them even when the target moved.

Planner-inferred decisions. The human is unavailable. Carry each one into the SUMMARY tagged `[inferred — audit]`.
- I-01 Run ids are claimed by a non-recursive `DirBuilder::new().mode(0o700).create(<project_dir>/<id>)`, trying `-2`, `-3`… on `AlreadyExists`. Today's `unique_run_id` + recursive create would hand two simultaneous launches the same id. The daemon child (given `--run-id`) opens the claimed dir. The project-level `oneoff.lock` is never taken again; it is only probed for legacy runs.
- I-02 One helper, `store::live_seen(project_dir, run_dir, run_id)`, chooses the lock. If `<run-dir>/run.lock` exists (symlink_metadata), it probes that; otherwise it probes the project's `oneoff.lock`. `read_view`, the inbox liveness check, `stop` and `run_detached`'s readiness wait all use it.
- I-03 `--run-id` is added to `status`, `stop`, `send` and `budget`. `attach` keeps its own, and every verb uses one `store::resolve_run`. Omitted means the newest run. `status`/`stop`/`send`/`budget` refuse (exit 1) when more than one run may be live (`LiveState::may_be_live`) and list those ids. `attach` follows the same rule.
- I-04 `task list <project> [--json]` prints every run, newest first: id, live state, mode, outcome or report status, commits, tracked branch, last landing. It is the CLI half of the run-history todo (C-31). The ids of concurrent runs are otherwise only in `task run` stdout.
- I-05 `task run` no longer exits 3. The `task_cli.rs` header and the docs say so. `LauncherError::Locked` remains for a per-run lock collision, which I-01 makes unreachable in normal use.
- I-06 The masks cover BOTH `dirs::data_local_dir()/gsd-meta-manager` (one-off run dirs with inboxes, driver config dirs, push mirrors) AND `dirs::config_dir()/gsd-meta-manager`, because the stored run OAuth token (`launcher::auth::token_path`) lives there. An `XDG_CONFIG_HOME` outside `$HOME` makes that token readable through `--ro-bind / /` today: the same issue (C-33). A root is masked only if it exists and is lexically under neither `$HOME` nor `/tmp`; duplicates are dropped. The in-sandbox commands (`taskctl`, `driverctl`, `bridge`) read neither root: `src/main.rs:58-80` dispatches them before any config load. The driver's run dirs live under the project, whose siblings are already masked. Its config dirs and mirrors are under the data root.
- I-07 The masks reach the argv through a new `sandbox::bwrap_argv_masking(spec, mode, masks, command)`, and `bwrap_argv_with` delegates to it with no masks. `SandboxSpec` gets NO new field, because `tests/launcher_sandbox.rs` builds it literally and must stay unedited. Each `--tmpfs <root>` sits right after the non-project `$HOME` entries and immediately before `--bind <project> <project>`, so the clone, the guard binds, the run/report dir, the config dir and the sockets are re-established on top. Bind sources resolve on the host, so the gitconfig bind is unaffected.
- I-08 `RunRecord` gains `tracked_branch: Option<String>` (the full ref when it was made or already matched) and `tracking_note: Option<String>` (why not, or the mismatch), both serde-default.
- I-09 Discard deletes the branch with `git update-ref -d refs/heads/gsd-oneoff/<id> <recorded head>`. That is an atomic compare-and-delete with exactly C-08's "only while it points at the recorded head" semantics, without a check-then-act race.
- I-10 Every git command in a land clone goes through `push::git_mirror_only` (hooks off; host global and system config off, so an agent-written `.gitattributes` cannot reach a host filter driver). The merge identity is passed as `-c user.name=… -c user.email=…`, read from the project's effective config with `push::git_in(project, ["config", "user.name"])`. With no identity the land refuses: "git has no user.name/user.email for this project".
- I-11 The resolver never runs unsandboxed: its posture is decided with `unsandboxed = false`. On a host without the sandbox a conflicted landing refuses ("the conflict resolver needs the sandbox"). FF and clean merges still land.
- I-12 The land runs in-process. The CLI blocks; the TUI uses `spawn_blocking` as today (C-20). `land::merge` takes `&LandOptions { egress_allow, user_stop }`.

  - The TUI passes a never-set flag. If the TUI exits, bwrap's `--die-with-parent` ends the resolver, the land lock goes free, and nothing has landed.
- I-13 The land lock is `<run-dir>/land.lock` (`driver::lock` flock, holder = the run id, short retry budget). `land merge` refuses while it is held ("a landing of this run is already in progress"), and so does `land discard`.
