<objective>
Close 30-REVIEW WR-13. The WR-08 fix (quick 261028-t3f) stopped a host `hooks` or `permissions` value that is not an object from replacing the launcher's gate. One level down the same hole remains: in `managed_settings` (src/launcher/config_dir.rs:568-629), a host hook event whose value is not an array, or a permissions list that is not an array, is copied as written for any name the launcher does not already hold. A malformed matcher entry is appended right next to the gate's own entries. The managed file can then be schema-invalid beside the gate hooks and the deny list.

Fix it fail closed, in the WR-08 style. Wrong-shape nested values are dropped. Lists keep their well-formed entries and lose the rest, which is how Claude Code itself treats an invalid list entry. Well-formed host policy still merges. The launcher's gate hooks and its DENY_TOOLS deny list survive whatever shape the host values have. Apply the same filter in the degraded posture, where the per-run settings.json is the safety tier. Pin it with an end-to-end seed test from host files on disk plus shared shape tables for both postures. Correct the doc claims, and record WR-13 as fixed.

Purpose: on a bwrap launch the managed tier carries the whole gate (28.1 D-12/D-13). Claude Code documents per-field repair of a managed `permissions` block. For example, while `ask` or `deny` cannot be read it withholds `allow` and `additionalDirectories`. It documents no such repair for `hooks`. So what a malformed `hooks.<event>` does to the gate entries beside it is unspecified. The project rule from WR-08 and IN-03 applies: the safety tier must not depend on how Claude Code treats a bad file.

Output: three pure shape helpers wired into both merge paths, one end-to-end seed test, three unit shape-table tests, one inverted assertion, corrected doc claims and one disposition row set to fixed.

Inferred decisions (the human is unavailable; recorded for later audit):
- I-1 `[inferred — cleanup 2026-10-28]`: drop and normalize, never refuse. A wrong-shape event, list or setting is omitted. A list keeps its well-formed items in order. An event or list left with no well-formed item adds no key. Refusing the launch would let one administrator typo block every driver run, the same reasoning as t3f I-1. Claude Code's managed-settings doc ("Invalid entries in managed settings") strips an invalid list entry and enforces the valid subset, so normalizing matches it.
- I-2 `[inferred — cleanup 2026-10-28]`: this deliberately departs from the review's suggested fix for `permissions`. The review's loop drops every non-array `permissions` value. But Claude Code documents string and bool settings inside `permissions` (code.claude.com/docs/en/settings-reference: `defaultMode`, `disableBypassPermissionsMode`, `blockReadsOutsideWorkingDirectories`), and dropping them would hide host security policy, against the "merged in, never hidden" contract. The rule is therefore: the four list names `allow`, `ask`, `deny` and `additionalDirectories` must be arrays, of which only string items are kept. Any other `permissions` key is kept only when its value is a string or a bool, so arrays, objects, null and numbers are dropped.
- I-3 `[inferred — cleanup 2026-10-28]`: where the hook shape check stops. It checks the containers and the one discriminator every hook has: the event value is an array, each entry is an object, `matcher` is absent or a string, `hooks` is an array, and each hook item is an object with a string `type`. It does not check per-type fields (`command`, `url`, `prompt`, `timeout`) or event names. Those vary by Claude Code release, and Claude Code reports an unknown event name as a per-entry warning.
- I-4 `[inferred — cleanup 2026-10-28]`: the degraded posture gets the same filter even though WR-13 names only `managed_settings`. The task's invariant, that the gate hooks and deny entries always survive, does not depend on the posture. With a gate, the per-run settings.json is the only safety tier. At HEAD, `filter_user_hooks` keeps a non-array event and an entry whose `hooks` is not an array (config_dir.rs:475-481), which puts a malformed entry next to the gate's `Agent|Task` entry. The WR-08 fix pinned both postures, and `insert_gate_hooks` documents that the two postures must not drift. The filter runs in both `settings_transform` postures, giving one code path. A non-object top-level `permissions` with `gate = None` is not in scope and stays as it is.
- I-5 `[inferred — cleanup 2026-10-28]`: the IN-03 test's closing assertion (config_dir.rs:868-869) pins the WR-13 defect, because it expects a non-array `ask` to be copied. It is inverted, not deleted. Its deny-list assertions stay.
- I-6 `[inferred — cleanup 2026-10-28]`: a `permissions` setting keeps today's precedence. The first host doc that sets it wins (`entry(..).or_insert`). Changing that precedence is not part of WR-13.
- I-7 `[inferred — cleanup 2026-10-28]`: the disposition row follows the Phase 30 file's own precedent (WR-11, WR-12 rows): `fixed by quick <id> <sha> (<what> [inferred — cleanup 2026-10-28])`. The 28 WR-08 and 29 WR-02 rows describe the top-level fix, are still accurate and stay unchanged.
