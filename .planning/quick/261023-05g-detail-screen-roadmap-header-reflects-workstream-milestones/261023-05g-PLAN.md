<objective>
The Detail screen's Roadmap tab header summary line currently describes only the project's own milestone, for example ` sentriq · v0.12 Actuation Routines · phase 16 phase_complete · 8 of 9 phases done`. Make it also summarise each parallel workstream's milestone, as in `ws v0.13 7/7 · ws v0.14 4/6`. The numbers must match the workstream bands that commit d1b1457 added to the same tab. This closes the `unresolved:` entry in `.planning/debug/resolved/workstreams-not-surfaced.md` that reads "the Roadmap header line (`v0.12 … 8 of 9 phases done`) still describes the project's own milestone".

Purpose: a project with parallel milestones should show all of them at the top of the Roadmap tab without scrolling to each band, consistent with the dashboard's `ws v0.14 …` lines.
Output: a `roadmap_summary_lines` helper in `src/ui/screens/detail.rs`, `render_roadmap` wired to it, and regression tests on the existing sentriq-shaped fixture.

Inferred decisions (human unavailable; each marked for audit):
- [INFERRED — audit] D-1 Count source: each segment's k/n is read from the roadmap MODEL's scoped `BandFacts` (`done`, `total`), not from `ws.state.phase_progress()`. This makes the header equal to the band's own `4/6` by construction. A workstream band counts every roadmap entry of the workstream, while `phase_progress` filters to the current milestone, so the two could diverge on a multi-milestone workstream roadmap. `render_roadmap` already builds this model before the header, so this costs no extra I/O or parse.
- [INFERRED — audit] D-2 Segment text: `{tag} {done}/{total}`, exactly the task's example form. `tag` is the model's escaped `ScopeFacts.tag`, which is `crate::app::workstream_tag(ws)`, so `ws` / `ws*` and the STATE.md milestone label (`workstream_milestone_label`) match the band and dashboard vocabulary. The milestone NAME (`Voice Mechanic`) is left out because the band carries it and the header must stay short. Segments are joined to the project's count and to each other by the existing DarkGray ` · ` separator. Each segment is styled `Color::Magenta`, the workstream cue from `.planning/phases/18-driver-tab-live-watch-durable-injection/18-UI-SPEC.md` (§ "Magenta gains one new meaning"), and the `ws` word carries the meaning, so colour is never the only signal.
- [INFERRED — audit] D-3 Width ladder (80x24 has no row to spare, per the Phase 24 header design, so a row is spent only when nothing else fits):
  (1) the full project line plus all segments fits: one line;
  (2) else the project's count compacted to `k/n done` (the existing Mockup C rule) plus all segments fits: one line;
  (3) else line 1 is exactly the pre-change summary line (full if it fits, otherwise compact), and a continuation line directly below holds ` ` + the segments. If the segments overflow that line, whole trailing segments give way to a `ws +N more` tail (the dashboard's own overflow vocabulary from 0fd27fa), so no segment is cut mid-word. This matches the summary line's existing "never cut mid-word" rule.
- [INFERRED — audit] D-4 Every workstream gets a segment, including one whose roadmap lists no phases. That segment reads whatever its band reports (today `0/0`), mirroring the project's own `0 of 0 phases done`. It is never silently dropped.
- [INFERRED — audit] D-5 Flat projects (no workstreams) are byte-for-byte unchanged: same single line, same compaction trigger.
</objective>
