<objective>
Cap pull-request creation per project per rolling day and per run, enforce it from the
`PreToolUse` guard that is D-06's second layer, and generate the settings file that delivers that
guard — with the silent-ignore hazard that file carries closed by construction (SAFE-06, D-06,
D-07, D-19, D-20).

Purpose: this plan builds the only layer that sees a tool call before it runs, which makes it both
the most useful and the most dangerous surface in the phase. The danger is named in the codebase
already: `src/executor/mod.rs:225-239` records a reproduced 180-240 second hang caused by
`PreToolUse` hooks with no timeout, and `--setting-sources project` is the shipped mitigation. The
envelope's own hook must not reintroduce the bug it was born from.

Output: an append-only ledger outside the repository, a fast network-free guard with an explicit
timeout, and a settings file that is round-tripped and compared before the run is allowed to start.

Reversibility note: D-07, D-19 and D-20 are locked decisions in `19-CONTEXT.md`. Ratings are
recorded on the tasks; no `checkpoint:decision` is inserted.
</objective>

    where `at` is RFC3339 UTC at **second** precision, produced the same way `JournalRun::finish`
    and the opt-in stamp produce theirs, so timestamps compare directly without normalising.

  - `pub enum CapVerdict { Permit { used_24h: u32, used_run: u32 }, Refuse { reason: ParkReason, used_24h: u32, cap_24h: u32, used_run: u32, cap_run: u32 } }`
  - `pub fn record_and_check(alias: &str, entry: &LedgerEntry, policy: &EnvelopePolicy) -> anyhow::Result<CapVerdict>`.

**Ordering is the decision (D-20).** The entry is appended **before** the verdict is returned, not
after the tool call succeeds. Record the rationale in a doc comment in the shape
`writer.rs:101-107` uses for its own asymmetry: the guard is the only point that observes the
attempt, and a pull request opened by a path the guard did not see is one the ledger cannot know
about. Under-counting is the failure that matters, so the cap is deliberately biased to over-count
— a recorded-but-failed attempt costs one slot out of three. State that this is the correct
direction to be wrong in, and make the refusal message say it too, rather than leaving a user to
discover it.

**Append-only, torn-write tolerant.** Open with `create(true).append(true)` and write one JSON
object per line, the shipped NDJSON discipline. On read, follow the tolerant-parse posture
`reader.rs:196-211` established — but invert its disposition for this consumer and say why: a
malformed line in a run journal is skipped because dropping one observation is cheaper than
failing a read, while a malformed line in a cap ledger is **counted**, because a line the reader
cannot parse is an attempt that happened and forgetting it under-counts.

**Window arithmetic.** Compare RFC3339 timestamps through `chrono` at second precision. Use no
floating-point arithmetic anywhere in the decision. State the boundary contract explicitly in the
doc: the window is inclusive at exactly 24 hours, so an entry at the boundary counts. Count with a
saturating accumulator so an implausibly large ledger cannot wrap a counter into a permit.

**Rolling, not calendar.** Say in the doc why: a calendar day lets a run at 23:50 open three and
then three more ten minutes later.

**Location.** The file lives under the alias's envelope directory, outside the driven repository,
so an agent cannot reset its own cap by deleting a tracked file. Assert that in a test rather than
only stating it.

Add `pub fn write_settings(alias: &str) -> anyhow::Result<PathBuf>` to `src/envelope/hooks.rs`,
generating `<envelope_dir>/settings.json`.

**Three mitigations, and all three are required (D-07).** The agent CLI's own help states, for
print mode, that settings files failing validation are silently ignored with no error dialog. A
malformed envelope settings file therefore **disarms silently**, which is the single most dangerous
fact this phase rests on:
  1. **Typed, never templated.** Build a `#[derive(Serialize, Deserialize)]` struct tree describing
     the hook registration and serialise it with `serde_json`. No `format!`, no string
     concatenation, no template file. A templated settings file is a settings file with a hand-made
     syntax error waiting in it.
  2. **Round-trip and compare.** Immediately after `persist`, read the file back, deserialise it
     into the same struct tree, and compare against the value that was written. On any mismatch,
     return an error that **refuses the run** rather than warning. Place this check directly after
     the persist call, the position `19-PATTERNS.md` records for it.
  3. **Never the sole carrier.** Every control this file registers must also be carried by argv or
     by a git hook. Add a doc comment enumerating the controls and, for each, naming its second
     carrier — the tool denylist is also on argv via `--disallowedTools`, and the push boundary is
     also on the pre-push hook. A silently ignored settings file must degrade the envelope, never
     disarm it.

**The guard's timeout is registered here.** The hook entry must carry an explicit timeout value —
this is the mitigation for the reproduced 180-240 second hang, and `<specifics>` names it the
single biggest self-inflicted-wound risk in the phase. Choose a value in the low seconds, name it
as a constant with the reasoning beside it, and assert it in a test rather than trusting the
literal.

Also register the write-and-edit deny for the driven repository's `.claude/**`: `--setting-sources

agent-writable, so the envelope denies writing it rather than relying on it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| driven agent → `PreToolUse` guard | The agent supplies an arbitrary shell command string the guard must classify before it runs |
| guard → ledger file | An append-only file on disk decides whether a tool call is permitted |
| envelope → settings file → agent CLI | A generated JSON file is the only carrier of the guard registration, and the consumer silently ignores it when invalid |
| driven repository `.claude/**` → agent CLI | Project-tier settings in the driven repository are loaded by the child and are agent-writable |
