## The design question, answered

**The guard must stop asking "does this assignment spell `core.hooksPath`" and start asking "can I
establish what `core.hooksPath` will be."** An assignment the guard can BOUND to the key it names
leaves `core.hooksPath` exactly as the envelope injected it. An assignment that adds an indirection —
a file spliced in at the precedence of the directive that named it — leaves it unknowable from argv.
The second is **unresolvable**, and an unresolvable command is refused rather than guessed at.

**Four options, three rejected on measured grounds.**

**(i) Add `include.path` to `is_hooks_path_key`** — REJECTED. `includeIf.<arbitrary condition>.path` is
an open family, so the list is wrong the moment a condition type is used, and it would attribute the
refusal to `HookBypassBlocked` on a line where the guard has established no hooks-path write — D-24's
own prohibition, and the defect `19-21`'s executor reported as a blocker rather than working around.

**(ii) Read the included file and resolve the config at guard time** — REJECTED on three independent
measured grounds: the guard runs synchronously on the `PreToolUse` critical path where a reproduced
180–240 second hang is why `push_needs_resolved_dests` exists; the file may not exist at guard time or
may change between guard and exec; and `includeIf`'s conditions depend on the repository the command
will run in, which a pure argv function does not know.

**(iii) Refuse every `-c`** — REJECTED and pinned red. `git -c user.name="$NAME" commit -m x`,
`git -c core.pager=cat log` and `git -c a=b status` are measured PERMITTED and `19-22` pinned them; a
control that refuses ordinary configuration fails into unusability and gets switched off (AR-19-11).

**(iv) ADOPTED — read the SECTION, and read nothing else.** git's config graph is spliced from
elsewhere by exactly one mechanism, and that mechanism is identified by the section half of the key.
Reading the section and deliberately reading neither the subsection nor the variable covers **both**
open families by construction.

## And the honest part, which the doc must state in these terms

**This is not a fifth inversion.** Rounds 3, 5, 6 and 7 each made the guard's silence a refusal.
**This rule cannot**, because the complement is unbounded: a fail-closed default over config keys would
have to enumerate every section a user may legitimately set. What is available instead is a **closed
grammatical fact** about git's config graph, and the residue that leaves is exactly one thing:

> **A future git that adds a THIRD indirection section is not covered, this rule fails OPEN on it, and
> there is NO automated control over that direction.**

That whole sentence goes in the rule's own doc and in the record, **including its second half**.

**The residue must not be handed to the pin, and this is the correction the plan-check caught.** The
pin holds the REVERSE direction: it turns red if the installed git stops honouring a section the
constant already names. **It cannot observe a section it does not name** — a probe iterates the entries,
and an entry that does not exist is not probed. A third indirection section would therefore reach
`core.hooksPath` silently until a human adds it, and only a human reading a future git's release notes
closes that gap.

Writing *"the only control over that direction is the pin"* would be honest about the residual and then
hand it to a control that does not cover it — **`T-19-107`'s own failure mode, false reassurance in a
control's doc, committed by the round that registers `T-19-107`.** State the absence plainly instead.

## Case-insensitivity, answered explicitly

**Yes, and it is required, and it changes no existing pin.** Measured against `git version 2.43.0` with
the envelope's own injection as the control: `-c INCLUDE.PATH=<file>` and
