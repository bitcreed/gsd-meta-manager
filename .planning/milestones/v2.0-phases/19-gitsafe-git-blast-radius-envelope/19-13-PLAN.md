**`T-19-60` narrowed but not closed, plus the second blocking threat the re-audit found.**

Round 1 (plans 19-11 and 19-12) replaced `words[0]` with a structural resolver and closed all six
originally measured lines. Audit 2 re-measured against the built binary and found the mechanism
survives one level up (`19-SECURITY.md`, commit `0dcc6da`):

```
exit=2  env -u SOME_VAR git push --force origin main                        <- the discriminator
exit=0  env -u git git push --force origin main                             <- FORCE PUSH PERMITTED
exit=0  env -u git git -c core.hooksPath=/dev/null push --force origin main <- ALL THREE LAYERS CLEARED
exit=0  env -u gh gh pr create --title x                                    <- PR CAP BYPASSED, no ledger
exit=0  K=GIT_SSH_COMMAND; SSH_AUTH_SOCK=/tmp/evil env -u $K git fetch origin  <- T-19-81
```

`resolve_program` step 5 returns `Governed { index }` for the first token whose basename is
governed **without establishing that the token is in a command position**, so a wrapper's own
option operand captures the index and the real program becomes `argv[0]` of the classified argv —
where `classify_git` reads it as the verb, finds `git` absent from the denylist, and answers
`Allow`. Row 3 is strictly worse than the original `T-19-60`, whose D-09 note at least recorded
that the escape cost the agent its token: here `GIT_ASKPASS`, `GIT_CONFIG_GLOBAL/SYSTEM` and
`GIT_SSH_COMMAND` all survive and the push authenticates. Row 5 is independent — it removes the
`GIT_SSH_COMMAND` braces and restores `SSH_AUTH_SOCK` in one tool call, putting the user's own
ssh-agent back inside a driven run, which is what D-16 and `T-19-23` exist to prevent.

The diagnosis is settled; do not re-derive it.

**What this round closes, stated at the width the corpus can establish.** It closes the
**wrapper-operand** sub-class: a token that is not the effective program captures the resolver's
index because it is spelled `git`/`gh`/`glab` in a WRAPPER's operand slot. It does **not** close
the adjacent member found while planning this round — a GOVERNED program's own operand naming a
governed command:

```

exit=0  git rebase -x "git push --force origin main" HEAD~3
exit=0  git bisect run sh -c "git push --force origin main"
exit=0  git -c alias.p='!git push --force origin main' p
```

These resolve at the head — correctly, because the head IS the command position — and are then
permitted by `classify_git`'s denylist default arm, before this plan and after it. That shape is
named nowhere in the phase today. It is registered here as **`T-19-86`**, pinned at its current

refuses an argv whose verb is itself `git`/`gh`/`glab` — closes rows 2 and 3 and nothing else. It
does not reach row 4 at all, because a forge command is decided by `pr_command_label` returning

has spent three rounds refusing to encode. So it is refused rather than guessed at. The named fix
stays as a second, independent layer with its own unit pin.
