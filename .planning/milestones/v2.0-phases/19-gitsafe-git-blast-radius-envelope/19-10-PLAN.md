<objective>
**Gap G-19-4. A test harness whose failure mode points at the wrong thing.**

`tests/driver_lock.rs::the_lock_is_released_when_the_holding_process_dies` failed once, on
2026-08-18, with `the child driver never took the lock within 30s`. The user chose `fix` over
`accept` and `defer` after being shown that the item's original framing no longer holds.

**This is not product flakiness and not acceptable noise.** The root cause is established and must
not be re-diagnosed:

- All five tests in the file share `ALIAS = "locked"` (driver_lock.rs:56) and one process-wide
  envelope root (driver_lock.rs:90-97), so they all write `<root>/locked/settings.json`.
- `write_settings_in` persists and then re-reads that path to verify (hooks.rs:1340-1341), and the
  compared value embeds `std::env::current_exe()` via `guard_command` (hooks.rs:1281).
- The four siblings drive in-process, so their `current_exe()` is the TEST binary. This test's
  holder is the REAL binary. They write **different** JSON to one path.
- A sibling's atomic rename landing between the child's persist and its verify fails the child with
  `EnvelopeAssertionFailed`, and it exits **before** `lock::acquire`.
- Its stdout and stderr are null'd (driver_lock.rs:410-411), so the only visible symptom is the
  30-second timeout. A microsecond window, hence one-off; a misleading symptom, hence worth fixing.

The refuted hypothesis, recorded so it is not revived: `establish_envelope()` does precede
`lock::acquire` (run.rs:2493 before run.rs:2609), but slowness is **not** the cause — 100
reproduction attempts under load to load average 55 produced 0 failures, worst wall time 1.09s
against a 30s deadline.

Purpose: close the race at its source in the harness, and make the harness say what actually
happened when a child dies early — the second of which has value even if the race never recurs.
Output: `tests/driver_lock.rs` with per-test aliases, a surfaced child failure, and two controls.
</objective>
