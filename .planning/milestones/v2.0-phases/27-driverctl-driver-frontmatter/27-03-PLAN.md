<objective>
Define frontmatter schema v1 as one typed module that both reads and writes it: `DriverFrontmatter`
with its parse (DCTL-03, D-15, D-24) and its hand-written emitter, the 8-value `RunStatus` with
`stalled` (D-05), the closed `ItemState` and inline `item_states` (D-19), and the golden plus spike
fixtures that prove every generated state round-trips (D-16).

Purpose: "format-correct by construction" — the store (27-05) will build a `DriverFrontmatter` value
and call `emit()`, and Phase 30 parses the same type; one type for both halves means the writer cannot
emit what the reader cannot read.

`tests/driverctl_frontmatter.rs`, 18 spike fixture copies and 7 golden files.

Placement `[inferred — audit]`: the emitter is `DriverFrontmatter::emit` in the same state_reader
module rather than a separate `src/driverctl/frontmatter.rs` (27-RESEARCH's suggested layout). It is
a pure `&self -> String` with no I/O, it keeps the schema-evolution rule in one module doc (D-19), and
it lets this plan run in parallel with 27-02, which owns `src/driverctl/mod.rs` in wave 1. The
liveness-derived status (D-22) is added to this file by 27-04, which needs 27-01's `probe_at`.
