<objective>
Restructure the TUI event loop so control keys stay responsive while a run streams (D-17),
and prove it with deterministic tests rather than an assertion (TRANS-03).

Purpose: The committed architecture pass is right that the existing event bus already
multiplexes upstream, so adding a fourth producer is mechanically additive. The pitfalls pass
is also right that the restructure is still mandatory — for three reasons that are about
PRIORITY and PROGRESS rather than multiplexing: a single unbounded FIFO gives control keys no
priority over bulk stream traffic; the loop has no timer arm of its own and can only make
progress when a message arrives; and the blocking editor shell-out runs on the render thread.
That disagreement is resolved in writing by D-17, and this plan implements its conclusion.

Output: a `pump` function in the library where it can actually be tested, a biased
`tokio::select!` with a bounded batch drain, sibling driver state on AppContext, and three
deterministic tests that fail loudly if the priority ordering is ever removed.
</objective>

    Move the loop body somewhere testable, then give it priority and a timer.

    Create `src/main_loop.rs` and register it in `src/lib.rs`'s alphabetical module list. The
    loop body CANNOT stay in `src/main.rs` — that file is the binary, not the library, so a
    test targeting the library cannot reach anything defined there, and all three TRANS-03
    tests in Task 2 would be unreachable. This is a placement decision to make now rather than
    discover at test time.

    In `src/main_loop.rs` define `EXEC_BATCH` (start at 64), `PumpOutcome`, and
    `pub async fn pump(app, action_rx, exec_rx, batch) -> PumpOutcome`. Its body is a
    `tokio::select!` with `biased;` — arm order IS the priority order (D-17):

    1. The Action receiver first. Input and existing actions win every iteration, so a control
       key can never queue behind bulk stream traffic. That is exactly the failure TRANS-03
       forbids. Add a comment at this arm recording the flip side: because the arm is biased
       first, routing anything high-volume through the Action FIFO in a future phase would
       starve the other arms — D-17's rule that per-token stream output must not go through
       that FIFO is load-bearing, not stylistic.
    2. The executor receiver second, drained in a BOUNDED batch: handle the received event,
       then take up to `batch` minus one more with non-blocking receives, stopping at the first
       empty or closed result. The bound is what stops a burst starving a redraw.
    3. The loop's own redraw interval third — a 16ms tick with a delaying missed-tick
       behaviour. This is what lets the loop make progress with no message at all; today it is
       rescued only by the incidental 250ms tick.

    Guard the self-disabling arm (Pitfall C, the most likely concrete bug here). When a channel
    closes, its receive returns nothing, the arm's pattern fails, and `select!` disables that
    arm for good; if every arm disables, `select!` panics. The executor channel legitimately has
    no producer between runs, so do BOTH: create it ONCE for the process lifetime and stash a
    long-lived sender clone on the app context so it never closes, AND add an else branch so
    the panic is impossible even if that clone is ever dropped.

    In `src/main.rs`, `run_tui_loop` becomes: the existing redraw-flag sync and draw, then
    `pump`, then the editor block, then the quit check. Take the executor receiver as a fourth
    parameter. At startup, beside the existing event-bus wiring, create the bounded executor
    channel with a generous capacity (start at 8192 — backpressure on the reader risks Claude's
    thirty-second exit drain, so the buffer wants headroom), stash the sender clone on the app
    context on the same line as the existing sender, and pass the receiver in.

    The editor block moves VERBATIM (D-18). Preserve the terminal suspend, the two environment
    variables then the fallback binary, the blocking status call, all three match arms writing
    their status message with a timestamp, the terminal re-initialisation, and the redraw
    request. Do not refactor it beyond what taking it out of the receive arm strictly requires.
    It is a known wart, it is not on this phase's critical path, and widening the blast radius
    of an event-loop change is exactly how a foundation phase becomes a regression hunt. Note it
    for a later quick task; do not fix it here.

    Keep the 250ms tick. It drives the twenty-tick session poll and the three-second
    status-message expiry; the new 16ms redraw interval is a separate concern and additive.
    Removing the tick would silently break session detection.

    In `src/ui/screens/mod.rs`, add two sibling fields to `AppContext`, shaped exactly like the
    existing per-alias maps: a bounded executor sender held as an option beside the existing
    sender, and a per-alias map of driver run state. Driver state must NOT go on `ProjectState`
    (D-19): that type derives the equality `app.rs` uses to suppress the updated-alias status
    message, and driver state changes every few seconds — the spike emitted 22 thinking-token
    events in 68 seconds — so putting it there would flood the status bar for an entire
    multi-hour run. `App::new` constructs the app context with an exhaustive literal and no
    default fill, so both new fields need a line there.

    In `src/app.rs`, add `apply_exec_event`, which updates the per-alias run state and sets the
    redraw flag, and `App::new_for_test`, a constructor next to `App::new` that skips loading
    the config from disk and starts from an empty config. The test constructor is what makes
    Task 2's tests possible without a config file.

    No process handle, child stdin, or task join handle may be placed in an `Action` (D-19).
    `Action` derives `Clone` and those types do not, so the build itself is the gate — leave
    the derive in place and route all stream traffic through the separate channel.

    Add no widget, no screen, and no layout. This phase ships no UI; every rendered driver
    surface is Phase 18's.

    Put `#[cfg(test)] mod tests` last in every file touched.

  <behavior>
    Three properties, in the order of how much they prove. The first is the actual TRANS-03
    requirement and it is a PRIORITY property, not a timing one — which is what makes it
    deterministic.

    - `keypress_is_handled_before_a_flood_of_executor_events`: flood the executor channel with
      ten thousand events FIRST, then enqueue exactly one quit keypress on the Action channel,
      then run ONE `pump` iteration. Assert the app is quitting. A naive FIFO drains the flood
      first and this fails; removing the bias or merging the executor channel into the Action
      FIFO also fails it. The assertion message reports how many events remained queued, so a
      failure says how badly the key was starved. (D-17)
    - `executor_burst_is_drained_in_bounded_batches`: seed ten thousand events and no actions,
      run ONE `pump` iteration with a batch of 64, and assert the receiver still holds ten
      thousand minus 64 — control returned to the loop head instead of draining everything.
      (D-17)
    - `tui_renders_repeatedly_while_the_executor_channel_is_saturated`: build a terminal over
      the existing test backend, spawn a task that floods the executor channel continuously for
      about two seconds, run the real loop, and count draw invocations. Assert comfortably more
      than twenty frames. Timing-flavoured but robust with a generous bound — it fails only if
      redraws stop entirely, which is the actual failure mode the criterion names.

    Deliberately NOT written: any wall-clock keypress-latency percentile assertion. It passes on
    a developer laptop, fails on a loaded runner, gets ignored within a month, and at that point
    the criterion has no verification at all. If a latency number is ever wanted it belongs in an
    explicitly ignored benchmark documented in the testing guide, never in a gate.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| executor channel → render loop | High-volume events from a subprocess reach the thread that owns the terminal |
| AppContext → status bar | Driver state changing every few seconds could reach a surface built to report rare changes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-25 | Denial of service | control keys starved behind bulk stream traffic | high | mitigate | D-17's biased select with the Action arm first, proven by a deterministic test that fails the instant the bias is removed or the channels are merged. |
| T-15-26 | Denial of service | an unbounded executor channel growing without limit while the blocking editor holds the loop | high | mitigate | The executor channel is bounded rather than unbounded, so a blocked render loop applies backpressure to the reader task instead of consuming memory; the capacity is generous because backpressure on the reader risks Claude's thirty-second exit drain. |
| T-15-27 | Denial of service | `select!` panicking when every arm has disabled itself | high | mitigate | Pitfall C: the executor channel is created once for the process lifetime with a long-lived sender clone stashed on the app context, AND an else branch makes the panic impossible even if that clone is dropped. |
| T-15-28 | Repudiation | executor events silently dropped when the channel is full | medium | mitigate | The prohibition above forbids a silent drop; the reader applies backpressure or emits an explicit dropped-events signal so the user's view of a run is never quietly incomplete. |
| T-15-29 | Denial of service | the blocking editor shell-out on the render thread | low | accept | D-18 explicitly accepts this wart for this phase: it is off the critical path, and widening the blast radius of an event-loop change is how a foundation phase turns into a regression hunt. Noted for a later quick task; the bounded channel makes the blocking window safe. |
