## The `proptest` decision, argued rather than reflexed (D-21-72)

This project has a standing no-new-dependency reflex, and it also has a counter-precedent: `Cargo.toml`
carries `icu_properties` + `unicode-properties` added for *precisely* this failure mode, with the
comment *"Six consecutive rounds 'fixed' that by hand-enumerating the next level down, so this add
replaces the enumeration with a query against Unicode's own reference data"*. Weighing `proptest`
honestly against that precedent:

1. **The precedent does not extend.** `icu_properties` supplies Unicode's own REFERENCE DATA — an
   external ground truth this project cannot derive. `proptest` supplies a SEARCH STRATEGY. There is no
   external ground truth for "the set of session-id classes"; that set does not exist anywhere to be
   queried. The thing that made the Unicode add correct is exactly the thing absent here.
2. **`proptest` would not have found G1 either.** Its default `Vec<u8>`/`String` strategies are
   effectively uniform, and uniform bytes essentially never produce `" abc "`. The mixture grammar that
   reaches the padded class has to be written by hand in BOTH worlds. The dependency buys shrinking and
   case-count plumbing — not the class coverage that is the actual ask.
3. **Seed reproducibility in CI favours the hand-rolled generator.** A fixed seed reproduces
   byte-identically on every run, forever, with nothing committed. `proptest` is random-by-default; its
   reproducibility mechanism is a `proptest-regressions/*.txt` artifact written *after* a failure has
   been seen, which is reproducibility of past failures rather than determinism of the gate. For a gate
   whose whole value is that its green can be trusted, non-determinism is a cost, not a feature.
4. **Shrinking quality, honestly.** This is `proptest`'s real advantage and it is given up. It is
   mitigated, not dismissed: generated inputs are bounded at 12 bytes and the failure message prints the
   input as an explicit byte vector plus its escaped rendering, so a counterexample is already minimal
   enough to read without a shrinker.
5. **Graph cost, MEASURED (not borrowed from another manifest entry's sentence).** In a scratch copy of
   this project's own `Cargo.toml` and `Cargo.lock`, `cargo add --dev proptest` reported *"Locking 14
   packages to latest compatible versions"* and took the lockfile from **354 to 368** `name =` entries.
   All fourteen are new — none was already present: proptest 1.11.0, bit-set 0.8.0, bit-vec 0.8.0,
   ppv-lite86 0.2.21, quick-error 1.2.3, rand 0.9.5, rand_chacha 0.9.0, rand_core 0.9.5,
   rand_xorshift 0.4.0, rusty-fork 0.3.1, unarray 0.1.4, wait-timeout 0.2.1, zerocopy 0.8.56,
   zerocopy-derive 0.8.56. One is a proc macro, and `rusty-fork` + `wait-timeout` exist for
   default-enabled fork/timeout behaviour this project does not want in its test binaries.

**Decision: hand-rolled, seeded, with a committed non-vacuity floor.** The floor is what makes this
answer legitimate rather than a dependency-avoidance rationalisation: it is the same device
`unicode-properties`' `format_seen >= 150` sweep already uses, and it is what stops a generator from
silently degrading into a shorter enumeration.

**What is honestly NOT claimed.** A generator does not abolish enumeration — it moves the enumeration
from VALUES to a GRAMMAR and a DISTRIBUTION, and a grammar can still miss a class. What it removes is
the ability of the claim to pass with no input anywhere near the boundary, and the uniform-bytes arm
plus the ≥200-distinct-byte-values floor is what reaches classes nobody named. That sentence belongs in
the source, beside the generator, not only here.
