<objective>
Make the opt-in's re-confirmation promise true: a digest an adversary cannot forge, a disclosure
list that names exactly the files whose bytes reach a prompt, and a drift check at the gate rather
than at render time.

Purpose: `DriverOptIn::claude_md_digest` was recorded by Phase 17 for exactly this phase, and its
own documentation says the function behind it is not a security control. This phase's threat model
is explicitly adversarial — the tool drives other people's cloned repositories, whose `CLAUDE.md`
can change under a `git pull` the user did not read. A re-confirmation prompt is a security
affordance, and backing one with a non-security hash is what this codebase's honesty conventions
exist to prevent.

Output: `sha2` as a verified dependency, a `sha256_digest` sibling in `src/journal/mod.rs`, a
`prompt_inputs` list on `DriverOptIn`, a disclosure surface on the confirmation screen that
distinguishes the two spawn profiles, and a drift check at the gate.
</objective>

  </read_first>
  <context>
`DriverOptIn` lives in `config.json`, a user-owned file that older binaries load, re-save, and
must not corrupt. `src/config.rs:73-76` records that the record was made a struct rather than a
bool specifically so that adding the digest later would not be a second migration of a user-owned
file — which means the shape chosen here is the shape every future binary inherits. Changing it
after users have opted projects in is a migration of a file this tool does not own, and there is
no upgrade path that reaches a user who never runs the new version. That is a one-way door, and
it is the only one this phase contains.

The recommended option is (A). It keeps every existing key readable, adds nothing that an older
binary would drop (`RegisteredProject::extra`'s flatten preserves unknown fields), and puts the
disclosure list and the drift check behind one source of truth.
  </context>
  <options>
    <option id="option-a">
      <name>Keep `claude_md_digest` as a legacy key; add `prompt_inputs: Vec<PromptInput>` where each entry is a path relative to the project root plus a prefixed digest string</name>
      <pros>Old configs load unchanged with no migration. The prefix convention (`fnv1a64:` versus `sha256:`) already exists, so a legacy value is self-describing rather than ambiguous. One list feeds both the disclosure surface and the drift check. `#[serde(default)]` makes the addition non-breaking, matching every field on `DriverOptIn` after the first.</pros>
      <cons>Two keys describe overlapping facts for one release cycle; a reader must know `claude_md_digest` is legacy. The `PromptInput` entry shape is itself the thing that becomes hard to change later.</cons>
    </option>
    <option id="option-b">
      <name>Replace `claude_md_digest` outright with `prompt_inputs`, migrating on first load</name>
      <pros>One key, no ambiguity, no legacy reader.</pros>
      <cons>A migration of a user-owned file — precisely what `src/config.rs:73-76` says the record shape exists to avoid. An older binary that loads and re-saves would see an unknown key it cannot interpret, and a user who downgrades loses the opt-in's digest entirely.</cons>
    </option>
    <option id="option-c">
      <name>Keep `claude_md_digest` only, upgrade it to `sha256:` in place, and derive the disclosure list at render time from a hardcoded set</name>
      <pros>Smallest diff; no new key at all.</pros>
      <cons>The disclosure list and the drift check would then come from two places that can disagree, and a set derived at render time cannot record what was actually disclosed at approval time — which is exactly the replay hazard research Q4 names.</cons>
    </option>
  </options>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party repository file → recorded digest | `CLAUDE.md` in a cloned repo can change under a `git pull` between opt-in and spawn |
| `config.json` on disk → this binary | the file is user-owned, written by other versions of this tool, and read across binary versions |
| confirmation screen render → spawn gate | time passes between what the user read and what the run uses |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-21-17 | Tampering | the disclosed file changing between render and spawn | high | mitigate | the drift check moves to the gate where the opt-in is consulted before a spawn; the gate test is written to fail against a render-time-only check |
