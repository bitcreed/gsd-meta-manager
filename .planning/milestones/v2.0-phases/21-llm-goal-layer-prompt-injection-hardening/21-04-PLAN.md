<objective>
Wire the two seams into the run: one decomposition before the loop, one ambiguity escalation
inside it, and nothing else — with the never-self-goal prohibition enforced by the compiler rather
than by a comment.

Purpose: this is where the phase becomes a capability. Phase 20's loop already pursues a target
phase across commands; this plan gives that loop a goal a human stated in plain language, an
approval that covers the bytes that will actually enter the prompt, and a bounded consultation at
the one state the rules do not cover. It is also where the two most decay-prone properties live:
"we only call the decomposition before the loop" is control flow, not a mechanism, and an approval
that is not bound to its inputs is replayable.

Output: the decomposition capability and its single moved call site, the ambiguity seam at the
router's no-rule branch, the approved plan and the escalation counters on the run record, and the
source-scanning guards that keep the seam count at two.
</objective>

  <action>
Replace the `NoRule` arm's immediate park with a bounded consultation, and keep every other arm
byte-identical — the router stays authoritative for every state it covers, and the model never
overrides a rule.

The arm's order of operations is the whole design, and it must read in exactly this order.
First, ask the escalation budget for permission. If the budget refuses, park with the cap-reached
reason from plan 21-02's taxonomy — a park, not a halt, and not a silent degrade to rules-only,
because a run that stopped consulting the model has materially changed behaviour and must say so.
Second, spawn the seam profile with the schema from `goal.rs`, handing it the `observed` value the
arm already carries and nothing else. This is the input restriction that keeps the seam narrow
enough to reason about: feeding it file excerpts would reopen the untrusted-content problem at the
one place the model has influence over the running loop. Third, take the structured payload off
the terminal result envelope and re-parse the named command through `goal.rs`'s `RouterAction`
re-parse. A named action outside the alphabet parks with the action-refused reason and the named
string recorded verbatim on the park's detail, bounded and control-character-stripped — so an
injection attempt becomes evidence on disk rather than a silent no-op, because a silently dropped
injection teaches nobody that the repository is hostile. An absent payload, a malformed payload,
or the CLI's structured-output retry exhaustion parks with the output-unusable reason. A refusal
is never a retry with a stricter prompt: retrying a model that just produced an invalid action is
how a bounded seam becomes an unbounded one, and the CLI already retries internally, which plan
21-01 pinned. Fourth, on success, the validated `RouterAction` plus the phase the router was
already driving toward produce the next command through `RouterAction::verb`, which is the one
path from an action to a string. No shell string is constructed from model output at any point,
including for logging and for the dry-run preview.

There is deliberately no third seam. An error the deterministic rules cannot classify is a park,
not a prompt — do not add a recovery consultation, and do not widen the arm set this seam fires
under beyond the router's no-rule signal.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| human goal text → the run | the one trusted input; everything downstream of it is validated |
| model decomposition output → the run's plan | attacker-influenced through whatever third-party strings the seam was shown |
| model escalation output → the next command | the one point where a model influences the running loop |
| run record on disk → the spawn gate | time and other processes pass between approval and spawn |
| artifacts the run itself writes → the run's own goal | the self-referential loop that would remove every bound |
