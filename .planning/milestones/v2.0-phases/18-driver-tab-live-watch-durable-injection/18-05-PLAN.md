Wire the controller: close WR-15, open the seam the codebase has been holding for this phase, and add
the three `spawn_blocking` schedulers the Driver surface needs.

Purpose: `src/app.rs:693-704` is literally this phase's seam and says so — the

together."* This plan is what adds them. Leaving that comment above code that now does add the
surface is exactly the drift this codebase's comment discipline exists to prevent, so the comment is
rewritten, not merely tolerated.

contradiction visible** — a "no run" pane sitting next to a status line saying the signal failed.
And D-21's gating matters more than it looks: an unconditional per-tick redraw makes an idle fleet
dashboard burn CPU forever, which is the exact opposite of this tool's pitch.

Output: the WR-15 fix, three schedulers, goal threading, `DetailSubView::Driver`, the rewritten
seam, the gated tick, and the extended prune.

Add the three schedulers, thread the goal, and register the sub-view.

**`schedule_inbox_append`.** On `Action::DriverInjectRequested`, resolve the run's inbox path through
the fallible `run_paths`, move the owned `id` and `text` into a `spawn_blocking` closure that calls
`journal::inbox::append`, and send `Action::DriverInjectWritten { alias, run_id, id, error }` back on
a cloned sender. **The key handler never touches the filesystem** — blocking the render thread on a
`sync_data()` is the WR-10 failure mode where the symptom is a frozen frame, not an error (D-06,
D-28). In the `DriverInjectWritten` handler, set the success status message on `error: None` and the
error message on `Some(err)`; the exact strings are pinned by the Copywriting Contract, and the
failure copy must state that **nothing was written**. Do not mark the message `queued` anywhere
before the write returns `Ok`.

**`schedule_run_list_scan`.** Calls `journal::list_runs` **and** `journal::inbox::tail` for the
selected run on `spawn_blocking`, returning `Action::DriverRunsListed { alias, runs, inbox }`. The
handler stores both on the alias's `ProjectViewCache` and sets `needs_redraw`. This is one of this
phase's own new blocking paths — wrapping only the calls the review listed while leaving the new ones
on the render thread is the named half-fix (D-28).

**`schedule_dry_run_report`.** Calls `dry_run::build_report` + `render` on `spawn_blocking`,
returning `Action::DriverDryRunLoaded`. Until it resolves the UI shows the shipped `Loading...`
idiom; the handler just stores the string.

**The goal.** In the `DriverStartRequested` handler, pass the variant's `goal` through to
`start_driver_run` instead of `None`, and rewrite the comment that explains the `None`. **An empty
goal maps to `None`, never `Some("")`** — `drive_argv` omits the flag entirely for `None` and would
otherwise record an empty goal verbatim, which is a different and worse thing than no goal. Keep the
existing reasoning in the doc and extend it rather than deleting it.

**`DetailSubView::Driver`.** Add the variant and the two arms `tab_index` and `sub_view_from_index`
need to compile (`Driver => 10`, `10 => Driver`, keeping the existing fallback). Rendering, the tab
title vector and the footer are 18-09's; this task adds only what the compiler demands, and says so
in a comment so the next reader does not think the tab is half-wired by accident.

All three schedulers follow the shipped guard shape — a `let … else { return; }` on `event_tx`, a
cloned sender, owned data moved in — and each carries the searchable marker phrase this file already
uses for the boundary plus a `D-28` citation. Refusals are visible, never silent: the "no live run"
and "no registered project" cases set `error_message` and `needs_redraw` and send nothing, following
`app.rs:906-910`.

Inline tests: a dispatch with no `event_tx` sets an error and sends nothing; `DriverInjectWritten`
with `Some(err)` sets `error_message` and not `status_message`; an empty goal reaches
`start_driver_run` as `None`; `DriverRunsListed` populates the cache and sets `needs_redraw`.
