<objective>
Stop shipping a remote-code-execution-shaped flag in the released binary, and make a stand-in run
identifiable on disk when the flag is legitimately used.

Purpose: `--claude-program` lets any caller of the *released* binary make the driver exec an
arbitrary program in an opted-in project root, while the journal records the result as a normal GSD
run — `run_started`, `exec_started`, `run_ended`, `outcome` — with nothing distinguishing it. The
review's own words: `hide = true` removes it from `--help`, not from the parser, and the rationale
given (an env var would be inherited by children) argues correctly against an env var but does not
argue for shipping the flag in release. The spawn seam is guarded against *emitting* the flag;
nothing guards against a human or a script passing it.

D-30 requires **both** remedies rather than a choice between them, because each covers the other's
gap: the cfg gate removes the release surface entirely, and the journaled diagnostic closes the
ambiguity that remains in a debug build, where the flag must keep working for the nine fake-`claude`
fixtures.

Output: the cfg gate, the diagnostic, the mechanical guard, and the accepted consequence written down
where the next reader will find it.
</objective>

build the integration tests that pass these flags; the project gate is
`cargo build && cargo test && cargo clippy -- -D warnings` and does not run release tests; the nine

a flag shaped like remote code execution in the released binary in order to keep a release-mode test
path is the wrong trade. Write it as a decision that was made, not as a limitation that was
discovered.

`Diagnostic { code: AGENT_PROGRAM_OVERRIDDEN, detail }` from `src/driver/run.rs`, following the

discipline this codebase applies to every driver log line. The emission itself is
`#[cfg(debug_assertions)]` too, because in release there is nothing to mark.

Do not touch `drive_argv`: the TUI's own spawn argv never emits these flags and that must stay true;
