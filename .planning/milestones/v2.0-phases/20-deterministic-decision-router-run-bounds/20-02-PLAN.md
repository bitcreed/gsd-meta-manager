<objective>
Make the durable record honest now that a run is a sequence rather than a command.

The assumption-delta detector fired on exactly this: the driver's unit of work changed from
singular to plural. Before this phase a run IS one command — `DriveArgs::command` is a `String`,
`run.json` carries one `session_id` and one `gsd_command`, and five separate source sites state in
prose that the driver owns no sequence. Plan 20-01 made all of that false. This plan decides, field
by field, which singular things stay run-scoped and which became iteration-scoped, records the
bounds in force so a reader is never left inferring them from the binary's defaults, and repairs
every pinned or now-false statement in the same commit as the code that falsified it (D-25).

Purpose: `run.json` and `journal.jsonl` are read by a separate process — Phase 19 proved that —
and they are the only evidence a finished run leaves. A field whose meaning silently changed is a
record that lies quietly.
Output: a per-field scope classification on `RunRecord`, the caps in force on disk, a widened
park-reason taxonomy doc, honest preview text with its paired test moved, and an async-blocking
lint that can see the per-iteration snapshot capture.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>What `RunRecord.gsd_command` means once a run issues a sequence, and how a routed run's identity is carried on `run.json`</decision>
  <context>
`run.json` is written exactly twice — once at start, once at finish — and `gsd_command` is set on
the first write, before any routing has happened. Under 20-01's loop a routed run has no single
command at start. Whatever this field is made to mean is baked into every run record already on
disk and into every record written from here on, and the TUI's render layer reads it. There is no
version discriminator on the file, so a later change of meaning silently reinterprets history
rather than converting it.

Research settled the session half — one fresh session per iteration, with per-iteration ids riding
the `Decided` and `ExecStarted` events, which already carry `session_id` — and that resolution is
not in question here. What is in question is the command half.
  </context>
  <options>
    <option id="option-a">
      <name>Sentinel plus a typed sibling: `gsd_command` records a routed-mode marker and a new `target_phase` field carries the routed run's identity</name>
      <pros>The field never names a command the run did not choose. A reader who sees the marker knows immediately to read the `Decided` events for the actual sequence. `target_phase` is the routed run's real identity and belongs on the record.</pros>
      <cons>Introduces a value existing readers do not expect in a field whose type says command; the render layer needs an arm for it.</cons>
    </option>
    <option id="option-b">
      <name>Record the goal: `gsd_command` carries the routed goal text in routed mode, unchanged in command mode</name>
      <pros>The field stays a human-readable string at every existing reader with no new arm and no schema addition.</pros>
      <cons>The field's name says command and its content would not be one. That is the exact class of quiet lie this plan exists to remove.</cons>
    </option>
    <option id="option-c">
      <name>Empty in routed mode: `gsd_command` is written empty, `target_phase` carries identity, and the emptiness is documented as "read the Decided events"</name>
      <pros>No sentinel vocabulary to invent or keep in sync; an empty command cannot be mistaken for a command that ran.</pros>
      <cons>An empty string is a weaker signal than a named marker; a reader who does not consult the doc may read it as a missing value rather than a deliberate one.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| driver process → `.planning/meta-manager/runs/<id>/` → TUI process | `run.json` and `journal.jsonl` are written by one process and read by another, and land in a directory users commit. |
| older binary ↔ newer binary over the same `run.json` | Records are read and re-saved across binary versions; a strict parse or a dropped unknown field is a data loss. |
| driven agent → journal records | Anything the loop records that originates in agent output would be disclosed into a committed directory. |
