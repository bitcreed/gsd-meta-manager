## Spacing Scale

Terminal cell units (1 cell = 1 character width or height). All spacing in whole cells.
Inherited verbatim from Phase 11.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 1 cell | Inline padding between icon and text (e.g. `⏸ ` badge → alias) |
| sm | 2 cells | Column gaps in dashboard table; D-R-P-E-V inter-stage gap; panel left indent |
| md | 3 cells | Section padding within detail view; tab bar height (3 rows) |
| lg | 4 cells | Layout margins (detail view sides) |

Exception: Terminal cell units use a base-1 character grid. Standard base-4 pixel constraints
do not apply. Values xs=1, sm=2, md=3, lg=4 are the minimum practical increments for a
monospace cell layout and match the existing ratatui layout patterns in this codebase.

### Spacing changes in this phase

Exactly one, and it is a defect fix, not a design change:

| Surface | Before | After | Why |
|---------|--------|-------|-----|
| Dashboard Status column, D-R-P-E-V cell | `` ` D  R  P  E  V ` `` (leading 1 + trailing 1) | `` `D  R  P  E  V` `` | UIFIX-02 — leading pad cell misaligns the column against sibling values (`executing`, `verifying`, `v1.0 Complete`) |

The inter-stage gap stays at **sm (2 cells)** — the shipped visual rhythm is preserved, the
whole string simply starts at column 0 of its cell. Net width goes 16 → 13 cells.

**Explicitly NOT in scope:** the Pipeline tab's expanded pipeline
(`  [D]---[R]---[P]---[E 2/3]---[V]`, `detail.rs:3343`) has a deliberate **sm (2 cell)** left
indent as panel padding inside a bordered block. That is intentional layout indentation, not a
status-column value. It stays. Do not "fix" it.

## Color

ANSI terminal colors. Follows the status color vocabulary established in
`normal.rs::status_color()`. Inherited verbatim from Phase 11 + Phase 12.
**No color value changes in this phase.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Terminal default bg/fg | All surfaces, backgrounds, body text |
| Secondary (30%) | `Color::DarkGray` | Borders, separators, dim text, not-started D-R-P-E-V stages, code blocks, `Loading...`, line-number gutter |
| Accent (10%) | `Color::Cyan` | See reserved list below |
| Destructive | `Color::Red` | Blocked project rows. **No destructive action exists in this phase.** |

Additional established semantic colors, reused unchanged:

| Color | Meaning |
|-------|---------|
| `Color::Green` | Reached D-R-P-E-V stage; active session `▶` indicator; active project rows |
| `Color::Yellow` | Current (next-up) D-R-P-E-V stage; external-job `⏳` badge; idle project rows |
| `Color::Magenta` | Skipped pipeline stage; unknown-status rows |
| `Color::Blue` | `[DIR] ` prefix in the Browse listing |

**Accent (Cyan) reserved for — exhaustive list:**
- Pause badge glyph `⏸` (U+23F8) prepended to the alias cell on the dashboard
- Pause context line in the detail view status area
- Active tab label in the detail tab bar (Bold + Cyan)
- Selected list item highlight in Browse / Archive listings (Bold + Cyan, `"> "` symbol)
- `# H1` markdown headers in the file viewer
- Summary bar "done" count

Cyan is **never** used for generic interactive affordance. Footer key hints use Bold on
default fg, not Cyan.

### Badge Priority Rule (UIFIX-01)

The dashboard alias cell shows **at most one** leading badge. Priority, highest first:

| Rank | Condition | Badge | Color | Source |
|------|-----------|-------|-------|--------|
| 1 | `state.paused` (non-empty `HANDOFF.md` or `HANDOFF.json`) | `⏸ ` (U+23F8 + space) | Cyan | Phase 11 UI-SPEC + CONTEXT.md |
| 2 | `state.external_job_waiting` (`.planning/async-jobs/*.json` present) | `⏳ ` (U+23F3 + space) | Yellow | quick task 260722-emn |
| 3 | active Claude session for the project path | `▶ ` (U+25B6 + space) | Green | pre-existing |
| 4 | none of the above | *(no badge, alias renders flush)* | default | pre-existing |

This is the **shipped** three-tier rule (`normal.rs:421-441`), which extends Phase 11's
two-tier `pause > session` rule. It is recorded here as the contract, not changed. The
2026-03-27 todo's "badge shown alongside (not replacing) `▶`" is **superseded** — the pause
badge replaces, it does not stack. One badge cell keeps the alias column aligned.

## Interaction Contract

Four independent contracts, one per requirement. Each states the **observable** truth so the
planner can turn it into a `must_have` and the executor can write a regression test.

### UIFIX-01 — Pause badge from HANDOFF (verify-first)

**Status: believed ALREADY SATISFIED.** Ground truth read during this research:
`state_reader/mod.rs:57-99` (`detect_handoff`, both `.json` and `.md`, non-empty check) and
`normal.rs:409-441` (badge priority). This requirement is therefore a **regression-test
landing**, not an implementation. Do not re-implement. If a gap is found, fix only the gap.

| # | State | Dashboard alias cell renders |
|---|-------|------------------------------|
| 1 | `.planning/HANDOFF.md` present, non-empty after trim | `⏸ my-project` — `⏸ ` Cyan |
| 2 | `.planning/HANDOFF.json` present, non-empty after trim | `⏸ my-project` — `⏸ ` Cyan |
| 3 | `HANDOFF.md` present but empty / whitespace-only | *no badge* — `my-project` |
| 4 | No HANDOFF file | *no badge* — `my-project` |
| 5 | Paused **and** active session | `⏸ my-project` — pause wins, `▶` suppressed |
| 6 | Paused **and** async job waiting | `⏸ my-project` — pause wins, `⏳` suppressed |
| 7 | Async job waiting, not paused | `⏳ my-project` — `⏳ ` Yellow |
| 8 | `HANDOFF.json` non-empty but invalid JSON | `⏸ my-project`, no pause context (badge still shows) |

Badge appears identically at all three width tiers (`>=80`, `>=60`, `<60`) — the alias cell is
in every tier's cell vector (`normal.rs:443-460`).

### UIFIX-02 — D-R-P-E-V has no leading blank

**Root cause located:** `normal.rs:74` — `Span::styled(format!(" {} ", label), ...)` pads
*every* stage on both sides, so the assembled cell is `" D  R  P  E  V "`.

**Fix at the source** (per CONTEXT.md): change how `compact_pipeline()` constructs the string,
not by trimming at the call site.

| Property | Contract |
|----------|----------|
| First character | `D` — the rendered cell **must not** begin with whitespace |
| Last character | `V` — no trailing pad cell (dead cells inside a percentage-width column) |
| Inter-stage separator | exactly 2 spaces (**sm**) — unchanged visual rhythm |
| Exact cell content | `D  R  P  E  V` (13 cells) |
| Per-stage color | unchanged: Green if `status >= threshold`, Yellow if `status == prev_status(threshold)`, else DarkGray |
| Span structure | each stage remains its own `Span` so per-letter color survives; separators may be their own unstyled spans |
| Terminal widths | identical at `>=80`, `>=60`, and `<60` — `status_cell` is used by all three tiers, so one construction-site fix covers "any terminal width" |

Alignment truth: after the fix, `D` starts at the same column as the `e` of `executing` and the
`v` of `v1.0 Complete` in the Status column.

### UIFIX-03 — Markdown edit key activates on first press

**Root cause located:** `detail.rs:1602` — the `KeyCode::Char('e')` arm branches on
`Archive`, `Queue`, and `Backlog` only. `DetailSubView::Browse` (the Docs tab, added by quick
task 260512-fe6) has **no branch**, so `e` falls through to the generic `else` at
`detail.rs:1726` and pushes the Enqueue overlay — the editor never opens. This is the
"key-routing / screen-guard problem" CONTEXT.md predicted, not a missing feature: the
`ScreenAction::SuspendAndEdit` → `$EDITOR` machinery already exists and already works on the
Archive and Backlog tabs.

Wire Browse into the **existing** `SuspendAndEdit` path. Do not invent a second editor flow.

| # | Context | `e` press → |
|---|---------|-------------|
| 1 | Browse, `BrowserDepth::View`, file under `.planning/` | `SuspendAndEdit(current file)` — TUI suspends, `$EDITOR` opens **on the first press** |
| 2 | Browse, `BrowserDepth::View`, path contains `/milestones/` | status message `Archived files are read-only` — no editor |
| 3 | Browse, `BrowserDepth::List`, selected entry is a `.md` file | `SuspendAndEdit(that file)` |
| 4 | Browse, `BrowserDepth::List`, selected entry is a directory, or listing is empty | status message `Select a markdown file to edit` |
| 5 | Any other tab | unchanged — Archive / Queue / Backlog / generic-enqueue behavior is untouched |

**Claude's Discretion (auto) — rows 3 and 4.** CONTEXT.md and the todo only require the View
depth. Extending to the List depth is chosen because the Browse footer hint is rendered
per-*tab*, not per-*depth*: an `[e]dit` hint that silently opens the Enqueue overlay at one
depth and the editor at another is exactly the class of defect this phase exists to remove.
It also removes the surprising "file browser opens a queue prompt" behavior. Reviewable and
cheap to drop back to View-only if the user disagrees.

**Read-only guard rationale:** the Browse root is `.planning/`, from which a user can descend
into `.planning/milestones/`. Applying the same `/milestones/` guard the Archive tab uses
(`detail.rs:1632`) keeps archived-milestone immutability true regardless of which tab reached
the file.

**Footer:** the Browse arm of `build_footer` (`detail.rs:3641-3650`) gains `[e]dit  ` —
Bold `[e]`, default `dit`, two trailing spaces — placed after `[Enter]open  ` and before
`[Esc]up  `, matching the Archive arm's ordering (`[Enter]open  [e]dit  `). No other footer
arm changes.

### UIFIX-04 — PageDown clamps to the end of content

**Root cause located:** four unclamped `saturating_add` sites. The render path already
computes the correct bound and clamps *for display* — the **stored** offset keeps growing, so
PageUp is a no-op for several presses.

| Handler site | Line | Current | Render-side bound that already exists |
|--------------|------|---------|---------------------------------------|
| PageDown, Browse/View | `detail.rs:808-810` | `browser_scroll_offset.saturating_add(PAGE_SCROLL_LINES)` | `detail.rs:2944-2945` `total_lines.saturating_sub(visible_height)` |
| PageDown, Archive/FileView | `detail.rs:780-781` | `archive_scroll_offset.saturating_add(PAGE_SCROLL_LINES)` | `detail.rs:2804-2805` (same formula) |
| Down/`j`, Browse/View | `detail.rs:595-596` | `saturating_add(1)` | same as above |
| Down/`j`, Archive/FileView | `detail.rs:555-556` | `saturating_add(1)` | same as above |

**Contract:**

| Property | Requirement |
|----------|-------------|
| Bound | `max_scroll = total_lines.saturating_sub(visible_height)` — the **same** formula the renderer uses (`detail.rs:2804`, `detail.rs:2944`). Do not introduce a parallel calculation that can drift. |
| Where | Clamp in the **key handler**, so the *stored* offset is never out of range. Render-time clamping alone is insufficient — the stored value is the bug. |
| PageDown at end | The last content line remains on screen. Offset does not exceed `max_scroll`. |
| Repeated PageDown at end | Offset is idempotent — pressing PageDown N more times leaves the offset at `max_scroll`. |
| PageUp after that | The **first** PageUp press visibly scrolls. No dead presses. |
| Short document (`total_lines <= visible_height`) | `max_scroll == 0`; PageDown is a no-op; the document never scrolls off screen |
| Down/`j` | Same clamp applies (CONTEXT.md: adjacent unclamped scroll paths in the same handler are in scope) |
| Scope fence | Scroll **offset** only. No keybinding refactor, no scroll-behavior redesign, no change to `PAGE_SCROLL_LINES = 20`. |

**Mechanism note for the planner:** the key handler has no `Rect`, so it cannot know
`visible_height` directly. The established ratatui pattern — and the one this contract
assumes — is that the render pass records the last-known `total_lines` and `visible_height`
into `ProjectViewCache` (alongside the existing `browser_scroll_offset` /
`archive_scroll_offset` at `ui/screens/mod.rs:75,106`), and the handler clamps against those.
Before the first render the recorded height is 0, which yields `max_scroll = 0` — a safe
floor, not a crash.

**Claude's Discretion (auto):** the generic `_ =>` fallback path
(`self.scroll_offset.saturating_add(...)`, `detail.rs:602` and `detail.rs:816`) has the same
unbounded-growth shape and is already clamped only at render (`detail.rs:2029`,
`detail.rs:2125`). Fixing it is **optional and encouraged** — it is the identical defect on
non-file tabs — but it is not a success criterion and must not expand the phase if the
viewport plumbing for those tabs proves invasive.
