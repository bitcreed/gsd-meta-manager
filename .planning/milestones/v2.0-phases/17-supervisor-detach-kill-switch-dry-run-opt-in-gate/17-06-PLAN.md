<objective>
CTRL-01: a user can stop any run at any time, and stopping terminates the entire process tree
including `claude`'s Bash grandchildren. ROADMAP success criterion #1 is the strictest in the
phase — *"Pressing stop during an active run leaves no `claude` process, no grandchild build or
server process, and no zombie behind — verified 15s later."*

This is the second of the two deliverables the user personally made a hard requirement when they
chose full autonomy including `git push`, and it has one specific way of looking finished while
being broken: **stopping the driver but not `claude`**. Phase 15 spawns `claude` with its own
process group leader, so `claude`'s pgid is distinct from the driver's and
`kill(-driver_pgid, SIGTERM)` does **not** reach it. Layer 1 alone *looks* like it works. The tell
is `pgrep -x claude` returning processes after a stop.

D-06's required sequence, all four steps:

1. TUI sends SIGTERM to the **driver's** process group, by the pgid on the run record.
2. The driver's SIGTERM handler calls the **existing** `Executor::cancel()` — Phase 15's already
   built SIGTERM → 10s grace → SIGKILL → unconditional `wait()` on the `claude` group at
   `src/executor/claude.rs:1491-1549`. **Reuse it. Do not build a second teardown.**
3. The driver finishes its journal, releases the lock, and exits.
4. TUI waits out a grace period, escalates to SIGKILL on the driver's group, and reaps.

And D-07's two reaping arms, both required, because the TUI is only *sometimes* the parent: if it
spawned this driver in the current session it must `wait()` or it leaves a zombie; if it restarted
and adopted the run, the driver was reparented to init, `wait()` returns `ECHILD`, and death is
confirmed by re-probing `/proc` until the pid disappears. A plan with one arm fails criterion #1 in
exactly the case the phase exists for.

Output: `src/driver/kill.rs`, the driver-side signal arm, and the criterion-#1 proof with a real
grandchild and a real zombie check.
</objective>

**`src/driver/run.rs`** — extend `execute_run`'s drain loop. Plan 17-01 built it as a
`tokio::select!` loop with a single arm precisely so this task adds an arm rather than
restructuring the body.

Install the handler **before** the loop, not inside it:
`let mut term = tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())`, mapping
its error to `DriveError::Journal`-adjacent handling — a driver that cannot install a terminate
handler must not proceed silently, because the kill switch would then be a no-op; log it at warn
and continue only if installation genuinely cannot fail on this platform, otherwise fail the run
before spawning. Decide and record which, in a comment.

The loop becomes a `biased` `select!` with the signal arm **first**, following
`src/main_loop.rs:130`'s precedent. Order matters: a stop request that loses to a full event queue
is a stop request the user experiences as ignored.

The signal arm calls `shutdown_on_terminate(&executor, &mut handle, &mut journal)`, which does, in
this order and the order is the decision:

1. `Executor::cancel(&mut handle).await` — **this is layer 2 in its entirety**. It is Phase 15's
   already-built sequence: SIGTERM to the `claude` process group, a 10-second grace, SIGKILL, then
   an unbounded unconditional `wait()`. Write a doc comment in the shape of
   `claude.rs:1497-1521` — number the steps, say what each earns, and mark the final wait as
   unbounded on purpose — but the body is a **single call**. State explicitly that a second
   teardown must not be written here and why: `process-wrap`'s `start_kill()` and `kill()` both
   send the uncatchable signal, `signal(15)` is the only graceful path, and re-implementing that
   distinction is how the CLI's documented clean shutdown — the turn abort, the Bash-tree teardown
   through its own handler, the `SessionEnd` hooks — gets skipped (D-06.2).
2. Journal the stop: `journal.record(&JournalEvent::Diagnostic { code, detail })` with a fixed code
   naming a terminate-signal shutdown, before the terminal record, so the reason survives.
3. `journal.finish(outcome_label(&RunOutcome::Killed { .. }))` — the label from plan 17-01's
   `outcome_label` helper, which is why that helper exists. This is the write that makes a stopped
   run distinguishable from a crashed one: a crashed run has no `ended_at`, a stopped one has
   `ended_at` and the killed outcome.
4. Return from `execute_run`, dropping `DriverRun` and with it the `RunLock` — the descriptor close
   is the release (D-20.2). Do **not** add an explicit unlock; the drop is the release path and a
   second one would be a second way to be wrong.

Add `the_outcome_label_for_a_stopped_run_is_killed` to this module's test module, asserting
`outcome_label` maps the killed outcome to the expected snake_case string. It is a one-line test
and it is what stops a later refactor silently relabelling a stop as a failure.

`pub const DRIVER_TEARDOWN_GRACE: std::time::Duration = Duration::from_secs(12);` with a doc in
the `claude.rs:104-107` constants shape stating **both** bounds and why each exists:

`fn signal_group(pgid: u32, sig: Signal) -> std::io::Result<()>` — `rustix::process::Pid::from_raw`
on the pgid, then `rustix::process::kill_process_group`. Its doc states D-08 in full: never a
shell-out to `/bin/kill`, and never a hand-written negative-pid call, because both are ways to get
the sign convention wrong silently and the repository already committed to `rustix` for exactly
this. A `from_raw` returning `None` (a zero or negative pgid) is a hard refusal, not a signal to
pid 0 — signalling process group 0 means *the caller's own group*, which under a TUI is the user's
terminal session. Say that explicitly; it is the single most dangerous mistake reachable from this
function.

`pub enum ReapArm { Parent, Adopted }` — which of D-07's two arms applies. Its doc states the
distinction: `Parent` when this TUI session spawned the driver, `Adopted` when the TUI restarted
and rediscovered the run through the reconciliation scan.

`pub enum StopOutcome { ExitedOnTerminate, ExitedAfterKill, AlreadyGone, SignalFailed { detail } }`
with a `Display`, so the TUI renders a state rather than a message.

`pub async fn stop_run(pid: u32, pgid: u32, run_id: &str, arm: ReapArm) -> StopOutcome` — layers 1
and 4:
1. If `!liveness::is_run_alive(pid, run_id)`, return `AlreadyGone` without signalling. This is the
   pid-reuse guard applied at the moment it matters most: signalling a recycled pid's group is how
   a stop kills a stranger's processes (D-10).
2. `signal_group(pgid, terminate)`. A failure returns `SignalFailed` with the errno kind only.
3. Wait for death, up to `DRIVER_TEARDOWN_GRACE`, by the arm:
   - `Parent` — the caller holds no `Child` here (the reaping task in `src/driver/spawn.rs` owns
     it), so this arm polls the same way as `Adopted` and additionally relies on that task to
     `wait()`. Document this honestly rather than pretending to `wait()` from two places: the
     reaping task is the single `wait()` owner in the parent case, and double-waiting is a race.
   - `Adopted` — the driver was reparented to init, so `wait()` from this process would return
     `ECHILD`; liveness is confirmed by re-probing `/proc` until the pid disappears (D-07).
   Both arms poll `liveness::is_run_alive` on a short fixed interval, following
   `tests/executor_lifecycle.rs`'s `gone_within` shape. Return `ExitedOnTerminate` on death within
   the grace.
4. Otherwise `signal_group(pgid, kill)`, poll again on a short bound, and return `ExitedAfterKill`.
   Log a `tracing::warn!` carrying the pgid and the arm and nothing else when escalation was
   needed — an escalation means the driver did not shut down cleanly and its `claude` tree may have
   been orphaned, which is precisely the case D-09's journaled `claude` pgid exists to make
   traceable and Phase 18's orphan sweep exists to clean.
