## Summary

Both Phase 26 Opus attempts died of two independent, now fully diagnosed instrument/plumbing faults, neither of which is a model-quality finding.

**Root cause A (run1, gap count 3 after one gap round).** The spike-002 launcher counts "distinct `gaps_found` VERIFICATION.md writes" by SHA-256 of the raw file (`launcher.py:119-140`). In run1 round 1 a single `gsd-verifier` agent (`ad3daeda0551148fd`, "Re-verify phase 1") did a `Write` of `01-VERIFICATION.md` at 02:57:04.6Z and, 6.5 s later, a `sed -i` that corrected two line-number references in the same file at 02:57:11.1Z. Two hashes, one verifier run, so `gap-observed count=2` and `count=3` (8 s apart). The launcher gate denies a phase dispatch at `n >= gl + 1` (3) and the driver's rule 5 says the launcher count is authoritative, so the driver parked `gap-rounds` after round 1, and a legitimate round-2 dispatch would have been denied by the launcher even had the driver wanted it. A prompt-only fix cannot work; the counting must change, and spike 002 is pinned, so the change lives in a spike-003 fork of the launcher.

**Root cause B (run1b, "crash").** The GSD `plan-phase` workflow dispatches the planner with `run_in_background=true` whenever `planner.stall_detection_enabled` is true (the default) and expects the orchestrator to poll `gsd_stall_watch`. The Sonnet worker did launch it in the background, said "I'm waiting for its completion notification" (exactly what the v0.3 worker brief tells it to do), and ended its turn. For a subagent, ending the turn completes it (task_notification `completed` after 26 s), while the nested planner (spawn_depth 2) kept running for 8 more minutes. The driver then saw the worker "complete" without a report, correctly noted "the planning worker stopped before sending its report", ended its own turn twice, and when the nested planner's notification arrived there were zero background tasks left, so the session exited rc=0 with no `RUN end`; the launcher labelled that `crashed` (`launcher.py:362-363`). In run1 the identical dispatch used a foreground planner call (`bg=None`), so the hazard is non-deterministic worker behaviour, not a deterministic launcher bug.

**Primary recommendation:** Fork the launcher as `tools/launcher_s003.py` (spike 002 stays byte-identical to `a16e338`) with four small hunks: a shared `gapcount.py` coalescing rule (sliding 45 s window on file mtime; proven on run1 evidence to give counts [1,2] not [1,2,3]), an exit classifier that labels "rc=0, no `RUN end`, last dispatch unreported, no tripped cap" as `stalled`, not `crashed`, a second `Stop` hook (`stop_guard.py`) that blocks the driver's stop while a dispatch is unreported and no agent runs (verified live this session on Haiku, including SendMessage resumption of the finished worker), and prevention at the source (`planner.stall_detection_enabled: false` in the scratch config plus a v0.4 worker-brief fix). Fix `acceptance.py` so RESULT is PASS only with zero FAIL and zero UNDETERMINED and at least one PASS (T-26-11, WR-06). Pre-register every instrument/rubric change as an addendum block with its own prereg SHA before the first paid launch. Expected spend: roughly $7-9 per full Opus launch; three launches fit comfortably inside $52.19.

### Pattern 1: Pure counting module, three consumers
**What:** `gapcount.py` holds the only definition of "a new gap round". The fork launcher, `acceptance.py` (A8/A10 over snapshots) and the replay selftest all call it.
**When to use:** any rule that both gates a live run and later scores it.
**Proposed shape** (values are `[inferred]` design choices; `COALESCE_S` justified by the measured 6.5-8 s rewrite vs >= 534 s between legitimate gaps):
```python
# tools/gapcount.py  (stdlib only)
COALESCE_S = 45                      # [inferred] rewrite 6.5-8 s observed; shortest legitimate gap 534 s observed

class GapCounter:
    """Per phase: a gaps_found write more than COALESCE_S after the previous write starts a new round."""
    def __init__(self, window=COALESCE_S):
        self.window, self.last_write, self.count, self.hashes = window, {}, {}, set()
    def observe(self, phase, ts, digest):
        """-> ("new", k) | ("coalesced", k) | ("duplicate", k)"""
        if digest in self.hashes:
            return ("duplicate", self.count.get(phase, 0))
        self.hashes.add(digest)
        prev = self.last_write.get(phase)
        self.last_write[phase] = ts                       # sliding: a 3-write burst still collapses
        if prev is not None and ts - prev < self.window:
            return ("coalesced", self.count[phase])
        self.count[phase] = self.count.get(phase, 0) + 1
        return ("new", self.count[phase])
```
**Persisted state:** keep `caps["gap_rounds"]["seen"]` (hash -> phase/file, as today) and add `last_write` / `coalesced` siblings under `caps["gap_rounds"]` via `setdefault`, so a relaunch (loaded `state.json`) keeps the window. The frontmatter reader only touches `per_phase` (`driverctl.py:281-283`), so extra keys are harmless.

## Common Pitfalls

### Pitfall 1: Replay that does not reproduce the bug proves nothing
**What goes wrong:** a counting replay that passes with the new rule but was never shown to give 3 with the old rule.
**How to avoid:** the replay prints both: `OLD(hash-distinct) counts=[1, 2, 3]` and `NEW(coalesced) counts=[1, 2]`, and asserts both. Add negative controls: observations 534 s apart stay separate; a burst of three writes 20 s apart collapses to one; a write exactly at the window boundary starts a new round.

### Pitfall 2: A stall guard that blocks forever or blocks while the worker is genuinely running
**What goes wrong:** infinite continuation, or interrupting a healthy wait.
**How to avoid:** allow the stop whenever `background_tasks` is non-empty (docs: the array lets hooks "distinguish 'session is done' from 'session is paused waiting for background work to wake it back up'" `[CITED]`); allow when `stop_hook_active` and the guard's own attempt count >= 3; allow after `RUN end`. The attempt counter file lives in the per-run config dir (bound read-write in the sandbox, `launcher.py:286` `--bind cfg cfg`), not the read-only run dir (`launcher.py:285`).

### Pitfall 3: A "fixed" run still dies because workers background the planner
**What goes wrong:** the guard is a net, not a cure; every block costs driver tokens and relies on Sonnet cooperating with a SendMessage resume.
**How to avoid:** apply `planner.stall_detection_enabled: false` in `setup-scratch.sh`'s `config.json` heredoc (lines 141-166). Verified: GSD `config-get planner.stall_detection_enabled` returns `false` when `{"planner":{"stall_detection_enabled":false}}` is in `.planning/config.json` and `true` otherwise [VERIFIED: probe in scratchpad]. The workflow text then says "issue the same Agent() call but omit `run_in_background`; await its ordinary runtime-native completion" [VERIFIED: ~/.claude/gsd-core/workflows/plan-phase.md:952]. This is rubric J4's named cheap fix (README.md:175), so record it as an ADJUST-class observation, not a silent change.

### Pitfall 4: L7 and the stand-in silently stop testing the cap
