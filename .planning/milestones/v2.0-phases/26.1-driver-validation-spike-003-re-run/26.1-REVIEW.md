## Info

### IN-12: Dead `FM_STATUS` regex in the launcher keeps the pre-IN-06 pattern

**File:** `tools/launcher_s003.py:137`
**Issue:** `FM_STATUS = re.compile(r"^status:\s*([A-Za-z_]+)", re.M)` has no remaining reference (`grep -n FM_STATUS`
finds only the definition) since WR-03 moved `scan_gaps` onto `gapcount.fm_status`. It is exactly the pattern
IN-06 removed (no value boundary, `\s*` crosses lines). It is not in this review's changed-file set, but it
contradicts the "one definition" statement in `gapcount.py`'s docstring and would silently reintroduce the
looseness if someone reused it.
**Fix:** Delete the line (and `re` if it becomes unused; it is still used by `scan_gaps`).

### IN-13: `gen` "always names the generation on disk" is slightly overstated; `finally` can mask the poll error

**File:** `tools/drift.py:11-21, 409-433`
**Issue:** `write_feed` performs two atomic writes (`expected.txt`, then `titles.txt`). If the second fails,
`expected.txt` is already at generation `nxt` while `gen` and `titles.txt` stay at the old generation until the
retry. The docstring claim and the `_poll_verifier` comment hold for `titles.txt`, the file the verifier reads,
not for both feed files. Separately, if `_snapshot_verifications()` raises inside the `finally` while
`_poll_verifier` is already propagating an exception, the snapshot exception replaces it, so `poll-error` logs
the snapshot's exception name and the feed-write failure is not recorded in this poll (it is retried and
re-logged on the next one). Neither affects a verdict; the window is one poll under a disk fault.
**Fix:** Reword to "`gen` names the generation of `titles.txt`, the verifier's input", and, if the diagnostic
matters, wrap the snapshot call in the `finally` in its own `try/except Exception` that logs
`snapshot-error {Name}`.
