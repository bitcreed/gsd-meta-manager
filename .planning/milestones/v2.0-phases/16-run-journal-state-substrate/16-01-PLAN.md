on the first commit rather than retrofitting it.

The slice: a `JournalEvent` carrying a planted credential and a planted dash-encoded home path
is redacted at capture (D-21), wrapped in the `RedactedLine` newtype whose only constructor is
the redactor (D-22), appended to a real `journal.jsonl` as one `write_all` of one

reader (D-13) and asserted **against the bytes on disk** (D-27).

seam is closed by construction rather than by sequencing."* A writer that exists unredacted for
even one commit defeats the whole rationale of SAFE-04.

Output: `src/journal/` with its four submodules (D-35), registered in `src/lib.rs`, plus the
pure `classify_change` function (D-11) that Wave 2's OBS-06 wiring consumes.

**`src/journal/redact.rs`** — transcribe RESEARCH §4.2's `PARTS` table **verbatim, in its stated
order**, with its comments. Order is load-bearing: Rust's `regex` alternation is leftmost-first,
not leftmost-longest (RESEARCH §4.1), so the dash-encoded forms must precede the slash forms and
the most specific credential shapes must precede the generic ones. Two entries carry a comment
recording the leak they fix: the header-value class runs to end of line rather than to
whitespace, because a whitespace-terminated scan redacted only the scheme word and wrote the
credential to disk (RESEARCH §4.3 leak 1); and the slash-path character classes exclude the
square brackets, because the replacement literal re-matched itself and appended a bracket per
pass (leak 2). Compile the single alternation once in a `std::sync::LazyLock<Regex>` built from
the table's named groups — `LazyLock` is stable since 1.80 and the crate's MSRV is 1.87, so no
lazy-static crate is added. `redact` uses the **closure** form of `replace_all`, dispatching on
which named group matched; never a `&str` replacement, because `regex` expands dollar-prefixed
names inside string replacements (RESEARCH §4.7).

Add a second `LazyLock<Option<Regex>>` for the host-specific layer (RESEARCH §4.5): if
`dirs::home_dir()` yields a path, build an alternation of the escaped literal home path and the
escaped slash-to-dash transform of it. `dirs` is already a dependency (`src/config.rs:44`).
Their replacements must be **the same literals the generic rules produce** — the slash form maps
to the generic home literal and the dashed form to the generic dashed literal — so the generic
pass cannot alter the host pass's output and idempotence holds by the same argument that took
RESEARCH's corpus from three failures to zero. Apply the host regex first, then the generic
alternation, in that order, inside `redact`.

`redact_value` is RESEARCH §5.1 verbatim: rewrite every string leaf, recurse arrays, and for
objects drain and rebuild the map so **keys** are rewritten too — `memory_paths`-style maps put
paths in key position (D-23). On a key collision after redaction, disambiguate with a numeric
suffix; never let an insert silently overwrite, which would lose an event field. Numbers, bools
and null are untouched by construction, and that is exactly why the tree walk cannot corrupt a
payload — state this in the doc, since it is D-23's whole argument against post-serialisation
replacement.

`RedactedLine` is a single-field tuple struct holding a private `String`, following
`DrivableProject` at `src/executor/mod.rs:109-140`: private field, one named accessor
(`as_line`, `pub(crate)`), and **no trait implementations of any kind** — no conversion trait,
no deref, no display. PATTERNS line 129 records the one deliberate deviation from the
`DrivableProject` template: this type gets **no** test-only escape-hatch constructor, because
that would reopen exactly the seam D-22 closes. Its sole constructor `new(mut v: Value)` does
three things in this order and the order is load-bearing: `redact_value(&mut v)`, then
`cap_payload(&mut v, MAX_EVENT_PAYLOAD_BYTES)`, then serialise compactly. Capping **after**
redacting is what stops a truncation boundary from splitting a secret so it no longer matches a
pattern; capping the serialised string instead of the tree would produce invalid JSON.
`cap_payload` walks string leaves and truncates any that exceed the cap at a UTF-8 char boundary
using `char_indices`, never by byte slicing — byte slicing panics on a multi-byte boundary
(RESEARCH §10) — and appends a visible marker naming the number of bytes removed, mirroring
`ExecutionEvent::LineTruncated { bytes, prefix }`'s field shape.

Module docs record the honest limit (D-25): a pattern redactor cannot catch an arbitrary
high-entropy secret with no recognisable shape, and a bare username outside a path context is
deliberately not redacted because word-bounded username redaction would shred readable logs for
a marginal gain while every path-shaped occurrence is already covered. Also record D-26: there
is no raw sidecar file, no unredact path, and no verbose mode that skips the filter — any of the
three would reintroduce the exact file SAFE-04 exists to prevent. And record that SAFE-04 is a
capture-path control, not a guarantee: Phase 19's tool-boundary denial is the complementary
control that fires before a secret enters context, and neither substitutes for the other.

**`src/journal/writer.rs`** — `JournalWriter` holds the open `File`, the next `seq`, and a
running `bytes_written`. `open(journal_path)` uses `OpenOptions::new().create(true).append(true)`
and keeps the handle for the run's lifetime; reopening per append costs a syscall pair per event
and buys nothing under `O_APPEND` (RESEARCH §3.4). `append(&mut self, event: &JournalEvent)`
converts the event to a `serde_json::Value`, inserts `ts` (RFC3339 UTC, millisecond precision)
and `seq` into the object, constructs a `RedactedLine` from it, and issues **one** `write_all`
of a single buffer consisting of the line plus its newline. Never two write calls for one
record: two calls reintroduce the torn-line window that one call closes (RESEARCH §3.4,
Pitfall 8). Write straight to the `File` — do not introduce a userspace buffering wrapper, whose
whole effect would be to hold already-serialised events in the dying process's memory, which is
exactly the data D-29 promises is on disk. `seq` starts at 1 and increments monotonically so a
tailing reader can detect gaps (D-03). `bytes_written` accumulates the buffer length; plan 16-03
consumes it for the per-run cap.

D-29's ordering contract is satisfied structurally: `append` takes `&mut self`, so exactly one
owner can write at a time and records land in call order. State in the doc that a
fire-and-forget spawn per event is the shape D-29 forbids and that exclusive `&mut` ownership is
a stronger guarantee than an ordered channel, so no channel is introduced for a producer that
does not exist until Phase 17.

Note in the doc that `serde_json::Map` is a `BTreeMap` in this project (the ordering-preserving
feature is off), so keys serialise alphabetically and a record reads `kind`, `seq`, `ts`, then
its payload rather than in the sketch order. This is deliberate and irrelevant to framing —
nobody should reach for the ordering feature to "fix" it.

**`src/journal/reader.rs`** — transcribe RESEARCH §2.2's `TailCursor`, `TailRead` and
`tail_lines` sketch, which compiles and was executed against a real concurrently-appended file,
including all four of its commented edge cases: a missing file returns an empty read rather than
an error, a file shorter than the cursor resets to zero and reports `restarted`, `read_to_end`
under a `take` bound tolerates the file growing between the metadata call and the read, and a
non-UTF-8 fragment is skipped rather than lossily mangled. The tail splits on bytes and stops at
the last newline; a trailing partial line is left unconsumed. Do **not** reach for the standard
line-iterating reader wrapper — RESEARCH §2.1 demonstrates it treats end-of-file as a line
terminator and therefore yields the torn line as if it were complete, turning a self-healing
torn write into a lost event, which is the exact failure D-13 forbids. Add
`JournalRecord { ts: String, seq: u64, kind: String, #[serde(flatten)] rest: Map<String, Value> }`
and `ParsedLine { Record(JournalRecord), Unparseable { raw, error } }` and
`parse_line(raw) -> ParsedLine`. `kind` is a plain `String`, never an enum: RESEARCH §9 verified
that an internally-tagged enum with a catch-all unit variant **discards the unknown variant's
payload**, which is exactly what D-30 requires it to carry, and `stream_json.rs`'s own rule that
open vocabularies stay `String` applies with more force here because Phase 20 is a known future
emitter of new kinds. Repeat the tolerance-contract sentences from `stream_json.rs:1-32` in this
module's doc.
