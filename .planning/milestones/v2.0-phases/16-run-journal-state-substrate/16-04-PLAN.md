<objective>
Make the reader's tolerance a tested property rather than an intention.

D-30 names three specific tolerances and RESEARCH found that the obvious implementation of one
of them **destroys the data it claims to tolerate**: an internally-tagged enum with a catch-all
unit variant deserialises an unknown kind to a bare marker and the record's fields vanish. The
reader then believes it tolerated the event while having destroyed it (RESEARCH §9, Pitfall 5) —
and every Phase 20 event kind is an unknown kind from this code's point of view. Plan 16-01
chose the shape that avoids this; this plan proves it, and proves the other four tail edge cases
RESEARCH executed against a real concurrently-appended file.

Purpose: OBS-01 makes the journal the *source of truth* for run state. A reader that loses the
last event before a crash, or that silently discards a forward-compatible record, is not a
source of truth. Success criterion 1 — *"the on-disk journal still shows every step it completed
and the last event before death"* — is a claim about the reader as much as about the writer.

Output: `src/journal/reader.rs` with `seq_gaps`, the diagnostic surfacing for `restarted` and
`skipped_oversize`, and the test module that pins all of it. No new public shape beyond
`seq_gaps` — plan 16-01 already defined `TailCursor`, `TailRead`, `tail_lines`, `JournalRecord`,
`ParsedLine` and `parse_line`.
</objective>

  <behavior>
    - A journal path that does not exist yet returns zero lines, an unchanged cursor, and no
      error — the run directory is created before the first append, so this state is normal.
    - Two whole newline-terminated lines return both, and the cursor lands exactly one byte past
      the final newline.
    - A trailing line with no newline returns nothing new and leaves the cursor exactly where it
      was; appending the rest of that line and re-reading returns the completed line once.
    - A file shorter than the stored cursor resets the cursor to zero, returns the whole file's
      complete lines, and reports that it restarted.
    - A buffer that fills the tail bound with no newline anywhere advances the cursor past it and
      reports that it stepped over an oversize line, so the cursor can never stall.
    - A byte sequence that is not valid UTF-8 between two newlines is skipped; the lines around
      it still arrive, and no replacement character is injected into any returned line.
  </behavior>

  <action>
Write the tests first, then adjust `tail_lines` only if a test exposes a defect — RESEARCH §2.3
already recorded this exact behaviour from an executed run, so the expected outcome of each test
is known before it is written and the tests are transcribing a measurement rather than guessing.

Build each case against a **real file** in a `tempfile::tempdir()`, not against an in-memory
buffer: the property under test is about file offsets, file length and end-of-file semantics, and
an in-memory fake would test the fake. Use RESEARCH §2.3's verified table as the expected values.

The partial-line test is the most important one in the file and its comment must say why: the
standard line-iterating reader treats end-of-file as a line terminator and therefore yields the
torn line as if it were complete, which turns a torn write from a self-healing condition into a
lost event — the exact failure D-13 forbids and the one RESEARCH §2.1 demonstrated. Write the
test so it would fail against that implementation: assert both that the torn line is absent from
the first read and that it arrives, exactly once and complete, from the second.

Surface the two diagnostics rather than swallowing them (RESEARCH §2.4). Add doc text on
`TailRead`'s `restarted` field recording that under D-31 and D-32 a journal is never truncated in
place and a run directory is never pruned while active, so `restarted` being true means an
invariant broke and is worth a `tracing::warn!` at the call site — consistent with D-30's rule
that a gap is reported, never fatal. Add doc text on `skipped_oversize` recording that with the
per-event payload cap in place this branch is pure defence against a corrupted file, and that the
cursor advancing is the point: without it the offset stalls forever and every later event is
invisible.

Record in the module doc why inode identity is deliberately not used for rotation detection: it
would be more precise but is platform-specific and unnecessary, because the cursor is keyed by
run and each run has its own immutable directory, so a file shorter than the cursor is the only
reachable rotation signal.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `journal.jsonl` → reader | The file's content was shaped by a driven agent that itself consumed untrusted repository content; the reader must treat every line as hostile input |
| a growing file → a concurrent reader | The writer may be appending during the read, and the process may die mid-line |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-18 | Denial of service | `tail_lines` | high | mitigate | The read is bounded by `MAX_TAIL_BYTES`, and a line that cannot complete inside the bound advances the cursor past it rather than stalling — a malformed or oversized line cannot make every later event permanently invisible (RESEARCH §2.2) |
| T-16-19 | Denial of service | `parse_line` | medium | mitigate | Parsing never fails a read; an unparseable line is counted and skipped. `serde_json`'s default 128-level nesting limit bounds recursion on parsed input, and the parse-then-walk order keeps that guarantee (RESEARCH §5.3) |
| T-16-20 | Tampering | forward-compatible records | medium | mitigate | The kind is a plain string with the remainder flattened, so a record this code does not understand is carried whole rather than reduced to a marker whose fields were silently destroyed (D-30, RESEARCH §9) |
| T-16-21 | Repudiation | a lost event at a crash boundary | high | mitigate | A torn trailing line is left unconsumed and completes on the next read; the tail is asserted against real files with real offsets, so success criterion 1's "last event before death" is a tested property |
| T-16-22 | Information disclosure | reader diagnostics | low | mitigate | `restarted`, `skipped_oversize`, the gap list and the unparseable count are all counts or offsets and carry no event content, per D-28 |

No package-manager installs occur in this plan, so no supply-chain legitimacy gate applies.
</threat_model>
