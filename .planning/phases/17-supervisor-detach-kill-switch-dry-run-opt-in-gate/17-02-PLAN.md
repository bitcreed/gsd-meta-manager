<objective>
CTRL-05: only one driver may execute against a given project at a time, enforced by an OS-level
lock — and a second attempt must be able to say **which** run holds it.

The repository has no file locking of any kind today: no `nix`, no `libc`, no `fs4`, no `fs2`, no
`flock` anywhere in `src/` or `Cargo.toml`. `NamedTempFile` + `persist` is the only on-disk
concurrency primitive that exists. This plan writes the first one.

Purpose: PITFALLS Pitfall 9 states it flatly — *"A PID-or-flag lock is not a lock"*. An advisory
`flock` is process-death-safe: the kernel releases it when the last descriptor closes, including
when the holder is SIGKILLed. A PID file is not, and an in-memory flag in the TUI is worse still,
because the TUI is the process that is *expected* to exit while the run continues.

D-20 names four mechanical properties, each of which is a way the naive version fails silently.
All four are delivered here, and each has its own test.

Output: `src/driver/lock.rs`, the `LockError` surface, `writer::ensure_runs_root`, and a contention
test that runs two real `drive` invocations against the same project and asserts the second names
the first.
</objective>

**`src/journal/writer.rs`** — add `pub fn ensure_runs_root(planning_dir: &Path) -> anyhow::Result<PathBuf>`:

`<root>/.gitignore`, return the root. Refactor `create_run_dir` to call it rather than duplicating

**`src/error.rs`** — add `LockError` in the existing hand-written style. Variants, each with
per-field docs:
`HeldBy { run_id: String, pgid: u32, started_at: String }` — the holder's own record, read out of
the lock file. Its `Display` renders all three, because "which run holds the lock" is the entire
content of success criterion #5 and a message that says only "locked" has not delivered it.
`HeldByUnknownRun` — the lock is held but the file's contents were empty, short, or unparseable.
Its doc states D-20.3's rule in full: a partial or empty read is reported as *held by an unknown
run*, **never** as *not held*, because the alternative converts a lost race into a second
concurrent run.
`Unavailable { detail: String }` — the lock file could not be opened or the runs root could not be
created; a real I/O fault, distinct from contention.
Add `Lock(LockError)` to `DriveError` and extend its `Display` and `source`.

`pub fn acquire(planning_dir: &Path, run_id: &str, pgid: u32) -> Result<RunLock, LockError>`:
1. `writer::ensure_runs_root(planning_dir)` — the ignore file lands **before** the lock file
   exists. Map failure to `Unavailable`.
2. Open `lock_path` with `OpenOptions::new().create(true).read(true).write(true)` — **never**
   `.truncate(true)`. Opening the winner's path with truncate would destroy the holder record the
   moment a second process merely tried; the truncate on the *loser* path is the failure D-20.3
   names, and forbidding it on both paths is cheaper than remembering which is which.
3. `rustix::fs::flock` with the **non-blocking exclusive** operation. On `WouldBlock`/`EWOULDBLOCK`
   (confirm the exact errno constant against the vendored source), fall through to the loser path:
   call `read_holder(planning_dir)` and return `LockError::HeldBy { .. }` when it yields a record,
   or `LockError::HeldByUnknownRun` when it does not. Any other errno is `Unavailable`. A
   **blocking** acquire is explicitly wrong here and the doc must say so: it turns a duplicate
   start into a hang, and a hang is the failure mode a user cannot diagnose (D-20.4).
4. Having won, **now** write the holder record: `set_len(0)` then write the serialised
   `LockHolder` then `flush`. Truncate-then-write on the descriptor already held is correct and is
   not the same act as opening with truncate — say so in a comment, because the two look alike. Do
   **not** write through a temp file and `persist`: a rename would replace the inode and silently
   hand the lock away, which is the single most likely way a reader of `write_run_record` gets this
   wrong. Set 0644 under unix as `write_run_record` does, so the file is readable by the loser
   under a different umask.
5. Return `RunLock { file, holder }`, holding the `File`.

`pub struct RunLock { file: std::fs::File, holder: LockHolder }` with `pub fn holder(&self) -> &LockHolder`.
Its doc states D-20.2 as the reason the type exists at all: `flock` is per open file description,
so dropping the `File` releases the lock — the guard must be stored in the driver's run state, not
in a local that falls out of scope, and a function returning `()` after locking would release
before it returned. Implement **no** explicit `Drop`: closing the descriptor is what releases the
lock and the kernel does that on drop; an explicit unlock would only introduce a second release
path. Say that in a comment so nobody adds one.

`pub fn read_holder(planning_dir: &Path) -> Option<LockHolder>` — the loser path. Open the lock
file **read-only**, read to string, parse. Every failure — absent file, empty file, short read,
invalid JSON — yields `None`, and the *caller* turns `None` into `HeldByUnknownRun`. The doc must
say that this function never opens for writing and never truncates, and that an `O_TRUNC` here
would destroy the very information it came to read.

Four unit tests in this module's `#[cfg(test)] mod tests`, named in the artifact list:
the path sits under the runs root and is matched by the ignore body's catch-all; a holder record
round-trips; an empty lock file yields `None` from `read_holder`; a lock file containing a
deliberately truncated JSON prefix yields `None`. The last two are the ones that matter — they pin
the *never as not held* rule at the parse layer.

other assertion in this file would still pass.

this process **succeeds**. State in a comment that this is the exact scenario a PID file cannot
survive: the file would still name a dead pid and every later start would either refuse forever or
have to guess.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| lock file contents → the refusal message | A file inside the driven repository's `.planning/` decides what the user is told about who holds the lock |
| concurrent driver processes → the shared project tree | Two drivers writing the same `.planning/meta-manager/runs/` would corrupt each other's `active` pointer and retention |
| a dead holder → the next start | Whether the lock survives its owner's death decides whether a project can ever be driven again |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-08 | Spoofing | lock holder record | medium | mitigate | The record is **advisory metadata only** — the kernel's `flock`, not the file's contents, is the enforcement.
