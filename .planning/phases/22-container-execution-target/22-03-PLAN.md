<objective>
Give the user a way to say "run this one in a container" — per project on the registry entry and
per run on argv, with the argv override winning — without adding a second spawn path.

This plan implements D-22-18 (per-project setting with a per-run argv override, override wins) and
the selection half of D-22-19 (the TUI reaches it through the one existing seam). It also closes,
deliberately, the seam-guard gap RESEARCH § Pattern 4 named: `AGENT_OVERRIDE_FIELDS` scans for the
two debug-only program-override fields and will **not** fire on a new target or image field, yet
an image reference is one entrypoint-shaped mistake away from the same hazard those fields are
debug-gated for.

Purpose: target selection is the whole of what "apart from target selection" means in criterion 4.
If it lands anywhere but the one spawn seam, the TUI and a hand-typed invocation stop agreeing and
the phase's central claim stops being checkable.

Output: a per-project field that survives a downgrade, two new argv flags judged at the parse
boundary, the resolved selection reaching the detached driver, and a test file that needs no
container runtime.
</objective>

<inferred_decisions>
- **I-13 — the argv flag spellings are `--target <host|container>` and `--container-image <ref>`.**
  Spelling is Claude's discretion per CONTEXT.md. `--target` is chosen over `--execution-target`
  because the existing neighbour is `--target-phase` and the pair reads as a set; `--container-image`
  is chosen over `--image` because an unqualified image flag on a tool that also talks about
  container images, project phases and roadmap artifacts is the kind of name that later needs a
  rename.
- **I-14 — the per-project field is `execution_target: Option<String>`, not a typed enum on the
  config struct.** The registry file is shared across two binary versions; a `String` plus
  `#[serde(default)]` round-trips a value a newer binary understands and this one does not, which
  is the same tolerance `extra`'s flatten provides for whole fields. It is **judged** into
  `TargetSelection` at the same boundary the argv value is, so there is one judge and not two.
- **I-15 — `CONFIG_SCHEMA_VERSION` is NOT bumped.** Read its doc at `src/config.rs:18-21` before
  acting: the version bumped for the opt-in because the field was required to parse. A
  `#[serde(default)]` addition loads every existing config unchanged, so bumping would be an
  unrelated behaviour change smuggled in under a migration (D-15). Record the reasoning in the
  commit body.
- **I-16 — this plan stops at the parse boundary and the spawn argv.** Turning a `TargetSelection`
  into an `ExecutionTarget::Container` requires the runtime probe and lives in `driver::run`,
  which plan 22-04 owns. A selection that reaches `driver::run` and finds no container support
  yet must **refuse**, never silently run on the host — see this plan's first prohibition — so
  until 22-04 lands, `--target container` is a typed refusal rather than a quiet host run.
- **I-17 — the seam guard's override-field census is extended additively** to cover the two new
  argv fields, per I-06 in plan 22-01: D-22-19 forbids weakening the guard, and an added
  assertion is not a weakening. Every pre-existing assertion stays byte-unchanged.
</inferred_decisions>
