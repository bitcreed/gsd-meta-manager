<assumption_delta_decision>
**Noun now primary:** `ExecutionTarget` — the *generalized* execution target, always an explicit
value, never a default arrived at by omission.

**Decision: `promote`.** `Host` stops being the privileged implicit case and becomes one variant
among two.

Concretely, three promotions, each cheap and each measured before it was chosen:

1. **`#[derive(Default)]` / `#[default]` come off `ExecutionTarget`** (this plan, Task 1). Measured
   with `grep -rn "ExecutionTarget" src/ tests/`: the *only* site that relies on the derive is
   `ExecutionOptions::default()` at `src/executor/mod.rs:518`, which already names
   `ExecutionTarget::Host` explicitly with its own comment. So the removal costs zero call sites
   and makes "a target was chosen" a compile-time property rather than a habit.
2. **The durable rendering goes through one total label function**, not a derived-trait render
   (plan 22-04, D-22-16). Every variant renders through the same exhaustive, wildcard-free match.
3. **Target resolution lives in one named resolver** whose `Host` arm is an explicit branch, not a
   fall-through (plans 22-03 and 22-04, D-22-18).

**Rationale:** `Host` was implicitly the default in four places at once — the derive, the
`Debug` rendering that reached disk, `ExecutionOptions::default()` and the absence of any
selection surface. Adding `Container` alongside a still-privileged `Host` would leave a container
run as a special case bolted onto a host-shaped system, which is exactly the shape criterion 4
("the driver's code path is identical to the host path apart from target selection") forbids.

**Contract test (encoding the generalized intent):** Task 3 of plan 22-04 adds
`every_execution_target_variant_renders_through_the_one_label_function`, a source-derived census
over the `ExecutionTarget` enum body compared against the label function's match arms, so a third
variant cannot be added without a label and the singular assumption cannot return silently.
</assumption_delta_decision>

<inferred_decisions>
The human operator was unavailable. Each line was chosen from the artifacts and the codebase, not
by the user, and is owed an audit.

- **I-01 — `ExecutionTarget::Container(ContainerSpec)` carries the whole spec, not just the
  runtime.** D-22-15 requires the verified identity in the payload; the image, the run id, the
  mounts and the network backend travel with it so `ClaudeExecutor::for_target` needs no second
  argument beyond the envelope environment.
- **I-02 — the network backend is resolved by scanning `$PATH` in-process, never by running
  `podman info`.** `tests/spawn_seam_guard.rs:447-488` fails on any `Command::new(` under `src/`,
  and D-22-19 forbids weakening it. A `$PATH` scan answers the same question RESEARCH § 3c
  answered with `podman info .Host.Pasta.executable`, with no process and with a pure function a
  unit test can drive.
- **I-03 — `DISABLE_AUTOUPDATER=1` rides BOTH the image and the run's `-e` set**, rather than the
  image plus a `.claude.json` key seeded into the volume as RESEARCH § Pattern 7 suggested. Both
  carriers satisfy D-07's never-the-sole-carrier rule; an argv carrier is assertable by a pure
  unit test while volume state is not, and volume state would silently not survive a volume the
  user recreates.
- **I-04 — `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` is added to the container `-e` set.** The spawn
  closure sets it on the *client*, and the client does not pass it on, so without this the
  background-wait ceiling silently does not bound a containerized run. Criterion 4 is false
  without it and no artifact names it.
- **I-05 — `GSD_MM_ENVELOPE_ROOT` is the mechanism that makes the container-side
  `envelope_root()` agree with the host's**, rather than `XDG_DATA_HOME`. The constant already
  exists (`src/envelope/mod.rs:203`), is already user-settable, and is already how the test suite
  relocates the envelope root — so the container path uses the supported seam instead of
  arranging for `dirs::data_local_dir()` to land somewhere by accident.
- **I-06 — extending `tests/spawn_seam_guard.rs` with an ADDITIVE assertion is not a weakening**
  and is therefore permitted under D-22-19. The existing assertions must stay byte-unchanged;
  Task 3 states that explicitly and verifies it.
- **I-07 — the seam guard's `AGENT_OVERRIDE_FIELDS` gap is closed in plan 22-03, not here.** The
  image name is one `--entrypoint`-shaped mistake from the hazard those fields are debug-gated
  for, and the field only exists once 22-03 adds it.
</inferred_decisions>
