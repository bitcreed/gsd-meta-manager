<objective>
Make every prerequisite a named refusal before anything is created, and make stopping a
containerized run reach the container rather than the client.

This plan implements D-22-02 (probe by connecting), D-22-05 and D-22-06 (the API is how a
container is inspected and stopped), D-22-11 (the auth-path proof is inherited — with the
correction RESEARCH measured), D-22-12 (first-time authentication is a separate interactive
one-shot and a driven run refuses rather than logging in), D-22-13 (host prerequisites reported by
name), D-22-14 (the image posture, with its egress claim corrected), D-22-17 (a run whose
envelope cannot be live inside the container refuses), and D-22-19 (no new spawn site). It
resolves RESEARCH conflicts **C-1** (the egress allowlist is not deliverable on rootless podman,
so the posture is stated and recorded instead of promised) and **C-4** (a podman API socket can be
brought up with no systemd and no privilege — the remedy is named and deliberately not automated).

Purpose: RESEARCH measured the one genuinely silent failure mode this phase can produce — mount
the envelope directory without shipping the binary and git's push boundary is absent while git
says nothing at all, exit 0, no warning. A probe is what turns that into a refusal.

Output: `src/executor/container/preflight.rs` and `lifecycle.rs`, the refusal types with their
remedies, and three test files — two of which need no container runtime at all.
</objective>

Create `src/executor/container/preflight.rs` and declare it from `src/executor/container/mod.rs`.

Define `pub struct PreflightOutcome` in the shape of `gate::GateOutcome` at `:133-155` — facts to
record, one doc line each: the socket path that **answered** (never the one a config claimed), the
runtime kind, the server and API versions, the network backend chosen, the observed image-side
binary version, the observed `authMethod`, and the egress posture. Define
`pub enum EgressPosture { Enforced { mechanism: String }, Unrestricted { backend: String } }` and
document, on the type itself, the measurement that forces it: an enforced allowlist is available
on rootful docker (`docker network create --internal` measured blocking DNS and egress, with a
default-bridge control returning 405 from the real API) and is **not** available on rootless
podman inside the no-privileged / no-capability-add fence — slirp4netns has no destination filter,
user-defined networks need `passt` plus `aardvark-dns`, and `CAP_NET_ADMIN` is absent from a
default rootless container's effective set. This is I-08 and RESEARCH conflict **C-1** made
concrete: the type cannot express a restriction that was not obtained.

`pub async fn run_preflight(...) -> Result<PreflightOutcome, PreflightError>` runs the five checks
in an order where a later refusal cannot mask an earlier cause, the discipline
`DrivableProject`'s constructor states at `src/executor/mod.rs:190-216`:

1. **The runtime answered and identified itself** — delegate to `container::detect::detect()`.
   Refusal names every candidate socket path tried.
2. **A network backend exists** — delegate to `argv::rootless_network_backend` for podman; docker
   is the default bridge. This check **reports** rather than refuses when a backend was found, in
   the same class as `gate.rs:221-228`'s warn-and-proceed arm, because a pre-flight that refuses a
   working configuration is the shape of control that gets switched off.
3. **The image exists and can execute the envelope binary** — `assert_envelope_binary_runs_in_image`.
4. **The credential volume is authenticated** — `assert_volume_authenticated`.
5. **The egress posture is determined** and recorded on the outcome.

`assert_envelope_binary_runs_in_image` runs `<host-binary-path> --version` inside the image with
the binary mounted read-only at its identical absolute path and a writable home, and requires the
output to contain the host binary's own `env!("CARGO_PKG_VERSION")`. One probe covers three
measured failure modes at once: a musl base image (alpine was measured failing with an
exec-no-such-file error while a Debian trixie glibc image ran the same binary and printed its
version), a forgotten mount (the same error for a different reason), and an unwritable home
(measured: a panic in `tracing-appender` initialising its rolling file appender, which on the hook
critical path is fail-closed but an unusable envelope). Its refusal carries the remedy verbatim in
spirit: the image cannot execute the envelope binary — rebuild the image on a glibc base
(debian/ubuntu), since a musl base such as alpine cannot run a glibc-linked binary, and give its
non-root user a writable home. Write the doc that explains **why this probe must run before the
real container is created**: if it is skipped, git's own behaviour is the fallback, and git's
behaviour here is fail-open and silent — a hooks path pointing at a directory that does not exist
was measured pushing with exit 0 and no warning at all.

`assert_volume_authenticated` runs `claude auth status` inside the image with the named volume
mounted at the mount point and `CLAUDE_CONFIG_DIR` set to it, deserialises the JSON tolerantly
(unknown fields kept, never rejected — the CLI adds fields between releases, the posture
`stream_json` already takes), and requires `loggedIn == true`. A body that will not parse is a
refusal, not a pass. It additionally requires the reported `configDirectory` to equal the mount
point (I-12). It **reports** `authMethod` rather than enumerating it (A2). Its refusal carries the
interactive one-shot command as the remedy, spelled out with the runtime's own program name and
identity flags, the volume, the mount point, the image and the login subcommand — the remedy is
named, never a generic unavailable-runtime sentence. Its doc must state, in full, why this does
**not** duplicate `gate::check_auth_path` and why the distinction is the point: measured, an
unauthenticated config directory emits a perfectly ordinary first `system/init` with the
subscription api-key-source value, which the Phase 15 gate ACCEPTS, and only then does the run
fail with a not-logged-in result. D-22-11's inheritance proves that no API key snuck in; it does
not prove the volume is authenticated. Both checks are needed and neither subsumes the other.
Do **not** detect authentication by looking for the credentials file: the file is present while a
refresh token can be expired, and the CLI's own status subcommand already owns expiry.

**Every one-shot goes through the runtime API's create / start / wait / logs calls.** Nothing in
this module may launch a child process: `tests/spawn_seam_guard.rs:447-488` fails in both
directions on a new spawn site under `src/`, and D-22-19 forbids weakening it. Build both probes'
container configuration through **one** function that also supplies the real run's identity
settings, so a probe that passes cannot certify a run that would have failed on uid mapping
(I-10); note in its doc that the keep-id userns mode over the Docker-compat API is A-NEW-1, an
assumption the spike measured only as a CLI flag, and that this is its first consumer. Both probes
create with auto-remove so nothing survives them, and both are bounded by a timeout.

`pub async fn stop_container(runtime: &VerifiedRuntime, name: &str) -> ContainerStopOutcome`
copies `driver::kill::stop_run`'s **ordered-steps doc, where the order IS the decision**, in the
same voice:

1. **Inspect before acting.** Ask the runtime whether a container by this name exists and is
   running. A container that is already gone is a distinct fact from a stop that could not be
   determined, and `kill.rs:316-323` is emphatic that the two must not collapse.
2. **Stop with a bounded timeout** — `CONTAINER_STOP_TIMEOUT`, defined in
   `src/executor/container/mod.rs` and documented as a frank number with no tuning data behind it,
   in the register of the neighbouring caps.
3. **Escalate to a forced removal** if the bound expired, with a `tracing::warn!` naming what was
   escalated and why, exactly as the driver's own escalation does.
4. **Return a typed outcome** whose already-gone arm is distinct from its could-not-be-determined
   arm, and which **never invents a state**: a container the runtime still reports after a forced
   removal is one whose removal has not been observed yet, not one that survived, and reporting it
   as anything else would invent a state.

Define `pub enum ContainerStopOutcome` with those arms and a `Display` in the existing voice, in
this module rather than in `src/error.rs` — it is an **outcome**, not a refusal, exactly as
`driver::kill::StopOutcome` lives beside `stop_run` and not in the shared error module. Do not
edit `src/error.rs` in this plan; any refusal this needs is already in the taxonomy 22-01 landed.

State in the module doc why this exists at all (D-22-06): a process-group kill reaches the
`podman`/`docker` **client**, not the container, so relying on the client's signal forwarding
alone would leak a running container past a kill switch. This is the container-shaped extension of
`src/driver/kill.rs`, never a replacement for it. State also why the name is knowable without a
third write to the run record: the container is created under the run id, which
`crate::journal::new_run_id` produces before spawn and which is already validated as a plain path
component, so a reattaching driver, the TUI and `driver::reconcile` can all reach the container
with no extra state (assumption A8 — a runtime with a narrower name grammar would need a prefix,
falsified trivially by the first e2e run).

**Never call this on the render thread.** Say so in the doc, in the register
`kill.rs:334-336` uses: the TUI dispatches a container stop on a task and takes the result back as
an `Action`, exactly as the existing driver stop does.

Mirror the grace relationship the way `kill.rs:372-389` mirrors the claude group grace: add an
in-source test asserting `CONTAINER_STOP_TIMEOUT` is **strictly less than** the driver teardown
grace, with the assertion message explaining the ordering — there are three graces now (the
container stop, the claude group grace, the driver teardown grace) and a container stop that
outlasts the grace the client's own group is given would make the teardown story arrive in the
wrong order (I-11).
