**Planner investigation of failure 1 `[inferred — audit]` (the executor confirms or corrects it and
records the choice):** the listing order reaches the baseline comparison, so it is a product
property, not just a test artifact.
- `walk_nested_git` and `walk_tracked_dir` pop a LIFO stack over raw `fs::read_dir` order.
- Under truncation, which `.git` entries and tracked files a snapshot records depends on that
  order. `findings` then diffs that partial set against the baseline, and a nested `.git` path is
  a git-relevant (push-blocking) finding.
- So the same checkout can yield different findings on different file systems, or after a
  directory is rewritten. On the container's overlayfs the walk exhausts its budget in `flood/`
  before reaching `.claude/worktrees/w/.git`.
- The user-visible findings list is already sorted (`out.sort()`); the snapshot contents are not.
- Hence the fix goes in production code. Making the test order-insensitive would leave a
  nondeterministic guard.

**Budget arithmetic for the planted fixture under a name-ordered, pre-order walk with limit 10**
(planner's count; the executor re-counts):
- the tracked dirs take 2 (`.git/hooks/pre-commit`, `.claude/agents/a.md`);
- the root listing takes 3 (`.claude`, `.git`, `flood`), for a total of 5;
- `.claude` takes 2 (7), `.claude/agents` 1 (8), `.claude/worktrees` 1 (9), and
  `.claude/worktrees/w` 1 (10, which records `.claude/worktrees/w/.git`);
- `flood/`'s 40 entries then exceed the 0 remaining, so the walk truncates.

The existing exact assertions therefore hold deterministically.
