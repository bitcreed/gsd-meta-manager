## Warnings

### WR-10: The pre-registration gate ("no bypass") is satisfied by an edited or untracked prereg file

**File:** `experiment/run.sh:97-113` (with `experiment/acceptance.py:651-675`)
**Issue:** `prereg_gate` requires `rubric-check --block 26.1-run2` to print `RUBRIC-UNCHANGED` and
`PREREG_SHA` to be an ancestor of HEAD. Both inputs come from `results/prereg-26.1-run2.txt`, a plain file
whose own state is never checked. `rubric-check` compares the README at `PREREG_SHA` with the working-tree
README, so the answer depends entirely on which sha the file names. Changing the rubric block, committing it,
and pointing `PREREG_SHA=` at that new commit (or at HEAD) yields `RUBRIC-UNCHANGED` and an ancestor sha. An
untracked or locally modified prereg file passes just as well. The header and the message advertise "no
bypass" and "commit it and prereg-... first", but the gate verifies neither. This is the control that is
meant to make the Run 2 rubric pre-registered before paid spend.
**Fix:** Require the prereg file to be tracked and clean, and require the recorded sha to be at or before the
commit that introduced that file:
```bash
git -C "$S3" ls-files --error-unmatch "$pf" >/dev/null 2>&1 || { echo "run.sh: $pf is not committed" >&2; return 1; }
git -C "$S3" diff --quiet HEAD -- "$pf"                     || { echo "run.sh: $pf differs from HEAD" >&2; return 1; }
add="$(git -C "$S3" log --diff-filter=A --format=%H -- "$pf" | tail -1)"
git -C "$S3" merge-base --is-ancestor "$sha" "$add"         || { echo "run.sh: PREREG_SHA postdates $pf" >&2; return 1; }
```
(Keep the existing ancestor-of-HEAD check.) Add a selftest case with a temp repo.

### WR-11: An in-flight in-script relaunch is not reserved, so a concurrent run's ceiling gate under-counts by one launch budget

**File:** `tools/campaign_budget.py:131-151`, `experiment/run.sh:465-476`
**Issue:** The first launch of a run is reserved while it is in flight: the dir has `run-env.txt` and no
result, so rule 4 charges `MAX_BUDGET_USD`. After a relaunch the gate copies `launcher-result-N.json` into the
results dir (WR-05), and from then on the dir is priced at the finished launches only (for example 3.0). The
relaunched launch N+1 can spend up to `BUDGET` (15 for run2) that no other gate sees until its result is
copied at the end. Parallel runs are the project default, so a second run that starts during that window
passes the ceiling check although the combined worst case is over $60. The WR-05 fix text ("counting relaunch
spend") holds for the run itself but not for its neighbours.
**Fix:** Have `relaunch_gate` mark the in-flight launch, for example by appending
`RELAUNCH_IN_FLIGHT=<N+1>` to `run-env.txt` before `continue`, and have `dir_cost` add `MAX_BUDGET_USD` for a
launch number with that marker and no `launcher-result-<n>.json`. Alternatively, make `dir_cost` charge
`max(priced, ...) + budget` whenever `run-env.txt` has no `ENDED_UTC=` line. Add a selftest for a dir with
`launcher-result-1.json`, no `ENDED_UTC`, and the marker.

## Info

### IN-06: `STATUS_RE` has no value boundary and its `\s*` can cross a line

**File:** `tools/gapcount.py:63`
**Issue:** `^status:\s*["']?([A-Za-z_]+)` is now the single definition for the launcher cap, the snapshots
and the scoring. The value is not terminated, so `status: gaps_found2` reads as `gaps_found`. `\s*` also
matches a newline, so an empty `status:` line followed by another key reads that key's name as the status
(`status:\nphase: x` yields `phase`, reproduced). A write the verifier did not intend as `gaps_found` could be
counted as a round by every consumer at once. A UTF-8 BOM before `---` also reads as no frontmatter.
**Fix:** `STATUS_RE = re.compile(r"""^status:[ \t]*["']?([A-Za-z_]+)(?![\w-])""", re.M)`, and decode with
`utf-8-sig`. Update the pinned `assert STATUS_RE.pattern == ...` selftest line and add a case for each shape.

### IN-07: The stop-guard tamper-bound comment is not accurate

**File:** `tools/stop_guard.py:26-30`
**Issue:** The docstring says the clamp "bounds a forged counter to at most GUARD_LIMIT blocks per dispatch
(a forged file can only restart the count, never extend it)". Restarting the count is extending it:
`{"key": "<current>", "n": 0}` written back before each Stop gives unlimited blocks, and `n` above the limit
silently disables the guard. Both stay inside spike 002's accepted trust boundary and the 90-minute cap, but
the stated guarantee is wrong. The negative-number case from the original IN-01 is fixed.
**Fix:** Reword to "the clamp only rejects malformed values; a well-formed forged counter can lengthen or
disable the guard, which is inside the documented trust boundary", or keep the counter outside the
model-writable config dir.

### IN-08: `dispatch-denied` pairing relies on the prompt's log-before-spawn ordering

**File:** `tools/exitclass.py:59-82`
**Issue:** A denial cancels the latest open dispatch when no item-level event lies between them. If the driver
makes a top-level Agent/Task call without logging `dispatched` first (the hook denies it all the same,
`driverctl.py:452-457`) straight after a genuine dispatch, the denial cancels the genuine, unreported one. The
Stop guard then allows the stop and `classify_exit` labels it `crashed` instead of `stalled`. This is the
narrow remainder of the original WR-01 and rests on the prompt's step 3 being followed.
**Fix:** If the gate can be extended, add the denied call's `description` or `prompt` hash to the
`dispatch-denied` line and cancel only a dispatch whose `step` matches; otherwise document the assumption in
the `outstanding_dispatch` docstring.

### IN-09: Verifier-spawn counting trusts the tool_use block, and a failed feed write loses the advance

**File:** `tools/drift.py:333-336, 402-412`
**Issue:** A spawn counts as soon as an `Agent`/`Task` tool_use block for `gsd-verifier` is in a transcript.
A call that a hook denied or that failed to start is still counted and advances the feed. Separately,
`_poll_verifier` records the spawn in the scanner and increments `self.gen` before `write_feed`; an `OSError`
there is swallowed by `poll_safe`, leaving `gen` ahead of the feed on disk until the next spawn, so snapshots
are labelled with a generation the verifier did not read. The first case is unlikely (nested spawns are not
gated), the second needs a disk fault. Both skew only the seed, not a verdict directly.
**Fix:** Increment `gen` after `write_feed` succeeds and re-queue the spawn on failure; optionally count a
spawn only once the matching `tool_result` exists.

### IN-10: The fail-closed `--block 26.1-run2` selftest is skipped once the prereg file exists

**File:** `experiment/acceptance.py:1340`
**Issue:** The `RUBRIC-MISSING` assertion sits behind `if not os.path.exists(.../prereg-26.1-run2.txt)`. The
file is now committed, so the only test of the fail-closed branch for this block never runs, and the selftest
result depends on repository state. `rubric_check(base, sha, block)` already takes a base directory.
**Fix:** Run the assertion against an empty temp directory: `rubric_check(tmpdir, block="26.1-run2")`.

### IN-11: The prereg sha is passed to `git show` unvalidated

**File:** `experiment/acceptance.py:655-659, 687`
**Issue:** `PREREG_SHA=(\S+)` is taken from the file as is and interpolated into `git show`'s first argument.
A value beginning with `-` is parsed by git as an option (for example `--output=...`). The file is
operator-controlled and committed, so this is hardening only, and the Phase 26 path has the same shape.
**Fix:** Require `re.fullmatch(r"[0-9a-f]{7,40}", sha)` before the call, as `run.sh` already does in `sed`,
or pass `--end-of-options`.
