<objective>
Give the run directory its durable shape: the record that is committed, the ignore file that
protects everything else, the caps that stop a four-hour run filling a disk, and the retention
that keeps the last N runs.

Three of these are traps rather than features, and each is a trap RESEARCH found by executing
rather than by reading:

1. `git check-ignore` answers *"did a pattern match?"*, not *"is this file ignored?"* — a
   negation counts as a match, so the obvious verification of D-08 reports `run.json` as ignored,
   the precise inverse of the truth. A first pass of the research itself made this mistake before
   the ground-truth check corrected it (RESEARCH §1.2).
2. A driven repository whose own root `.gitignore` excludes `.planning/meta-manager/` as a
   **directory** makes the nested re-inclusion impossible, because git never descends into an
   excluded directory. D-07's goal-legibility rationale then evaporates silently, in exactly the
   third-party repositories this tool exists for (RESEARCH §1.3).
3. `NamedTempFile::persist` preserves the temp file's 0600 mode, so the one file whose whole
   purpose is being read by somebody else later is unreadable to a second uid (RESEARCH §1.4).

Purpose: OBS-01 says the journal is the source of truth for run state. That is only true if the
record survives, is findable, is committed where a collaborator can read it, and does not grow
without bound.

Output: the writer's durability and layout surface, plus the integration test that proves the
ignore posture against a real `git init` using ground truth rather than a question git answers
backwards.
</objective>

`write_runs_gitignore(path)` writes the body **only if the file is absent**, returning whether it
wrote. Idempotent by construction, so a second run in the same project does not churn the file.

`create_run_dir(planning_dir, run_id)` computes `run_paths`, `create_dir_all`s the run directory

`warn_if_parent_excludes(project_root, run_json)` runs `git check-ignore -v` **once** against the

bare quiet-mode invocation answers the inverse of the question (RESEARCH §1.2, Pitfall 1). That
is why this function inspects the reported pattern rather than the exit status.

`write_active_pointer(runs_root, run_id)` writes the run id and one newline to the `active` file;
`clear_active_pointer` removes it if present. `read_active_run(planning_dir)` returns the id.

file is written because it is cheap to poll and useful to Phase 17's reconciliation, but the

lexicographic sort equal chronological sort and a listing cannot go stale after a crash while the
file can. `read_active_run` therefore returns the pointer only when a directory of that name
actually exists, and logs a `tracing::warn!` on disagreement.

`write_run_record(paths, record)` mirrors `src/config.rs:71-87` exactly, with `anyhow::Context`
on every fallible step: `NamedTempFile::new_in` the run directory, write the pretty-serialised
record, and `persist`. Two deliberate deviations from `save_config`, both already decided:
pretty serialisation is right here because the record is a document rather than an NDJSON line;
and under `cfg(unix)` set the temp file's permissions to 0o644 before persisting, because
`persist` preserves the temp file's 0600 and a second uid on the same host — a container mount,
a shared CI runner — otherwise cannot read the one file whose purpose is being read later
(RESEARCH §1.4). Do **not** copy `queue_md.rs`'s fixed-`.tmp`-name-plus-rename write: a fixed
temp name collides if two writers ever race, and RESEARCH §1.1 additionally measured that
`NamedTempFile` produces a dot-prefixed basename which the ignore body already covers, so an
interrupted persist leaves no untracked litter.

The doc on `write_run_record` carries D-06 and D-07 together, because they are one argument:
this document is written exactly twice — write one at run start, before any agent is spawned,
carrying the immutable facts (run id, goal prompt, GSD command, execution target, opt-in record,
start timestamp, session id, pid and pgid, CLI version, argv digest); write two at terminal
transition, after the last agent has exited, adding the end timestamp and the derived outcome.
Nothing else ever rewrites it. That immutability is what neutralises the Aider garbage-commit
hazard: the driven agent runs git inside the very worktree containing this file, so a file that
were perpetually dirty for the whole run would let any `git add -A` the agent issues sweep a
mid-run snapshot into an unrelated commit and record a running status in history forever. Record
the forward constraint for Phase 20 verbatim: when a run becomes a multi-invocation loop, the
terminal write must still happen after the *last* invocation exits, never between steps —
per-step state belongs in the journal, which is ignored.

Unit tests in this file's test module: the ignore file is written on first call and a second call
leaves its bytes and modification identical; a run record round-trips through
`write_run_record` and deserialises back to an equal value; and under `cfg(unix)` the persisted
record's mode is 0o644.

Bound growth at the **run** level. The per-event level is already handled inside
`RedactedLine::new` (plan 16-01) and must not be duplicated here; D-31 bounds two levels because
the two failure modes are different, and this task owns the second.

`JournalWriter` gains a `truncated: bool`. On each `append`, after the line is built and its
length known: if `truncated` is already set and the event `is_content()`, drop the event and
return without writing. If `truncated` is not set and `bytes_written` has reached
`MAX_RUN_JOURNAL_BYTES`, write exactly **one** `JournalEvent::JournalTruncated` carrying the
bytes written so far and the cap, set the flag, and then apply the content rule to the event that
triggered the breach. Once the flag is set the writer keeps writing every non-content event —
lifecycle, decision, diagnostic and outcome kinds — forever. D-31 is explicit about why the
asymmetry exists: the run must always be able to write its terminal record, and silently
dropping the ending is the one failure OBS-01 cannot tolerate.

Add a counter of suppressed content events and include it in the `JournalTruncated` event's
successors only as a `Diagnostic` at run end if it is non-zero — a suppressed-event count is the
same kind of signal as the dropped-event count in plan 16-02, and it costs one line. Keep the
count out of every log line's body; a count is content-free by construction (D-28).

`prune_runs(planning_dir, retain, active_run_id)` implements D-32. Read the runs root, keep only
entries that are directories whose names parse as a run id, and sort them lexicographically —
which equals chronologically by D-02's construction, and that equality is the whole reason
pruning is a directory listing rather than a parse of every record. Skip the active run id.
Skip any run whose `run.json` is missing, unreadable, or has no end timestamp: that record is
precisely what Phase 17's crash reconciliation reads, and pruning it would destroy the evidence
of the crash this phase exists to survive. Remove the remainder beyond `retain`, newest first,
and return the removed ids. Removal failures are logged as `tracing::warn!` and never propagate —
a failed prune must not stop a run from starting. The doc states D-32's timing argument: pruning
happens at **run start**, not at run exit, because an exit-time prune is skipped by exactly the
crash the phase is built to survive.

Add `crash_test_writer_loop(journal_path) -> !` in this file, `pub` and **not** `cfg(test)`,
because plan 16-06's crash harness re-execs the integration-test binary and the child must run
the real writer, which a shell fixture cannot (RESEARCH §6.1-6.3). Its doc must open with a bold
**Test support only** in the deliberately-loud style of `DrivableProject`'s escape hatch at
`src/executor/mod.rs:117-122`, and must state that it reaches the file through the ordinary
`append` path and therefore does not reopen the `RedactedLine` seam. It opens a `JournalWriter`
on the given path and appends `JournalEvent::ExecEvent` records in a tight loop, forever, each
carrying a planted Anthropic-shaped key and a planted dash-encoded home path of a fictional user
so the crash test can assert redaction on the bytes that survived the kill (D-27). Expose the two
planted values as `pub const` items in this module so the test asserts against the same values the
child wrote rather than against a retyped copy.

Unit tests: appending past the cap emits exactly one truncation notice and then suppresses only
content events; a terminal record appended after the cap is reached is still present in the file;
pruning with a retain count keeps the newest and removes the oldest; pruning never removes the
active run; pruning never removes a run whose record has no end timestamp.
