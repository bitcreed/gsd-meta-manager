<objective>
Close the phase: give a run one lifecycle API, wire the journal to the executor stream as a
consumer, and prove the two properties the phase is actually judged on with a real signal and
real bytes.

D-36 scopes this precisely. Phase 16 wires the journal as a **consumer** of the existing
`ExecutionEvent` stream plus its own run-start and run-end lifecycle events. It does **not**
build the observe-decide-act loop, detached spawn, or any rendered surface — nothing in this
repository spawns a `ClaudeExecutor` yet, and that is Phase 17's to add. So the consumer is a
library component driven here by a synthetic event sequence, ready for Phase 17 to hand a real
one. D-36 also requires the schema to carry the kinds Phase 20 will emit while Phase 16 emits
only the kinds it can actually produce **and says so** — this plan writes that statement down.

D-37 constrains the mapping: `claude_code_version`, `session_id`, capabilities and the derived
outcome are all read off `ExecutionHandle`, `GateOutcome` and the outcome types, which Phase 15
recorded specifically so Phase 16 could journal them without a signature change. Do not widen
those types. Carry Phase 15-05's notional-cost caveat into the field docs rather than restating
cost as if it were billed.

Purpose: success criterion 1 says the journal survives death, and D-34 says that is tested
**mechanically**, with a real signal, not a mock. RESEARCH §6 built and ran exactly that harness
eight times with no new dependency: re-exec the integration-test binary, select a child role with
an environment sentinel, and use the standard child kill, which is already SIGKILL on unix and
was confirmed by the child's wait status every run.

Output: the run lifecycle, the mapping, the crash test, and the phase gate.
</objective>
