<objective>
Make Phase 15's dropped-event count reachable by something other than a log line.

Plan 15-08's summary hands this over explicitly: *"a run that silently lost 40 events is
materially different from one that lost none, and the count is the only signal that
distinguishes them"* — and today that count is a `tracing::warn!` and nothing else, living as a
local `u64` inside the run loop at `src/executor/claude.rs:939`. D-33 requires the journal to
record it. A journal consumer reads the `ExecutionEvent` stream, so the count has to arrive on
that stream.

Purpose: this is the smallest change that satisfies D-33 without widening any of the types D-37
protects. `ExecutionHandle`, `GateOutcome` and `RunOutcome` are untouched — D-37 says Phase 15
recorded `session_id`, `capabilities`, `claude_code_version` and the derived `RunOutcome`
specifically so Phase 16 could journal them **without a signature change**, and that constraint
holds here. The drop count is different in kind: Phase 15 never recorded it anywhere a consumer
could see, so a new stream event is the honest mechanism rather than a widened struct. An
`Arc<AtomicU64>` on the handle was rejected for the same reason D-20 bans handles in cloneable
message types.

Output: one new `ExecutionEvent` variant, one small helper with its own tests, one call site,
and one explicit reducer arm. This plan is deliberately narrow and file-disjoint from 16-01 so
the two run in parallel; plan 16-06 maps the new variant into a journal record.
</objective>

    - Given zero drops, `report_dropped` sends nothing and the receiver sees an empty channel.
    - Given N drops with N > 0, `report_dropped` sends exactly one `EventsDropped` whose `count`

    - `ExecutionEvent::EventsDropped` carries only a number, so nothing it can print is content.

  <action>
Add `EventsDropped { count: u64 }` to `ExecutionEvent` in `src/executor/mod.rs`, following the
file's convention that each variant's doc says *why the variant exists*. The doc must record:
this is the running total of events lost because a stalled consumer did not take them inside the
forward bound; it is emitted **once per run**, in the terminal path, and only when the total is
non-zero; it carries a count and nothing else, because the count is the only thing that has ever
reached the log and widening it to carry the lost events would defeat the point of having
dropped them (T-15-53, D-28). Name D-33 and cite 15-08's handover in the doc so the next reader
finds the provenance. No boxing: RESEARCH §8.3 measured `ExecutionEvent` at 120 bytes and the
lint's threshold as a 200-byte *difference*, so an 8-byte variant is nowhere near it —
add a one-line comment saying the sizing question was measured, not assumed, so nobody boxes
reflexively.

In `src/executor/claude.rs`, add `async fn report_dropped(sender, dropped)` next to `forward`,
sharing its doc idiom. Behaviour: return immediately when `dropped` is zero; otherwise send one
`ExecutionEvent::EventsDropped { count: dropped }` wrapped in `tokio::time::timeout` at
`EVENT_FORWARD_TIMEOUT`, discarding the result. Use the same bounded shape as the existing
`Exited` send at lines 1232-1236 and for the same stated reason: this send goes to the very
channel a stalled consumer has already filled, so an unbounded send here would be a new way for
a run to end without its outcome ever being sent, which is the one thing that must never happen
(CR-01). The doc must say the report is **best-effort**: if the consumer is still stalled when
the run ends, the report is lost and only the `tracing::warn!` in `forward` remains, and that is
an acceptable degradation because a lost diagnostic is strictly better than a parked run.

Call `report_dropped(&events_tx, dropped_events).await` in the terminal path immediately
**before** the existing `if let Some(status) = status` block that forwards `Exited`, so the count
lands ahead of the terminal event and a journal reading the stream in order sees the loss before
the ending. Do not move, reorder or otherwise touch the `Exited` send or `drop(events_tx)`.

Update the comment on `dropped_events` at line ~936-939 so it no longer says the count is the
only thing that reaches *the log* — it now also reaches the stream, once, at the end.

Tests, in `src/executor/claude.rs`'s existing test module, using `#[tokio::test]` as the module
already does. Write them before the helper body: a zero-drop call leaves `try_recv` empty; an
N-drop call yields exactly one `EventsDropped` with `count == N` and then an empty channel; and a
call against a channel built at capacity 1 and pre-filled, with the receiver held but never
read, returns — assert with a wall-clock upper bound generous enough not to flake (a multiple of
the forward bound), which is the only place a timing assertion is warranted here because the
property being tested *is* a deadline.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| supervisor run loop → bounded event channel | A stalled consumer is the adversary here; the supervisor's own bounds must stay enforceable while it is stalled |
| dropped-event report → log and journal | The report is about content that was lost; it must not carry that content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-08 | Information disclosure | `ExecutionEvent::EventsDropped` | medium | mitigate | The variant carries a `u64` and nothing else; there is no field that could hold a raw line or message body, which is the same discipline `claude.rs:1262-1266` already states for the warning (D-28, T-15-53) |
| T-16-09 | Denial of service | `report_dropped` | high | mitigate | The send is wrapped in `tokio::time::timeout` at `EVENT_FORWARD_TIMEOUT`, so a stalled consumer cannot hold the run loop open past the outcome send (CR-01); tested against a pre-filled channel with no reader |
| T-16-10 | Repudiation | run history | medium | mitigate | Emitting the count once per run means a journal can distinguish a lossless run from a lossy one; without it a truncated run history is indistinguishable from a complete one (D-33) |
| T-16-11 | Tampering | Phase 15's verified transport | high | mitigate | The change is additive — one variant, one helper, one call site — and the acceptance criteria require the full `executor_lifecycle` and `executor_transport` suites to stay green and `ExecutionHandle`/`GateOutcome`/`RunOutcome` to stay byte-identical (D-37) |
