**Gap T-19-60 — the `PreToolUse` guard decides what a command is by looking at `words[0]`.**

`classify_segments` (`src/envelope/hooks.rs:929-1054`) resolves `policy::program_name(words[0])`
and asks three questions of it — is it `eval`, is it a nested shell with a `-c` payload, is it
`git` — then asks `pr_command_label` whether it is `gh`/`glab`. A command whose FIRST token is
anything else falls through to `Ok(None)`, which `guard_in` turns into a permit. Reproduced
against the built binary and recorded in `19-SECURITY.md`:

```
exit=2  git push --force origin main                      <- denied, correct
exit=0  env git push --force origin main                  <- PERMITTED
exit=0  GIT_CONFIG_COUNT=0 git push --force origin main   <- PERMITTED
exit=0  timeout 60 git push --force origin main           <- PERMITTED
exit=0  command git push --force origin main              <- PERMITTED
exit=0  env gh pr create --title x                        <- PERMITTED, NO ledger line
```

The diagnosis is settled; do not re-derive it. Three guarantees fail on one line:
layer 2 does not see the command, layer 1's `Bash(git push:*)` is a prefix rule that a
four-letter prefix does not match, and the SAFE-06 cap is bypassed with no ledger line and
therefore no park (D-06, D-19, D-24).

**The class, not the instances.** The obvious fix is an enumerated wrapper list
(`env`, `timeout`, `nohup`, `command`, `nice`, `sudo`, …) plus one test row per listed name.
That is a fix certified by a corpus structurally incapable of failing on the class at issue: it
is green on the day it lands and silent on `stdbuf`, `setsid`, `ionice`, `chrt`, `taskset`,
`doas`, `runuser`, `script`, `xargs`, `time`, `/usr/bin/env`, `busybox env`. The class is
**anything that changes which token is the effective program without appearing as the first
token**, and this plan resolves the effective program structurally: consume leading `NAME=VALUE`
assignment words by the shell's own grammar, then find the first token whose BASENAME names a
program the envelope already governs. It never asks what the wrapper is called, so there is
nothing for a new wrapper to be missing from.

later wrapper cannot walk around and a later reader can tell was measured rather than intended

`pub fn mentions_governed_program(text: &str) -> bool` — whether any whitespace-delimited word of

`pub enum ProgramResolution { NoProgram, Governed { index: usize }, NestedPayload { index:

reason from the message would be deriving the same fact a second way.

`pub fn resolve_program(segment: &[Token]) -> ProgramResolution`, in this order — the order is
part of the contract because each step exists to be reached only when the one above it did not
answer:

  1. Any token satisfying `tampers_with_envelope_env` → `Refuse { HookBypassBlocked, … }`.
     `19-SECURITY.md` records that `GIT_CONFIG_COUNT=0 git push --force` neutralises layer 3 with
     the same token that made layer 2 blind, so the assignment is refused on its own account and
     not merely parsed past (D-09).
  2. Skip leading assignment words. Nothing left → `NoProgram`: a bare `FOO=bar` executes no
     program, and refusing it would be refusing an assignment.
  3. The head token carries `expansion` → `Refuse { EnvelopeAssertionFailed, … }`, preserving
     today's refusal verbatim in meaning.
  4. `program_name(head) == "eval"` → `Refuse { EnvelopeAssertionFailed, … }`, likewise.
  5. Left to right from the head, the first token that is not `-`-prefixed and does not carry
     `expansion` and either
       (a) has a basename in `GOVERNED_PROGRAMS` → `Governed { index }`, or
       (b) contains whitespace and whose FIRST word has a basename in `GOVERNED_PROGRAMS`
           → `NestedPayload { index }`.
     (b) is what covers the payload half of the class — a command handed to an unknown program
     as one quoted string. It discriminates rather than blanket-denying, because the payload is
     classified: a payload that classifies as allowed is allowed. The doc states the resulting
     cost plainly: an argument that literally spells a refused git command, such as
     `rg "git push --force" src/`, is refused, while `rg "git status" src/` is not.
  6. Otherwise the first `-`-prefixed, non-`--` short-option word containing `c` whose following
     word exists → `NestedPayload { index: that following word }`. This is the structural
     replacement for the `NESTED_SHELLS` list: `-c` is the shell's own spelling for "here is a
     command line", so `sh`, `bash`, `busybox sh`, `script` and anything else that consumes one
     are covered without being named, and `bash -lc "…"` is covered where the exact-`-c` match
     was not.
  7. Otherwise, before answering `Ungoverned`, one last check: any assignment word whose VALUE
     has a basename in `GOVERNED_PROGRAMS` → `Refuse { EnvelopeAssertionFailed, … }`. This is
     the narrow case where resolution is ambiguous in a way that could be hiding a governed
     program — `X=git; env $X push --force` binds the name in a segment the guard can see — and
     it is checked HERE, after resolution has otherwise failed, so it can never fire on
     `git commit -m x=git`, whose segment already answered at step 5.
  8. `Ungoverned`.
