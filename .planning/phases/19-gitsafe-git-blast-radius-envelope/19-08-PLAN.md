Create `tests/async_blocking_guard.rs`, modelled structurally on `tests/spawn_seam_guard.rs` — same
header block, same allowlist-with-justification shape, same word-boundary matcher, same
`concat!(env!("CARGO_MANIFEST_DIR"), "/src")` root, and the same reason for being an integration
test rather than an in-source one: it reads the source tree, and a test that walks `src/` has no
business living inside it. Keep the walk to `src/` only, never `tests/`, which is what lets this
file's own prose name the tokens it forbids without invalidating its own gate.

**What it scans.** For each `.rs` file under `src/`, track whether the current line is lexically
inside an `async fn` body — track `async fn` openings and brace depth, which is enough for a lint
and is all a lexical scanner can honestly claim. Inside such a body, flag a line that calls a
known-blocking marker: the synchronous process-execution methods `output`, `status` and `spawn` on
the standard-library command type; the advisory file-lock call; and the blocking standard-library
filesystem calls on the driver's paths. Do not flag a line inside a region that has already handed
off to a blocking task — track the blocking-task hand-off the same way, so the canonical wrapper in
`src/driver/mod.rs`'s dry-run arm reads as compliant rather than as a violation.

**Matching.** Copy `calls_marker` rather than substring-matching, for the reason
`spawn_seam_guard.rs:75-104` records: a plain `contains` is wrong, and the concrete case it records
is an unrelated identifier whose letters contain a marker's letters. A guard that fires on a
coincidence is a guard that gets disabled.

**The allowlist.** Declare `ASYNC_BLOCKING_ALLOWLIST` as a const array of file paths, each with a
one-line justification in the sibling file's comment style. Use the in-file const rather than a
separate data file, matching the established convention exactly — one guard shape in this tree, not
two — and say so in a comment so the choice is visible rather than accidental. Repeat the sibling's
"a declared allowlist, not a habit" framing: whoever adds an entry adds it in the same commit as
the code it covers, and that deliberate edit is the entire point.

**The honest limit, in the file's own doc.** State plainly that this is **a lint, not a proof**: a
lexical scanner cannot see through a helper function, so a blocking call reached indirectly is
invisible to it. State why it is worth having anyway, citing the observation rather than a theory —
the deadlock recorded at `tests/driver_lock.rs:201-215` was reproduced, not theorised — and citing
this phase's own reason: several synchronous git shell-outs landed on paths a TUI-side caller
already reaches, where the same stall is a frozen frame the user cannot escape.

Run the guard against the tree as it stands after plan 19-07 and resolve every hit: either wrap the
call in a blocking hand-off, or add a justified allowlist entry. Do not weaken the marker set to
make a hit disappear.
