## The design question, answered

**Is there a source of truth better than a hand-maintained list?** The honest answer has three parts.

**No, not for the guard.** Git's global-option grammar is not derivable from the shape of the word:
`git --attr-source HEAD status` and `git --no-pager status` are syntactically identical — a long
option followed by a bare word — and only git knows which word is the value. Knowledge is
unavoidable. And it cannot be fetched at guard time: the guard runs synchronously on the agent's
`PreToolUse` critical path, where a reproduced 180–240 second hang is the reason
`push_needs_resolved_dests` exists at all; and a guard that asks the program it is guarding to
describe its own grammar can be lied to by a `git` earlier on `PATH`, which is precisely the surface
this phase's own argv-printing shims demonstrate. There is nothing machine-readable to fetch either:
git's global options live in prose, and `--list-cmds=` lists commands, not options.

**Yes, for the amount of knowledge required — and the reduction is the fix.** The only thing
`scan_leading` needs per option is **one bit: does it consume the next word.** Three structural rules
supply that bit with no knowledge of git at all — a `--`-prefixed token containing `=` is
self-contained whatever the option is, `--` ends the options, and a non-`-` token ends the scan — and
they go first. What remains is one bit for the spellings without an attached value, and **the fix is
to make the ABSENCE of that bit a refusal instead of a guess.**

**Yes, for the PIN.** `ENVELOPE_ENV_KEYS` was given a drift pin sourced from the place that changes
when the fact changes, after being wrong twice. There is no in-codebase source for git's grammar, so
the source is git itself — consulted in a TEST, not in the guard. A two-sided probe classifies every
entry mechanically:

```
git <opt> version          prints `git version …`  =>  did NOT consume the next word
git <opt> XVALUE version   prints `git version …`  =>  DID consume XVALUE
both print `unknown option: <opt>`                 =>  this git does not accept it at all
```

It already catches a live defect: the installed git answers `unknown option: --super-prefix` for an
entry the constant carries today. Its limit is stated rather than hidden — it pins the constants
against the DEVELOPER's git, not the runtime git. **So the fail-closed default is the safety property
and the pin is the maintenance property, and they are complementary: staleness costs refusals rather
than bypasses, and the pin says which refusals.**

## The cost, measured from both sides

**Zero on the installed git.** Every option `git version 2.43.0` accepts is classified by the probe
