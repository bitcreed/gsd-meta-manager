## Why the rule is inverted rather than extended

Rounds 1–3 enumerated the ways a shell assembles a word and guarded each one. Round 3 restored the
expansion bit at the decision boundary (Rule A); round 4 refused a segment whose head sat behind a
word-splitting closer (Rule B). Audit 4's verdict on that shape, in its own words:

> **Rule A decides on one bit. Rule B decides on one geometry.** … They cannot fail on the other
> ways bash makes a word — brace expansion, pathname expansion, tilde expansion, `$IFS`-driven
> re-splitting — none of which sets either signal.

Five rounds of enumeration have not converged. So the question changes direction:

> **A decision word must be LITERAL — the shell must hand it to the program byte-identically to how
> it is written. Anything else is unresolvable and refuses.**

That is positive evidence of literalness instead of enumeration of non-literalness, and it closes
brace expansion, pathname expansion, tilde expansion, `$IFS` re-splitting and the mechanisms nobody
has enumerated, in one rule.

**What LITERAL means, exactly.** The evidence is collected by `tokenize` as the word is consumed —
never by pattern-matching the recovered text, which has had its quoting removed and in which
`gh api "repos/{owner}/{repo}/pulls"` (literal, and counted today) is indistinguishable from a word
the shell rewrites. The bit is set when the tokenizer consumes, OUTSIDE quotes:

| Class | Characters | Why it is not literal |
|---|---|---|
| expansion | `$`, `` ` `` | parameter, command and arithmetic expansion — and every `$IFS` re-split of the result |
| pathname | `*`, `?`, `[` | the result depends on the working directory, so it is unknowable at guard time whether or not a file matches today |
| tilde | `~` | the result depends on the passwd database |
| brace | a `{`…`}` pair carrying a top-level `,` or `..`, or a `$`, a backtick or a nested `{`; or a `{` with no match | bash splices its alternatives back into the enclosing command |

And NOT set for: anything inside single quotes; a backslash-escaped character, because escaping is
exactly what makes a character literal; and a `{`…`}` pair with no comma and no range, which bash
passes through unchanged.

## The region does not move, and that is what keeps the cost small

The decision region is `19-14`'s, which audit 4 probed specifically and found slot-exact in every
adjacent cell: the git verb, `config`'s key operand, the forge's first two subcommand words, and the
`gh api` endpoint / method / flag-ness words — every index reported by the scan the classifier itself
runs. **Round 3's principle stands and must not be weakened.** Operands stay free:

```
refused:  git {push,--force} origin main         permitted: git commit -m "use ${HOME} here"
refused:  git pus? --force origin main           permitted: gh pr create --title 'fix $PATH handling'
refused:  gh p? create --title x                 permitted: git -c user.name="$NAME" commit -m x
refused:  git config core.hooksPat? /tmp/x       permitted: ROOT=$(git rev-parse --show-toplevel)
refused:  gh api repos/o/r/pul?s -f title=x      permitted: git add src/*.rs   /   rg "x" src/*
COUNTED:  gh api repos/{owner}/{repo}/pulls -f title=x        (a ledger line, and the cap charged)
```

## The two clauses, and why one is not enough

**Clause 1 — the word.** A decision word that is not literal makes the command unresolvable.

**Clause 2 — the simple command.** `git {push,--force} origin main` has NO decision word to test:
it splits into `git`, `push,--force` and `origin main`, the first resolves `Governed` with an EMPTY
argv, and `classify_git` returns `Allow` for a bare `git`. A brace expansion is a property of the
command, not of a word, so a command a brace expansion splices into is unresolvable and is refused
when **(a)** any of its segments resolves `Governed` or `NestedPayload`, **or (b)** any
comma-separated alternative inside its brace expansions names a governed program. Both halves are
load-bearing: (a) alone permits `{git,push,--force,origin,main}`, whose single segment's basename is
not a governed program; (b) alone permits `git push {--force,origin} main`, where the governed word
is outside the braces and what the splice hides is `--force`.

## The decision on `T-19-93`, and why it is the tokenizer rather than the scans

`gh api repos/{owner}/{repo}/pulls -f title=x` is **`gh`'s own documented placeholder syntax and not
an evasion**. Bash passes those braces through unchanged, and the correctness bar is **count, not
refuse**. It is closed by the literal-brace branch of the tokenizer's classification, not by teaching
`scan_gh_api`/`endpoint_is_pulls` about `{owner}`/`{repo}`, for three reasons:

1. **It is where the defect is.** The braces are literal in bash; the tokenizer was wrong about them,
   not the forge scans. A tolerance in the scans is a second consumer compensating for a splitter
   that mangles the word — the shape this phase has produced four times.
2. **It generalises.** `endpoint_is_pulls` is one consumer of one word. The same literal spelling can
   appear in a git verb, a `config` key operand and a `-c` assignment; a scan tolerance fixes one
   cell and leaves the rest one slot over.
