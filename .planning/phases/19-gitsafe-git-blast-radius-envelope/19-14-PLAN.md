## The design question, answered

**Option (a) — thread the expansion bit through to the classifiers' decision region — is chosen.
Option (b) — refuse any expansion-carrying token anywhere in a governed segment — is rejected.**

(b) is rejected on a cost, not on taste. It refuses `git commit -m "use ${HOME} here"` and
`gh pr create --title "fix $PATH handling"`, which are ordinary commands this project types and
which this round's scope names as must-keep-working. That is `T-19-75` widened from `rg` to every
commit: a control that fails into unusability gets switched off, which is the failure mode
AR-19-11 exists to record.

(a) is implemented as a **decision region**, and the region is exactly **the words the matched arm
reads** — no wider, no narrower. Every index in it is reported by the scan the classifier itself
runs, so it cannot drift one slot from the words that decide:

- **git — the VERB**, at the absolute index `classify_git` slices to, plus, when that verb is
  `config`, the one operand `classify_config` tests with `is_hooks_path_key`. The tokens
  `scan_leading` WALKS are deliberately *not* in the region: `leading_git_option` consumes a `-c`
  option and its assignment token, so a region defined that way would refuse
  `git -c user.name="$NAME" commit -m x`. Those options are governed instead by the key-half check
  below, which matches the only decision that scan makes.
- **forge — the first TWO non-flag subcommand words**, because `pr_command_label` matches on
  `["pr", "create", ..]` and `["mr", "create", ..]`. A region of one word leaves
  `P=create; gh pr $P --title x` unmatched, uncounted and unparked — `T-19-88`'s own shape
  recurring inside the fix for `T-19-88`. Widening to all of `subcommand_words` is wrong the other
  way: it pulls `--title`'s value in and refuses `gh pr create --title 'fix $PATH handling'`.
  For an `api` argv the region additionally covers the `-X` / `--method` value in both spellings
  and any token whose own text *begins* with an expansion marker — because in that arm a token's
  flag-ness is what decides, and such a token could itself be `-f`. A token like `title="$T"`
  begins with literal text and cannot be a flag, so it stays an operand.

Everything to the right is an OPERAND and stays free. That boundary is the whole of (a)'s cost
containment, and it is pinned from both sides rather than asserted:


The `-c` half is the same root cause one slot to the LEFT: `scan_leading` decides whether

it cannot make. It is refused only when the KEY half of the assignment is unreadable, which is why
`git -c user.name="$NAME" commit -m x` still runs.

## What `split_words` still needs, settled rather than deferred

Round 2 declined to change what `{`/`}` do in `split_words` because that is real shell grouping
syntax with blast radius across every command the guard splits. **That change is still not made,
and after Rule A it is not needed for the damaging half.**

`git ${X}push --force origin main` tokenizes to the segments `git $` | `X` | `push --force origin
main`, because the tokenizer flushes the current word at `{` and the flushed word `$` carries
`expansion`. The first segment resolves `git` at the head and its VERB SLOT is that `$`. So Rule A
refuses it — and refuses `${X}stash`, `${X}update-ref`, `${X}config`, `$(true)push`, `gh ${X}pr`
and the three-layer composed line — with `SEPARATORS` untouched. Six of the eight measured
`T-19-87` rows close on the verb-slot rule alone.

**What remains is the rows where the flush lands in a wrapper PREFIX severed from the governed
program.** `C=GIT_CONFIG; env -u ${C}_COUNT git fetch origin` yields `env -u $` | `C` |
`_COUNT git fetch origin`; the last fragment resolves `git` behind a clean one-word prefix and its
verb is the literal `fetch`. No verb-slot rule can see it, because by then the shape is gone.

**Rule B closes it positionally, and reads no name at all.** `tokenize` marks a `{`, `}`, `(` or
`)` as a *word-splitting flush* when a word was in progress immediately before it — true for every
boundary inside `${X}push` and `$(true)push`, false for `{ cmd; }` and `( cmd )`, because bash's
own grammar requires whitespace after `{` and an operator before `}`. A segment whose immediately
preceding operator is a word-splitting **CLOSER** (`}` or `)`) is a fragment continuing the
enclosing word after an expansion, so its first token is **not a command position**: what the shell
puts in front of it is unknowable. If such a segment resolves a governed program it is refused,
which is step 5's existing rule applied where the prefix was severed rather than merely expanded.

The **opener** is excluded on purpose: a segment after `(` is the substitution's own contents and
IS at a command position. That is what keeps `echo $(git rev-parse HEAD)`,
`git log --format=%h $(git rev-parse HEAD)` and `ROOT=$(git rev-parse --show-toplevel)` running.

**An earlier formulation of Rule B was withdrawn and must not come back.** Keying it on a literal
fragment being a substring of an `ENVELOPE_ENV_KEYS` entry is evadable by moving the split point —
`C=GIT_CONFIG_COU; env -u ${C}NT git fetch origin` leaves the two-character fragment `NT` — and it
simultaneously refuses `ROOT=$(git rev-parse --show-toplevel)`, `DIR=$(mktemp -d)`,
`RUN_ID=$(uuidgen)`, `CONFIG=$(cat cfg)` and `COMMAND=$(which git)` on every Bash tool call,
because those uppercase names sit inside envelope key names. The positional rule refuses the
moved-split-point spelling AND the bare `env -u ${C} git fetch origin` — which has no literal
fragment for any substring rule to find — while permitting every uppercase-assignment row, and it
has nothing to floor or evade.
