## Warnings

### WR-02: The egress server's work sits outside the sandbox cgroup and is unbounded in memory, connections and time

**File:** `src/launcher/egress/http1.rs:21`, `src/launcher/egress/mod.rs:59`, `:594-605`, `:710`
**Issue:** _Carried from prior review, not re-reviewed (`egress/http1.rs` and `egress/mod.rs` are outside this increment's file scope)._ The server runs inside the launcher, not under the scope's `MemoryMax`/`TasksMax`. Several resources are bounded only per connection, or not at all:
- A sandboxed driver can hold up to 64 connections (`MAX_CONNECTIONS`), each buffering up to `BODY_MAX_BYTES` (32 MiB) before the judge. That is about 2 GiB of raw bodies, and `serde_json::Value` expansion on a 32 MiB array-heavy body multiplies it again. The driver's own memory cap does not apply to this.
- `tunnel()` (`copy_bidirectional`) has no idle or lifetime timeout.
- `relay_response` has no read or write timeout, so a client that stops reading, or a stalled upstream, pins a permit forever.
- Pinned permits turn every later request into `503` for the whole run. In an unattended run that shows up as inference failures.
**Fix:** Add a total-memory budget, for example a `Semaphore` weighted by body bytes, or a lower body cap for non-streaming JSON. Wrap `copy_bidirectional` and the relay loop in idle timeouts, for example by resetting a deadline per chunk. Document the residual host-side cost in the "residual risks" section of `docs/DRIVER-SANDBOX.md`.

### WR-04: The directory of this binary is bound read-only whole, which can expose unrelated files

**File:** `src/launcher/home.rs:235-241`, `:87-98`, `:187-194`
**Issue:** _Re-verified. Partly fixed by 28.1-12, still open._ `REFUSED_ROOT_REL` now includes `.local/bin` and `bin`, so a binary installed in either of those two shared bin directories is bound as a single file. That closes the common case. The rule is still a fixed list of names, so the exe directory is bound whole for every other shared directory: `~/Downloads`, `~/tools`, `~/go/bin`, `~/.npm-global/bin`, `~/.bun/bin`, `~/.volta/bin`, and so on. Sibling files there become readable inside the sandbox (scripts, wrappers with embedded tokens, other installers' state).

The `install_root` fallback has the same shape: the parent directory is bound whenever its name is not `bin` or `versions`, for example a tool at `~/Downloads/node` or `~/tools/x/node`. The ledger records this half as deferred.
**Fix:** Bind the file itself (`ro(facts.exe)`) for the exe unless the parent is a dedicated install root (it holds only this product). The shim and the bridge need only the single executable. For `install_root`, apply the same rule: bind the parent only when it is `bin`/`versions` under a named tool directory, else bind the file.

### WR-05: Allowlist binds that lie under the project path are covered by the later read-write project bind

**File:** `src/launcher/sandbox.rs:509-535` (home binds) against `:548` (`--bind project project`)
**Issue:** _Carried from prior review, not re-reviewed (`sandbox.rs` is outside this increment's file scope)._ The home binds are emitted first and the project bind later. A later bind covers earlier mounts beneath it. `sandbox.rs` itself says "a later bind covers an earlier one" for the guard binds. `HomeSetup` does not know the project path.

When the binary lives under the project being driven, for example `target/debug/gsd-meta-manager` while the tool is used on its own repository, or any PATH tool inside the project, the "read-only" bind of the exe directory is masked by the writable project bind. The agent can then rewrite the binary that the `driverctl` shim, the gate hooks and the bridge execute, and that the host later runs.
**Fix:** In `HomeSetup::for_host` (or `SandboxSpec::from_host`), drop any `Ro`/`Overlay` entry that lies under the project path. Better, re-emit those entries after the project bind, or refuse a launch whose exe lives under the project.

### WR-06: `git worktree add` of the driver-written tip still runs the host's global or system filters

**File:** `src/launcher/push.rs:259-270` (`GIT_HARDENING`), `:649` (the scan worktree)
**Issue:** _Carried from prior review, not re-reviewed (`push.rs` is outside this increment's file scope)._ `GIT_HARDENING` neutralises `core.fsmonitor`, `core.hooksPath` and `core.pager`. The scan step then checks out the tip tree that the driver wrote into a worktree of the mirror. Attributes committed in that tree (`.gitattributes`: `* filter=lfs`) activate any filter driver defined in the host's `~/.gitconfig` or `/etc/gitconfig`, for example git-lfs's `filter.lfs.smudge`/`process`. That runs a host program on driver-chosen content, and git-lfs reads `.lfsconfig` from the working tree to choose its endpoint.

The planted-file guard only inspects the checkout's own files, so this path is not covered.
**Fix:** For the mirror-only steps (`fetch`, `rev-parse`, `worktree add`) set `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_SYSTEM=/dev/null` (or `GIT_CONFIG_NOSYSTEM=1`). The one `push` step can keep the credential configuration it needs. Alternatively add `-c filter.lfs.smudge= -c filter.lfs.process= -c filter.lfs.required=false` plus the same for other known drivers, and prefer `git archive` over a checkout for the credential scan.

### WR-08: A truncated scan always refuses the push, so large repositories need `--ack-planted` every time

**File:** `src/launcher/push/planted.rs:47`, `:265`, `:289`, `:873-877`; `Finding::is_git_relevant` at `:139-151`
**Issue:** _Re-verified, unchanged by 28.1-11..14._ The nested-`.git` walk shares one 200,000-entry budget and visits every directory outside `SKIP_DIR_NAMES`, including `vendor`, `dist`, `build`, `.next` and data directories. Any repository over that count has `truncated = true` on every snapshot, and `ScanTruncated` is git-relevant. Every push of such a project is refused and parked until the operator passes `--ack-planted`, so the flag becomes routine and the guard is reduced to noise. The baseline hides nothing here, because truncation is recomputed on each snapshot.
**Fix:** Walk only what git could treat as a nested repository (skip any directory git ignores, or use a much larger or per-subtree budget). Report truncation as informational, not push-blocking, when the baseline was truncated too. Document the limit in `docs/DRIVER-SANDBOX.md`.

### WR-09: The header posture row still clips `PLANTED` and `absent:` when three sandbox pieces are missing

**File:** `src/ui/screens/driver_run.rs:1061-1068` (the `missing:` list), `:1141-1170` (`push_posture_28_1`); test gap at `:5055-5082` (`degraded_fm`, `posture_row_keeps_the_security_groups_visible_at_narrow_widths`)
**Issue:** The 28.1-13 change claims "importance order so that `clip_line` removes the least important text first" and a test that keeps `PLANTED`/`absent:` visible at widths 72, 80 and 100. But `clip_line` cuts from the right, and the DarkGray `missing: ...` list is emitted before the security groups. The test fixture (`degraded_fm`) uses only two missing pieces (`bwrap, systemd-run`). A real degraded run with all three pieces missing is the normal case: `off_platform_missing()` always reports three, so every macOS run is one. A Linux host with `--unsandboxed` and none of the tools has the same shape.

I measured this with a scratch copy of the tree (not the repo). `degraded` with `bwrap, systemd-run, user-systemd` missing:

```
72 : [  sandbox UNSANDBOXED missing: bwrap, systemd-run, user-systemd  ·  PLA…]
80 : [  sandbox UNSANDBOXED missing: bwrap, systemd-run, user-systemd  ·  PLANTED 1  …]
100: [  sandbox UNSANDBOXED missing: bwrap, systemd-run, user-systemd  ·  PLANTED 1  ·  absent: all 8  ·  ]
```

With no planted findings, `absent: all 8` is cut to `absent: all…` at 80 and `abs…` at 72. So at 72 columns the `PLANTED` warning is unreadable, and at 80 columns `absent:` is lost. These are the cases SC7 was written to protect. The host-token run also puts a 40-character hint ahead of `prompt`, `egress` and `api`, which pushes those off at 100 columns and below.
**Fix:** In the degraded branch, drop the per-piece list when it does not fit, or abbreviate it (`missing: 3`), or emit the posture groups (`PLANTED`, `absent:`) before the `missing:` list. Add the three-piece fixture, and a `PLANTED`-plus-degraded case at 72 and 80, to `posture_row_keeps_the_security_groups_visible_at_narrow_widths`.

### WR-10: The `egress.log` cap lets the driver switch the audit trail off

**File:** `src/launcher/egress/log.rs:70-72`, `:117-148`
**Issue:** This is a follow-on to the WR-03 fix. The cap works as designed: once 8 MiB is written, one `log truncated` line goes in and every later record is dropped, and a reopened full log (any relaunch of the same run) stays silent. The driver chooses the request rate, so it can reach the cap whenever it wants, with junk requests that each cost one 100 to 800 byte line. Every request after that, including a `CONNECT` to an allowlisted host or an inference call, leaves no trace. The disk-fill channel is closed, but it has become an audit blind spot that the sandboxed party can trigger on demand. The marker line tells the operator that the log was cut. It does not say what happened afterwards, and the counters in `EgressStats` do not record hosts.
**Fix:** Keep the tail rather than the head. Rotate once to `egress.log.1` (bounded to 2 x cap) and keep writing, or reserve part of the budget for non-refused records (`Inference` and `Connect` with a forwarded verdict), or collapse repeated identical refusals into a count. At the least, keep appending a per-minute summary line of `connect` hosts after the cap.

## Info

### IN-03: A non-array host `permissions.<list>` replaces the launcher's deny list

**File:** `src/launcher/config_dir.rs:524-536`
**Issue:** _Carried from prior review, not re-reviewed (`config_dir.rs` is outside this increment's file scope)._ In `managed_settings`, a host value that is not an array is inserted with `ours.insert(list, other)`. A host `"deny": "x"` therefore replaces `DENY_TOOLS`. The module claims Claude Code refuses such files, but the launcher should not depend on that for a safety list. Separately, `disableAllHooks` is not among `LOCK_KEYS`, so a host managed value stays in force; that is deliberate ("never hidden") but undocumented.
**Fix:** Skip non-array values for `deny` (keep the launcher's list). Consider adding `disableAllHooks` to `LOCK_KEYS`, or document it.

### IN-04: `EGRESS_KEY` names the `driver` key, not the egress key

**File:** `src/config.rs:164-166`
**Issue:** _Carried from prior review, not re-reviewed (`config.rs` is outside this increment's file scope)._ `EGRESS_KEY = "driver"` and `EGRESS_SUBKEY = "egress"`. The name reads as the opposite of what it holds and will mislead whoever adds the next `driver.*` setting.
**Fix:** Rename to `DRIVER_KEY` (and update the doc links).

### IN-05: `current_exe()` can carry a ` (deleted)` suffix after an in-place upgrade

**File:** `src/launcher/run.rs:662` (used in `bridged_command` and the shim)
**Issue:** _Carried from prior review, not re-reviewed (`run.rs` is outside this increment's file scope)._ On Linux, when the binary is replaced while the launcher runs, `current_exe()` returns a path ending in ` (deleted)`. The bridge command and the `driverctl` shim then name a non-existent file, so every relaunch of a long run fails with exit 127.
**Fix:** Resolve once at start, or strip the suffix and re-check that the path exists. Failing that, refuse the relaunch with a clear message.

### IN-06: Gateway and alternative-provider setups are silently unsupported and the docs do not say so

**File:** `src/launcher/sandbox.rs` (`ROUTING_STRIP_ENV`), `docs/DRIVER-SANDBOX.md`
**Issue:** _Carried from prior review, not re-reviewed (`sandbox.rs` and the docs are outside this increment's file scope)._ `ANTHROPIC_BASE_URL`, `ALL_PROXY` and the Bedrock/Vertex/Foundry switches are stripped in both postures. In the bwrap posture the egress server hard-codes `api.anthropic.com:443`. A user who routes through a corporate gateway or a cloud provider therefore either fails inference or, when degraded, silently talks to the public API. The "residual risks" list covers an upstream `HTTPS_PROXY` but not this.
**Fix:** Add a line to the unsupported/limits section, and print a one-line launch warning when the stripped variables were set in the launching environment.

### IN-07: The duplicate-key refusal is exact-case, so a case-variant key is still judged and forwarded differently

**File:** `src/launcher/egress/policy.rs:278-350` (`UniqueKeys`), `:364-376` (`judge_body`)
**Issue:** This is a residual of the original WR-01 reasoning, not a regression. The WR-01 text named case-insensitive field matching (Go's `encoding/json`) as a second differential. The fix closes exact-key duplicates, including escape-spelled ones, but `{"tools":[],"Tools":[{"type":"web_fetch_20250910"}]}` still passes: the judge sees an empty `tools` and an unknown `Tools`, and the original bytes go upstream. The doc comment on `judge_body` says a body with unique names "means the same thing to every conforming parser", which holds for conforming JSON parsers but not for case-folding struct decoders. The Anthropic API's decoder is not known to fold case, so this is defence in depth only.
**Fix:** In `visit_map`, track keys by `to_ascii_lowercase()` (or Unicode case-fold) and refuse a body where two keys fold to the same string at any depth. Add `"Tools"` and `"MCP_SERVERS"` to the `a_repeated_key_at_any_depth_is_denied` matrix. Reword the doc comment to say "case-insensitively unique names".
