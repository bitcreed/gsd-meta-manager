# Phase 28.1: Code Review Report

**Reviewed:** 2026-10-24
**Depth:** standard (diff `736e134..HEAD`, security-relevant source read in full; test files sampled, not audited line by line)
**Files Reviewed:** 50
**Status:** issues_found

## Summary

Phase 28.1 adds the launcher-side egress server (inference reverse proxy and CONNECT proxy), the in-sandbox bridge, the `$HOME` allowlist, the managed-settings tier and the planted-file guard. The pure-policy layer (`egress/policy.rs`, `egress/http1.rs`) is carefully built: the request head is parsed whole, smuggling shapes are refused, the upstream request is re-serialised, and the DNS answer is vetted once and dialled without a second lookup. The weak spots are at the edges of that core.

- One ship blocker: an ungated unix-only test module in `home.rs` should fail the release workflow's `cross-target-check` for Windows. I found it by inspection and did not run it, because cargo was off limits.
- The sandbox boundary leaks in a few places: the exe-directory bind, binds under the project path, and host-side resource use the cgroup does not cap.
- The planted-file guard has gaps: a BOM in a git config, a truncation rule that blocks large repos, and `git worktree add` honouring host-global filters.

No hardcoded secrets, no token logging (the `Debug` impls redact), and no header or CRLF injection path into the upstream request were found.

## Critical Issues

### CR-01: `home.rs` tests use unix-only items ungated, so the Windows `--all-targets` check cannot compile

**File:** `src/launcher/home.rs:544` (also `:806-809`, `:925-933`); module declared ungated at `src/launcher/mod.rs:73`
**Issue:** `pub mod home;` is not cfg-gated, and its `tests` module is plain `#[cfg(test)]`. It does the following without a platform gate:
- `use std::os::unix::fs::symlink;` (line 544), used at 806-809 and 933.
- `host_facts_resolve_a_home_symlink_back_to_the_known_name` (925-933) calls `HostFacts::from_host`. That function lives in `mod imp`, which is `#[cfg(any(target_os = "linux", target_os = "macos"))]`.

`.github/workflows/release.yml` runs `cross-target-check` for `x86_64-pc-windows-gnu` with `--all-targets` and clippy, and the publish job needs it. On Windows, `std::os::unix` does not exist and `HostFacts::from_host` is absent, so the test cfg fails to compile (E0433/E0599). The workflow comment says this gate exists because "v1.14 shipped Linux-only code ungated". It is the same class of regression.
**Fix:** Gate the tests that touch unix-only items, or the whole module:
```rust
#[cfg(all(test, any(target_os = "linux", target_os = "macos")))]
mod tests { /* ... */ }
```
Alternatively, keep the platform-neutral tests (`the_golden_allowlist_*`, `render_gitconfig`) in an ungated module and move the `symlink` and `from_host` tests into a gated one. Confirm with `cargo check --all-targets --target x86_64-pc-windows-gnu`.

## Warnings

### WR-01: The body is judged as a parsed value but forwarded as the original bytes

**File:** `src/launcher/egress/mod.rs:516-521`, `src/launcher/egress/policy.rs:270-275`
**Issue:** `judge_body` parses the body into a `serde_json::Value`, which is last-key-wins for duplicate keys and case-sensitive. `request_bytes` then forwards the original bytes, not the judged value.

For example, `{"tools":[{"type":"web_fetch_20250910"}],"tools":[]}` passes the judge, because the last `tools` is empty, but the upstream still receives both keys. The security boundary (`mcp_servers`, `container`, `tools[].type`, `source.type`) therefore depends on the upstream parser agreeing with serde_json on duplicate keys. Any case-insensitive field matching on the upstream, as Go's `encoding/json` does for struct fields, would have the same effect.

Every common parser is last-wins today, so this is defence in depth, but it is the core control of the phase.
**Fix:** Forward what was judged. Either re-serialise the accepted `Value` with `serde_json::to_vec` and send those bytes, or refuse a body that has a duplicate key at the top level or inside `tools[]` and `source`. Re-serialising also removes any whitespace or encoding oddity from the forwarded request.

### WR-02: The egress server's work sits outside the sandbox cgroup and is unbounded in memory, connections and time

**File:** `src/launcher/egress/http1.rs:21`, `src/launcher/egress/mod.rs:59`, `:594-605`, `:710`
**Issue:** The server runs inside the launcher, not under the scope's `MemoryMax`/`TasksMax`. Several resources are bounded only per connection, or not at all:
- A sandboxed driver can hold up to 64 connections (`MAX_CONNECTIONS`), each buffering up to `BODY_MAX_BYTES` (32 MiB) before the judge. That is about 2 GiB of raw bodies, and `serde_json::Value` expansion on a 32 MiB array-heavy body multiplies it again. The driver's own memory cap does not apply to this.
- `tunnel()` (`copy_bidirectional`) has no idle or lifetime timeout.
- `relay_response` has no read or write timeout, so a client that stops reading, or a stalled upstream, pins a permit forever.
- Pinned permits turn every later request into `503` for the whole run. In an unattended run that shows up as inference failures.
**Fix:** Add a total-memory budget, for example a `Semaphore` weighted by body bytes, or a lower body cap for non-streaming JSON. Wrap `copy_bidirectional` and the relay loop in idle timeouts, for example by resetting a deadline per chunk. Document the residual host-side cost in the "residual risks" section of `docs/DRIVER-SANDBOX.md`.

### WR-03: `egress.log` is driver-fillable and has no size cap

**File:** `src/launcher/egress/log.rs:91-98`
**Issue:** Every request, including each refused junk request, appends a line of up to about 800 bytes (four fields of up to 200 characters each). The sandboxed driver controls the request rate, and the file is on the host in the run state directory. Nothing rotates or caps it, and write errors are silently dropped. A hostile or runaway driver can fill the host disk over a long unattended run.
**Fix:** Stop appending once a byte cap is reached, for example 8 MiB per launch. Keep counters going and write one final `log truncated` line.

### WR-04: The directory of this binary is bound read-only whole, which can expose unrelated files

**File:** `src/launcher/home.rs:225-231`, `:88`
**Issue:** The exe directory is bound with `ro(dir)` unless `root_refused(dir)`. `REFUSED_ROOT_REL` refuses `.local`, `.local/share`, `.config` and `.cache`, but not `.local/bin` or `~/bin`. A user who installs the binary into `~/.local/bin` or `~/bin`, which is common for a downloaded release, makes everything in that directory readable inside the sandbox: pipx entry points, personal scripts, wrappers with embedded tokens. The tool hits are handled correctly: for PATH hits only the file is bound when the root is refused (`install_root`).

The `install_root` fallback of "the parent directory when the parent is not `bin`/`versions`" has the same shape: a tool at `~/Downloads/node` or `~/tools/x/node` binds the whole parent.
**Fix:** For the exe, bind the file itself (`ro(facts.exe)`) whenever the parent is not a dedicated tool root. Alternatively add `.local/bin` and `bin` to `REFUSED_ROOT_REL` so those fall back to the file bind. The shim and the bridge only need the single executable.

### WR-05: Allowlist binds that lie under the project path are covered by the later read-write project bind

**File:** `src/launcher/sandbox.rs:509-535` (home binds) against `:548` (`--bind project project`)
**Issue:** The home binds are emitted first and the project bind later. A later bind covers earlier mounts beneath it. `sandbox.rs` itself says "a later bind covers an earlier one" for the guard binds. `HomeSetup` does not know the project path.

When the binary lives under the project being driven, for example `target/debug/gsd-meta-manager` while the tool is used on its own repository, or any PATH tool inside the project, the "read-only" bind of the exe directory is masked by the writable project bind. The agent can then rewrite the binary that the `driverctl` shim, the gate hooks and the bridge execute, and that the host later runs.
**Fix:** In `HomeSetup::for_host` (or `SandboxSpec::from_host`), drop any `Ro`/`Overlay` entry that lies under the project path. Better, re-emit those entries after the project bind, or refuse a launch whose exe lives under the project.

### WR-06: `git worktree add` of the driver-written tip still runs the host's global or system filters

**File:** `src/launcher/push.rs:259-270` (`GIT_HARDENING`), `:649` (the scan worktree)
**Issue:** `GIT_HARDENING` neutralises `core.fsmonitor`, `core.hooksPath` and `core.pager`. The scan step then checks out the tip tree that the driver wrote into a worktree of the mirror. Attributes committed in that tree (`.gitattributes`: `* filter=lfs`) activate any filter driver defined in the host's `~/.gitconfig` or `/etc/gitconfig`, for example git-lfs's `filter.lfs.smudge`/`process`. That runs a host program on driver-chosen content, and git-lfs reads `.lfsconfig` from the working tree to choose its endpoint.

The planted-file guard only inspects the checkout's own files, so this path is not covered.
**Fix:** For the mirror-only steps (`fetch`, `rev-parse`, `worktree add`) set `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_SYSTEM=/dev/null` (or `GIT_CONFIG_NOSYSTEM=1`). The one `push` step can keep the credential configuration it needs. Alternatively add `-c filter.lfs.smudge= -c filter.lfs.process= -c filter.lfs.required=false` plus the same for other known drivers, and prefer `git archive` over a checkout for the credential scan.

### WR-07: The planted-config parser misses keys after a UTF-8 BOM (strict mode)

**File:** `src/launcher/push/planted.rs:533-577` (`parse_config`), `:592-607` (`read_config`)
**Issue:** Git skips a UTF-8 BOM at the start of a config file. `read_config` uses `String::from_utf8_lossy`, which keeps U+FEFF. In `parse_config`, `raw.trim()` does not strip U+FEFF, because it is not Unicode whitespace. So a first line of `\u{FEFF}[core]` does not start with `[`, `current` stays `None`, and every key under that section is skipped. In strict mode (no baseline: runs older than 28.1, or a lost baseline file) a config with `core.fsmonitor` therefore yields no `GitConfigKey` finding. The same applies to included files. With a baseline, the plain hash difference still flags the file, so the miss is limited to strict mode and included files that already existed.
**Fix:** Strip a leading `\u{FEFF}` in `read_config` (or at the top of `parse_config`) before parsing. Add a test with a BOM-prefixed `.git/config`.

### WR-08: A truncated scan always refuses the push, so large repositories need `--ack-planted` every time

**File:** `src/launcher/push/planted.rs:51`, `:264`, `:288`; `Finding::is_git_relevant` at `:139-151`
**Issue:** The nested-`.git` walk shares one 200,000-entry budget and visits every directory outside `SKIP_DIR_NAMES`, including `vendor`, `dist`, `build`, `.next` and data directories. Any repository over that count has `truncated = true` on every snapshot, and `ScanTruncated` is git-relevant. Every push of such a project is refused and parked until the operator passes `--ack-planted`, so the flag becomes routine and the guard is reduced to noise. The baseline hides nothing here, because truncation is recomputed on each snapshot.
**Fix:** Walk only what git could treat as a nested repository (skip any directory git ignores, or use a much larger or per-subtree budget). Report truncation as informational, not push-blocking, when the baseline was truncated too. Document the limit in `docs/DRIVER-SANDBOX.md`.

## Info

### IN-01: A file name can forge the `PLANTED <n>` count

**File:** `src/ui/screens/driver_run.rs:1108-1116` (`planted_count`)
**Issue:** The last list item is read as an overflow marker after `trim_start_matches` strips any leading non-digit, non-`+` text. A planted file named `+9999 more` renders as `created +9999 more` as the final item and is counted as 9999. The path text is driver-controlled.
**Fix:** Match the overflow item exactly: `item.strip_prefix('+').and_then(|r| r.strip_suffix(" more")).and_then(|n| n.parse().ok())`, with no prefix trimming.

### IN-02: `connect_verdict` judges IP-literal-ness before removing the trailing root dot

**File:** `src/launcher/egress/policy.rs:456-467`, `:479-483`
**Issue:** `looks_like_ip_literal("1.2.3.4.")` is false: the last label after `.` is empty, and `"1.2.3.4."` does not parse as an `IpAddr`. `normalize_host` runs afterwards, so the allowlist comparison sees `1.2.3.4`. The pure function's contract, "any IP literal, even an allowlisted one", is not met. This is unreachable in production because config validation forbids IP-like entries and `ip_denied` still guards the resolved address. It is a trap for anyone reusing the function.
**Fix:** Call `normalize_host` first, then `looks_like_ip_literal`.

### IN-03: A non-array host `permissions.<list>` replaces the launcher's deny list

**File:** `src/launcher/config_dir.rs:524-536`
**Issue:** In `managed_settings`, a host value that is not an array is inserted with `ours.insert(list, other)`. A host `"deny": "x"` therefore replaces `DENY_TOOLS`. The module claims Claude Code refuses such files, but the launcher should not depend on that for a safety list. Separately, `disableAllHooks` is not among `LOCK_KEYS`, so a host managed value stays in force; that is deliberate ("never hidden") but undocumented.
**Fix:** Skip non-array values for `deny` (keep the launcher's list). Consider adding `disableAllHooks` to `LOCK_KEYS`, or document it.

### IN-04: `EGRESS_KEY` names the `driver` key, not the egress key

**File:** `src/config.rs:164-166`
**Issue:** `EGRESS_KEY = "driver"` and `EGRESS_SUBKEY = "egress"`. The name reads as the opposite of what it holds and will mislead whoever adds the next `driver.*` setting.
**Fix:** Rename to `DRIVER_KEY` (and update the doc links).

### IN-05: `current_exe()` can carry a ` (deleted)` suffix after an in-place upgrade

**File:** `src/launcher/run.rs:662` (used in `bridged_command` and the shim)
**Issue:** On Linux, when the binary is replaced while the launcher runs, `current_exe()` returns a path ending in ` (deleted)`. The bridge command and the `driverctl` shim then name a non-existent file, so every relaunch of a long run fails with exit 127.
**Fix:** Resolve once at start, or strip the suffix and re-check that the path exists. Failing that, refuse the relaunch with a clear message.

### IN-06: Gateway and alternative-provider setups are silently unsupported and the docs do not say so

**File:** `src/launcher/sandbox.rs` (`ROUTING_STRIP_ENV`), `docs/DRIVER-SANDBOX.md`
**Issue:** `ANTHROPIC_BASE_URL`, `ALL_PROXY` and the Bedrock/Vertex/Foundry switches are stripped in both postures. In the bwrap posture the egress server hard-codes `api.anthropic.com:443`. A user who routes through a corporate gateway or a cloud provider therefore either fails inference or, when degraded, silently talks to the public API. The "residual risks" list covers an upstream `HTTPS_PROXY` but not this.
**Fix:** Add a line to the unsupported/limits section, and print a one-line launch warning when the stripped variables were set in the launching environment.
