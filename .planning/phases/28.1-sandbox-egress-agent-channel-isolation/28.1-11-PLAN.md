## Decision: refuse duplicate keys, keep forwarding the original bytes `[inferred — audit]`

VERIFICATION offers two fixes: forward `serde_json::to_vec(&judged_value)`, or refuse any body that
repeats a key. This plan refuses repeated keys, at every depth, comparing decoded key text, and
leaves the forwarding path (`egress/mod.rs` `inference()` -> `http1::request_bytes(.., &body)`)
untouched. The reasons:

- **The judged reading becomes the only reading.** RFC 8259 §4 says parsers disagree only when a
  name repeats. serde_json already rejects every other ambiguity: trailing commas, comments, a BOM,
  invalid UTF-8, lone surrogates and trailing data. A body with unique names, strictly parsed,
  therefore means the same thing to every conforming parser, so the upstream's repeated-key rule no
  longer matters.
- **Re-serialising would change legitimate traffic.** This crate builds serde_json without
  `preserve_order`; `cargo tree -e features -i serde_json` shows only `default` and `std`. To
  serialise a `Value` would sort every object's keys alphabetically, which reorders tool
  `input_schema` properties and `tool_use` inputs in the model's view. It would also round integers
  beyond u64 through f64. Turning on `preserve_order` crate-wide would change the key order of every
  other `Value` this crate writes.
- **No false positives for the real client.** Claude Code builds its bodies with
  `JSON.stringify`, and a JavaScript object cannot hold a repeated key.
- **No second copy of a body of up to 32 MiB.** WR-02 already flags the host-side memory use.

RESEARCH's "never forward what you did not parse and re-serialise" rule (L643) is about the request
head and its framing, and the proxy still re-emits the head canonically. For the body, forwarding
the exact bytes that passed a strict, unique-name parse gives the same guarantee.

**Reversibility:** reversible. The rule lives in one private function behind `judge_body`; switching
to re-serialisation later is a local change.

**Not covered by this decision (deferred, T-28.1-41):** suppose an upstream matched field names
case-insensitively, the way Go's `encoding/json` matches struct fields. It would then read a lone
`Tools` key as `tools`. Neither proposed fix closes that, and closing it at every depth would refuse
legitimate PascalCase tool schemas, such as AWS-style MCP tools with `Type` or `Source` properties.
