<objective>
Make the refusal in TRANS-04 real and make the duplex channel two-way: harden the first-init
gate into a capability, version and auth-path check that fails closed (D-06, D-07, D-08,
D-30), then implement `send` and `interrupt` at the transport level with honest correlation
(D-22, D-31).

Purpose: TRANS-04's whole value is that an unsupported CLI is refused *up front*, at zero
token and zero quota cost, instead of failing mysteriously mid-run. That only holds if the
gate fails closed on absent fields, and only if a later per-turn `system/init` cannot re-arm
it into a mid-run abort. The control half matters for the same reason in reverse: the CLI
answers an interrupt request with an acceptance that means "request received", which is not
the same claim as "the thing you meant was cancelled".

Output: a pure, fully-tested gate; working `send` and `interrupt`; and the OQ2 finding
recorded so Phase 18 does not re-derive it.
</objective>

  <action>
    Implement the outbound half of the duplex channel at the transport level.

    `send` writes exactly one NDJSON user message line to the held child stdin and flushes.
    Write it DIRECTLY — build no driver-side turn-boundary flush buffer (D-31). The committed
    architecture pass prescribed one on the belief that a mid-turn message is dropped and lost
    from history; the phase spike refutes that on 2.1.220: the message is queued and executed
    as its own turn. The CLI already performs exactly the buffering that workaround
    prescribed, so a driver-side duplicate would only make the still-queued accounting harder
    to reason about. Never close or drop the stdin handle inside `send` — the handle stays
    alive for the whole run, and dropping it is the EOF that ends the run cleanly. EOF means
    "no more input", not "stop": the spike closed stdin at 14 seconds into a 71-second run and
    Claude drained its queue, finished, and exited 0.

    Surface the replay echo as its own observable fact and document what it actually means. The
    echo carries the replay marker and is emitted at DEQUEUE, not at receipt — the spike wrote
    a message at roughly 12 seconds and saw it echoed 45 milliseconds after the previous turn's
    terminal envelope, about 55 seconds later. So it is a "started processing" acknowledgement,
    not a "received" acknowledgement. Say that in the doc comment on `send`, because that
    distinction is exactly what Phase 18's three-state delivery display needs and it is easy to
    misread as a delivery receipt.

    `interrupt` writes a control request whose body carries an interrupt subtype and a caller
    generated request id, registers a oneshot sender in the handle's `pending_control` map
    keyed by that id, and awaits the matching response. The reader task resolves it when it
    sees a control response whose id matches. Use ONLY the request-and-response form; the
    single-field interrupt form that community sources describe was empirically refuted on
    2.1.220 — it produces no response and has no effect — so it must never be written.

    Read the result honestly (D-31, Pitfall D). An acceptance subtype means the REQUEST was
    accepted, not that the thing the caller meant was cancelled. The spike's race probe got an
    acceptance with an empty still-queued array while cancelling nothing meaningful. So
    `InterruptAck` carries both the acceptance flag and the still-queued list read from the
    DOUBLY nested response field — the response object contains a response object which
    contains the array — and the doc comment states that the still-queued list is the
    authoritative statement of what remains, with the subsequent synthetic interruption user
    message and a streaming-aborted terminal reason being the actual confirmation the turn
    stopped.

    Extend the trait doc for `capabilities` while here: `send` and `interrupt` are a Claude
    capability tier and not backend parity — a hypothetical alternative backend satisfies start
    and cancel and not the rest, and the still-queued response shape is Claude-specific (D-22).

    `tests/fixtures/fake-claude-echo.sh` — a stdin-reactive stand-in: read lines from stdin, and
    for a user message emit a replay echo line after a delay; for a control request emit a
    matching control response carrying the same request id and a still-queued array; then emit
    a terminal envelope and exit. Preserve the exec bit in git the same way as the base
    stand-in.

    Add to `tests/executor_transport.rs`: a test that `send` produces exactly the observed
    NDJSON wire shape on the child's stdin; a test that a message sent while a turn is in
    flight is not buffered by the driver and its echo arrives as a distinct event; a test that
    `interrupt` correlates on request id and returns the still-queued contents; and a test —
    driven from fixture 07 — that an acceptance response with an empty still-queued array is
    NOT reported as a cancellation.

    Record the OQ2 finding in this plan's SUMMARY (D-22): mid-turn injection is queued and
    executed as its own turn rather than dropped, the request-and-response interrupt form
    works while the single-field form does not, the replay echo is a dequeue acknowledgement,
    and whether an injected message survives a resumed session is deliberately untested and
    moot because the message executes in-process. Phase 18 depends on this and must not
    re-derive it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `system/init` → gate | The CLI's self-reported capabilities, version and auth source decide whether the tool proceeds; all three are attacker-irrelevant but regression-relevant |
| caller → child stdin | Injected user-message text crosses into a running agent's turn queue |
| control response → caller | The subprocess's answer to an interrupt is reported to the user as a fact about what happened |
