<objective>
Close the supervisor-loop half of GAP 2 (SC-1 / TRANS-01 / CR-01 + CR-02): the two reachable
unbounded-hang paths inside `Coordinator::run` itself.

Purpose: the phase goal is "know exactly how it ended". Today the coordinator can reach a state
where `outcome_tx` is never sent and the caller can learn nothing at all — a fast-emitting child
plus a stalled consumer disables both deadlines AND cancel simultaneously, and once the child is
observed exited every remaining bound is switched off, leaving stdout EOF as the only escape that
a surviving descendant can hold shut forever.

Output: a supervisor whose bounds are evaluated unconditionally on every pass, whose forward to the
caller can never outlive them, and whose post-exit path always ends and always reaps — plus three
regression tests, one per condition, each carrying its own hard timeout so a regression fails
rather than hangs.

## Why this is a separate plan from 15-07

Both plans edit `src/executor/claude.rs`, so they cannot share a wave — this one is wave 6 with an
explicit `depends_on: [15-07]`. The split is by code region: 15-07 owned the call-site and
lifecycle regions (envelope collection, the post-loop derivation call, `interrupt`, the run-end
drain); this plan owns the supervisor `select!` loop and the post-loop status dispatch. CR-01 and
CR-02 are deliberately NOT split from each other — they are two defects in one `select!` block, and
fixing them in separate plans would mean rewriting the same twenty lines twice.
</objective>

## Recorded decision: the SIGKILL-escalation test stops being ignored

`a_child_that_ignores_the_terminate_signal_is_still_killed_and_reaped` is currently `#[ignore]`d
with the reason "waits out the real ten-second teardown grace", and it is the ONLY proof the
escalation path works at all. This plan **un-ignores it**, for three reasons:

1. This plan makes that path newly reachable from a second entry — the post-exit branch now calls
   `tear_down_group` when the group is not proven reaped — so the escalation stops being exercised
   only by an explicit cancel and starts being reachable from an ordinary run's tail. A path with
   two entry points and zero CI coverage is exactly the shape that produced CR-02.
2. The measured cost is ~10 seconds, and Rust's test harness runs the tests within one integration
   binary concurrently on threads, so the wall-clock cost is absorbed by the other tests in the same
   file rather than added to them.
3. Hard constraint 8 of this replan forbids new ignored tests. Keeping a stale one while adding
   bounded ones would be inconsistent.

Record the reason in a comment on the test where the attribute used to be, so the next reader knows
the ~10 second cost is deliberate and is the price of covering the escalation.

  <action>
    Make the supervisor's own bounds independent of both `select!` arm ordering and the consumer's
    health. Two changes, exactly as the review specifies, plus the fixture and tests that prove them.

    **1. Let the stand-in actually flood (`tests/fixtures/fake-claude-slow.sh`).** In the heartbeat
    loop, skip the `sleep` call entirely when the interval argument is the string `0`, using a
    `case`/`esac` or a short-circuit test rather than calling `sleep 0` — the current code forks a
    `sleep` process per heartbeat, which caps the emission rate far below what is needed to fill a
    channel of 8192. `printf` and the arithmetic are shell builtins, so with the fork removed the
    script emits tens of thousands of lines per second. Document the zero-interval fast path in the
    script's usage header beside the existing `interval` description. Change nothing else: every
    existing caller passes a non-zero interval or zero heartbeats, so no existing test's pacing
    moves.

    **2. Evaluate every bound at the loop head (`src/executor/claude.rs`).** Add three locals to
    `Coordinator::run` beside the existing ones: `let mut drain_deadline: Option<Instant> = None;`,
    `let mut drain_expired = false;` and `let mut dropped_events: u64 = 0;`. (`drain_deadline` and
    `drain_expired` are wired to the exit arm in Task 2; declare them here so the loop head reads
    them from the start and Task 2 only sets them.) At the TOP of the loop body — before the
    `select!`, after `idle_deadline` is recomputed from the reader's stamp — insert an unconditional
    evaluation block that, in this order:

    - reads `let now = Instant::now();`
    - if not cancelled, drains a non-blocking `cancel_rx.try_recv()`; on a delivered value set
      `cancelled = true` and then, if the child is already observed exited, set `stop = true`,
      otherwise set `terminate = true`. This is the CR-02 half of the cancel fix and belongs here
      because a cancel that arrives while the loop is parked must be honoured on the very next pass.
    - if neither exited nor cancelled and `now >= wall_deadline`, sets `breach = Some(Breach::WallClock)` and stops the loop;
    - if neither exited nor cancelled and `now >= idle_deadline`, sets `breach = Some(Breach::Idle)` and stops the loop;
    - if `grace_deadline` is `Some` and elapsed, stops the loop;
    - if `drain_deadline` is `Some` and elapsed, sets `drain_expired = true` and stops the loop.

    Guarding the two breach checks with "not cancelled" is required, not optional, and is NOT a
    WR-02 fix: hoisting the checks makes them run every pass, which would make the pre-existing
    breach-outranks-cancel race fire far MORE often than it does today. The guard keeps that race
    exactly as frequent as it already is. Leave the outcome match's arm ordering untouched — that
    ordering is WR-02's and is out of scope.

    Keep the `select!` and all six of its arms, including `biased;` and the reader-first ordering:
    with the bounds now evaluated unconditionally, arm ordering can no longer starve anything, and
    reader-first is still the right priority for stream fidelity. The timer arms stay as the
    wake-up mechanism; the loop-head block is the enforcement mechanism.

    **3. Bound the forward (`src/executor/claude.rs`).** Add `pub const EVENT_FORWARD_TIMEOUT:
    Duration = Duration::from_secs(5);` to the const block, documented as: an absolute ceiling on
    how long the supervisor may be parked handing one event to its consumer. The consumer is a TUI
    that can legitimately stop draining for a while — the blocking editor shell-out is the known
    case — so the ceiling is generous rather than tight; but it is finite, because a supervisor
    parked on a send is a supervisor whose caps and cancel are all disabled, which is the CR-01
    defect. State plainly that the cost of a stall longer than this is a counted, logged dropped
    event, and that a dropped diagnostic is preferable to an unbounded park.

    Compute, once per pass at the loop head, `let forward_deadline: Instant = ` the EARLIEST of:
    `now + EVENT_FORWARD_TIMEOUT`; `wall_deadline` and `idle_deadline` when neither exited nor
    cancelled; `grace_deadline` when set; and `drain_deadline` when set. Because the forward can
    never outlive the earliest armed bound, a cap that expires while the supervisor is parked
    unparks it at exactly the right instant, and the loop head then classifies the breach on the
    next pass. Thread `forward_deadline` and `&mut dropped_events` into `handle_item` as two new
    trailing parameters (it already carries `#[allow(clippy::too_many_arguments)]`).

    Add `async fn forward(events_tx: &mpsc::Sender<ExecutionEvent>, event: ExecutionEvent,
    forward_deadline: Instant, dropped: &mut u64) -> bool` next to `handle_item`. It wraps the send
    in `tokio::time::timeout_at(forward_deadline, events_tx.send(event))` and returns: `true` on a
    delivered event; `false` when the send failed because the receiver is gone (the established
    "receiver dropped, stop producing" convention this file already uses); and, on an elapsed
    deadline, it increments `*dropped`, emits a `tracing::warn!` carrying the running COUNT and the
    channel capacity and NOTHING ELSE — no event, no raw line, no message body — and returns `true`
    so the loop continues and re-evaluates its bounds. Replace every `events_tx.send(...).await`
    inside `handle_item` with a `forward(...)` call, preserving each site's existing keep-going /
    stop semantics exactly. Do NOT touch `read_stderr`'s own direct send: it runs in its own task
    which holds no supervisor state, and D-04's rule that stdout and stderr are separate tasks that
    are never merged is exactly why blocking there cannot park the supervisor — widening the change
    into it is out of scope. Update the in-file
    `feed(...)` test helper for the two new arguments, passing a far-future `forward_deadline` and a
    throwaway counter so the existing first-init tests keep their current meaning.

    **4. Two regression tests (`tests/executor_lifecycle.rs`).** Add a
    `fn flooding(lines: u32) -> ClaudeExecutor` helper returning `slow(lines, "0", "result")`, with
    a doc comment stating that zero interval means the stand-in emits as fast as the shell can
    print, which is what fills the 8192-slot channel.

    `a_wall_clock_cap_still_fires_while_the_event_consumer_is_blocked`: start `flooding(50_000)`
    against a fresh `TempDir` with `capped(3_000, 30_000)` — a 3-second wall cap and an idle cap far

    stays alive inside the handle, so the channel fills and stays full, which is exactly the stalled
    consumer. Await `handle.wait_outcome()` inside a `tokio::time::timeout` of 60 seconds and assert:
    the timeout did not elapse; the outcome is `RunOutcome::TimedOut { after }` with `after` equal to
    3 seconds; and the measured elapsed time is under 30 seconds. The failure message must name the
    regression: a stalled consumer must never be able to disable the only bound on a runaway run's

    `a_cancel_is_still_honoured_while_the_event_consumer_is_blocked`: start `flooding(50_000)` with
