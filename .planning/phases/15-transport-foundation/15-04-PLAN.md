<objective>
Make a run stoppable and bounded at the executor level: two independent deadlines (D-13) and a
teardown that takes the whole process tree down and reaps it (D-14).

Purpose: A bare child kill reaches only the direct child, and `claude` spawns Bash
grandchildren — orphaning them is the failure this phase's dependency choice exists to
prevent. Meanwhile a hung run and a legitimately long run are indistinguishable by
time-since-spawn: the research pass reproduced a hang that sat silent for 180 to 240 seconds
while a real multi-step run emits events continuously. Only an idle cap measured from the last
observed line can tell those apart.

Output: a supervisor racing exit against both caps and a cancel signal, a four-step teardown,
three process stand-ins that make the tree teardown provable, and unix-gated integration tests.
</objective>

  <action>
    Add a supervisor task that owns the deadlines, and never await process exit unbounded.

    The supervisor is a `tokio::select!` racing four arms: the child's exit future, a total
    wall-clock sleep, an idle sleep, and a cancel signal from the executor's own command
    channel. Racing them this way is also what resolves the borrow problem — the exit future
    holds a mutable borrow of the child for its whole lifetime, so a supervisor that holds it
    across an await cannot call the signal method on the same object. When a deadline arm wins,
    `select!` drops the exit future, the borrow ends, and the signal call is legal in the same
    block. Record the child's pid as the process group id on the handle at spawn as well, since
    the group leader's id equals its pid and a task that does not hold the child can then tear
    the group down independently — which is also exactly what Phase 17 needs for crash
    reconciliation and orphan reaping, so recording it now costs nothing.

    The idle timer is driven by the READER task, not by the envelope (D-13, Pitfall E). Have
    the stdout reader publish the instant of every line it observes through a watch channel; the
    supervisor's idle arm sleeps until that instant plus the idle cap and re-arms whenever it
    moves. Never derive elapsed time from a duration field in the terminal envelope: the
    research pass observed the API-time field EXCEEDING the wall-clock field in a clean run
    because it aggregates across parallel API calls, and in any case those fields only arrive
    WITH the terminal envelope, which is far too late to serve as a stuck detector.

    Pick defensible starting values and make both configurable on the options struct — D-13
    leaves the numbers to the planner and real tuning data does not exist yet. Use a four-hour
    total wall-clock cap and a fifteen-minute idle cap, and derive the idle number rather than
    guessing it: background subagents are waited for up to a ceiling whose silent default is ten
    minutes, so a legitimate run CAN be silent for that long, and the idle cap must therefore be
    strictly greater than the ceiling or it would kill healthy runs. Set the ceiling explicitly
    on the child's environment at ten minutes rather than inheriting the silent default (D-14),
    and put both derivations in a doc comment so the next person retuning them knows the
    ordering constraint rather than breaking it.

    Scrub the child's environment. The child inherits the parent's environment, and this tool is
    plausibly launched from inside a Claude Code session, so CLAUDE-prefixed variables already
    set in the parent would leak into the driven child and make behaviour unreproducible. Remove
    every inherited variable with that prefix from the spawned command, then set the ceiling
    variable deliberately. Record the decision in the module doc.

    Distinguish the two breaches in the outcome. A wall-clock breach and an idle breach produce
    different classified outcomes — timed out versus stalled — because they mean different
    things to a user and to Phase 20's router. Both route through the same teardown.

    Note what this phase's deadlines DO NOT bound: they bound a single `claude` invocation, not
    a multi-step run. Run-level step, wall-clock and no-progress caps belong to Phase 20; say so
    in the doc comment so a later reader does not mistake one for the other. Likewise the budget
    option stays plumbed and nothing more (D-16) — it is a post-turn circuit breaker that cannot
    prevent the turn it fires on from spending, so no cost enforcement is built on it here.

  <action>
    Implement the four-step teardown and prove it kills the whole tree.

    The sequence is exactly: send the terminate signal to the process GROUP, wait a ten-second
    grace, then send the uncatchable signal to the group, then AWAIT the wait to completion
    (D-14). Each step exists for a reason worth stating in the module doc. The terminate signal
    is the documented clean path — it aborts the turn, tears down the Bash tree through the
    CLI's own handler, runs its session-end hooks, and exits with the conventional
    signal-terminated status. The uncatchable signal is only the backstop. The awaited wait is
    what prevents zombies, and it must be awaited to COMPLETION: the wrapper's wait awaits the
    leader and then loops a non-blocking group reap ten times before falling back to a blocking
    reap on a blocking task, so dropping that future mid-reap leaves the grandchildren
    unreaped.

    Do not reach for the wrapper's combined terminate-and-wait convenience method as the
    teardown story (Pitfall B). On a process group its start-of-kill method sends the
    UNCATCHABLE signal, and the convenience method is that plus a wait — so it skips the CLI's
    entire clean shutdown. Reading that method name as "terminate politely" is natural and
    wrong. Use the raw-signal method for the first step; it takes a plain integer, so no extra
    dependency is needed to name the signal.

    Keep the kill-on-drop wrapper composed at spawn as a BACKSTOP only, never as the teardown
    story, so a panic or an early return still takes the group down. The full panic-hook and
    crash-reconciliation version is Phase 17's; do not build it here.

    Write three stand-in variants beside the base one, each executable with the exec bit
    preserved in git:

    - a slow variant that emits an initialisation event and then goes silent forever, which
      exercises the idle cap
    - a spawner variant that emits an initialisation event, launches a long-sleeping background
      grandchild, prints that grandchild's pid on a line the test can read, and then sleeps,
      which is the only way to actually prove the group teardown reached the grandchild
    - a deaf variant that ignores the terminate signal entirely, which forces the escalation
      path

    Write `tests/executor_lifecycle.rs` with unix gating on every test, importing from the
    library crate path, using a temporary directory for the scratch project root, unprefixed
    behaviour-describing test names, and assertion messages that carry the observed value:

    - the spawner variant's grandchild is gone after teardown, checked by signalling its
      recorded pid with the zero signal and expecting failure
    - the deaf variant is still killed and still reaped after the grace period elapses
    - the slow variant trips the idle cap and produces the stalled outcome, not the timed-out
      one
    - a chatty stand-in that keeps emitting events past the idle cap is NOT killed by it, which
      is the property that makes the idle cap the correct stuck detector
    - a run torn down leaves no zombie: after teardown the wait has completed and the child
      reports an exit status

    Mark the tests that need a real ten-second grace as ignored so the default suite stays
