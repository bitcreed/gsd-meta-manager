<objective>
Turn the journal from something a machine can replay into something a human can read, and give the
Driver tab a cheap way to enumerate the runs on disk.

Purpose: `journal::from_exec_event` currently stores `format!("{m:?}")` — a Rust `Debug` rendering of
`TurnMessage`, whose message body `src/executor/stream_json.rs:105-107` explicitly declines to model,
calling content blocks *"Phase 18's rendering concern"*. **A live-output pane fed `Debug` structs is
the named "looks done but isn't" failure**: the criterion "watches its output" is met in the letter
while the pane fills with `TurnMessage { session_id: Some(..), is_replay: false, .. }`. One change
serves OBS-04 (a readable pane) and STEER-02 both, because the interjection echo cannot be
correlated or displayed without the text. Every sibling arm of `from_exec_event` already carries a
real string (`raw.clone()`, `line.clone()`), so the readable projection is the arm that matches its
neighbours — not a novelty.

Output: the projection helpers, the minimal tolerant content-block model, and `journal::list_runs`.
</objective>

Model just enough of the message body to render it, and project it into the journal.

In `stream_json.rs`, add `MessageBody` and `ContentBlock` and hang `message: Option<MessageBody>` off
`TurnMessage`. **Every added field is `Option` or `#[serde(default)]`** — the file's whole posture is
envelope tolerance, and a required field turns an unknown block shape into a parse failure that lands
in `ExecutionEvent::Unparseable`. `ContentBlock`'s discriminator field is named on the wire with a
Rust keyword, so it needs a `rename`; carry a comment saying so, matching the existing
`claude_code_version` precedent. Add `TurnMessage::text_content()` returning a `String`: text blocks
concatenated in order, and any non-text block rendered as a short bracketed label naming its type
(and its `name` where present) rather than dropped — a tool call that vanishes from the pane is
output the user cannot see. Update the struct's doc, which currently defers content blocks to this
phase, to say what is now modelled and what deliberately still is not.

In `journal/mod.rs`, replace the `Debug`-formatting in `from_exec_event`'s `Message` and
`TurnCompleted` arms with `exec_message_text` and `turn_result_text`. `exec_message_text` composes
the role prefix and `text_content()`. `turn_result_text` composes the facts the stream reported —
subtype, terminal reason where present, turn duration, and the cumulative cost — and must treat
`result` as `Option<String>` because it is **absent** on error envelopes (Phase 15 D-32). Neither
helper interprets the prose: the agent's own words may be displayed as content and may never drive a
badge, a colour, a status word or a sort key (D-13). Put that sentence in the doc comment on
`exec_message_text` so the next reader cannot undo it by accident.

Do **not** sanitise here. Terminal-control stripping happens at buffer-append time in the TUI
(18-04) because the journal is also read by tools other than this renderer, and stripping at write
time would destroy evidence. Say that in the doc, and name it as a deliberate division of
responsibility rather than an omission.

Inline `#[cfg(test)] mod tests`: a text-only message projects to its text; a message with a tool-use
block keeps a visible label; a message with no body projects to an empty-but-not-panicking string; an
error `result` envelope with an absent `result` field projects without panicking; a multi-byte
message round-trips without a byte-boundary panic.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent stdout envelopes → `from_exec_event` → journal text | Agent-authored bytes become the string a terminal will later render. |
| `runs/` directory entries → `list_runs` | Directory names and `run.json` bodies live inside the driven project, so the agent can create or alter them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-14 | Tampering | terminal-control sequences inside projected text | high | mitigate | Projection deliberately does not sanitise (the journal is evidence); the render-time sanitiser in 18-04 strips `ESC` unconditionally before any byte reaches a buffer. This row is only closed once 18-04 lands, and that dependency is stated here rather than assumed. |
| T-18-15 | Denial of service | an adversarially large content block | medium | mitigate | `text_content` is bounded downstream by the per-line and per-record caps in 18-04; the journal itself is bounded by `MAX_RUN_JOURNAL_BYTES` and `redact::RedactedLine`'s payload cap at write time. |
| T-18-16 | Tampering | a hostile directory name under `runs/` | high | mitigate | `list_runs` filters on `is_plain_run_id` before touching any entry (D-27), so a traversing name is skipped rather than joined. |
| T-18-17 | Spoofing | a fabricated `run.json` claiming a successful outcome | medium | accept | The record is written by the driver, and a project whose agent can forge it can already forge its own git history. Status derivation still comes from `RunEnded.outcome` / `ExecFinished.exit`, never from prose (D-13); accepted at ASVS level 1 with the reasoning recorded. |
| T-18-18 | Tampering | package-manager installs | low | accept | Zero Cargo dependencies added; no package-legitimacy surface exists. |

ASVS level 1; blocking threshold `high`. T-18-14 and T-18-16 are the `high` rows; T-18-16 is closed
in this plan, T-18-14 is explicitly closed by 18-04 and that dependency is recorded rather than
silently assumed.
