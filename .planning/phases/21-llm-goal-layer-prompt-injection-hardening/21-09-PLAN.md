`journal::recheck_approval` with `plan_digest: plan_digest.clone()` — the digest
of the plan *just observed*. `recheck_approval` then compares

`ApprovalRefusal::PlanChanged` arm is unreachable from that call site, and the
spawn-gate re-check at `src/driver/run.rs:2253-2260` passes
`&approved.plan_digest` as the observed digest, so it is a tautology there too.

Every real mismatch therefore falls through to `DisclosedFilesChanged`, whose
message opens *"the plan is unchanged but the disclosed files … are not"*. That
is the **common** case, not an exotic one: the review flow is to run without
`--approved-plan` to obtain a digest, then re-run with it — and the second run
re-decomposes the goal through a non-deterministic model. A model that answers
differently is the expected case, and today the user is told their files changed
and sent to look for a `git pull` that never happened.

Purpose: gap 2 in `21-VERIFICATION.md` is `partial` because the approval's
plan-half re-check message is not honest. `src/journal/mod.rs:620-624` claims
the two halves "stay distinguishable to the person reading the refusal"; at both
call sites they do not.

`approve_plan` compares the half the approval actually covered, `PlanChanged`
becomes reachable, a malformed or half token is refused by name, and the
spawn-gate re-check's doc says what it can establish.

<design_decision>
**One flag carrying two halves, not two flags.**

`21-REVIEW.md` WR-01 suggests adding a second CLI flag (`--approved-plan-id`)
beside `--approved-plan`, and `21-VERIFICATION.md` records the missing work as
"accept both digest halves on the CLI (**e.g.** …)". A combined token satisfies
that requirement and is chosen instead, for three reasons:

1. **`DriveArgs` gains no field.** Eleven call sites construct `DriveArgs`
   literally (`src/driver/mod.rs`, `src/driver/run.rs`, `src/main.rs` and eight
   test files). A new field would touch every one of them for a one-line
   addition each, inflating this plan's blast radius into files that have
   nothing to do with the defect.
2. **A reviewer copies one token, not two.** The refusal *is* the review
   surface; it prints the plan and the value to pass back. Two flags means two
   values to transcribe and a new way to get it half right.
3. **One value has one failure mode.** With two flags, "one supplied, the other
   not" is a state the code must classify anyway. With one token, a value that
   does not carry both halves is simply malformed, and the parse is the check.

The token is `<plan_digest>+<approval_digest>`. Both halves are
`prefix:hexdigits` (`sha256:` after plan 21-08, and `sha256:` for the approval),
so `+` cannot occur inside either half and `split_once('+')` is unambiguous. It
is shell-safe unquoted.
</design_decision>
