<objective>
Close **CR-02** and **WR-05**: the two defects that make the plan a user reviews
untrustworthy in the two ways that matter — its *identity* is not
collision-resistant, and its *tokens* are not bounded.

- **CR-02:** `goal::plan_digest` calls `journal::argv_digest`, which is FNV-1a-64
  and whose own doc says it is not a security control. `journal::approval_digest`
  then SHA-256s `plan=<plan_digest>` plus the file digests — but hashing a weak
  digest under a strong one preserves the weak digest's collision class exactly.
  Two plans whose FNV-1a-64 digests collide produce identical approval digests.
  The tokens hashed include `target_phase`, which is any roadmap-declared phase
  name — attacker-controlled under this phase's own stated threat model. Three
  doc paragraphs currently assert the composition is safe; that assertion is
  false.
- **WR-05:** in `goal::legality`, `rationale` is bounded but `target_phase` is
  stored raw and flows unsanitised into `DriveError::PlanApprovalRequired`'s
  `Display` — straight to the operator's terminal — and into the committed
  `run.json`. `journal::is_plain_path_component` rejects path separators and
  `.`/`..`; it accepts `ESC`, `\n`, `\r` and every other control character.

Purpose: ROADMAP criterion 1 is recorded ✗ FAILED and CR-02 is one of its two
causes; WR-05 is half of the recorded `partial` gap 2. Both live in the same two
files and both are the same concern — *is the plan the user reviews actually the
plan that runs, and is it shown honestly*.

Output: a `sha256:`-prefixed plan digest, three corrected doc paragraphs, a
bounded-and-refused `target_phase`, a sanitized approval refusal, and the
regression tests each fix owes.
</objective>

  <name>Task 1: The approval's plan half becomes collision-resistant, and the docs stop claiming it already was</name>

  <reversibility rating="reversible">
    This changes a **digest format** — an `fnv1a64:`-prefixed `plan_digest`
    computed by the current build will not validate against the new one — but it
    is `reversible`, not `one-way`, and the check is objective rather than a
    judgement call: **`src/driver/goal.rs` does not exist at tag `v1.6.0`**
    (verified with `git cat-file -e v1.6.0:src/driver/goal.rs`, which reports the
    path exists on disk but not in the tag). The entire goal layer, `plan_digest`,
    `--approved-plan` and `ApprovedPlan` are therefore **unreleased**: no shipped
    build has ever written an `fnv1a64:` plan digest into a committed `run.json`
    and no user holds an approval token from a released build.

    **How existing tokens and records are handled:** nothing is migrated, and
    nothing needs to be. A dev-tree `run.json` carrying an `fnv1a64:`-prefixed
    `plan_digest` compares unequal to a freshly computed `sha256:` one — the whole
    string is compared, and the prefixes differ — so it re-checks as stale and
    refuses. That is the fail-closed direction, and it is exactly the property the
    `sha256:` prefix was introduced for in plan 21-03 ("a legacy `fnv1a64:` value
    can never accidentally compare equal to a freshly computed `sha256:` one").
    Task 1 pins that behaviour with a test rather than leaving it as a claim in a
    doc comment. No `checkpoint:decision` is warranted: a `one-way` rating would
    require a released format, and there is none.
  </reversibility>
