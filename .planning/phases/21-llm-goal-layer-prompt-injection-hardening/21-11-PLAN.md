<design_decision>
## Why the blankness check goes at the seam and nowhere else

`21-VERIFICATION.md`'s `missing` item asks for two things: refuse a blank
`--command` at `command_source`, **and** add `CommandSource::Command(String::new())`
plus `CommandSource::Command("   ".into())` to
`every_command_source_renders_a_preview_with_no_empty_numbered_command`'s array.

The first is implemented exactly as asked. The second is implemented
**differently, deliberately, and more strongly** — and the reason is worth
stating because a reviewer will check the letter:

`preview_text(&CommandSource::Command(String::new()))` renders through
`dry_run::build_report`, which pushes the command it is given. Making that call
clean requires defending in the **renderer** as well as at the seam. Two places
that answer the same question are two places that can disagree — the exact shape
`CommandSource`'s promotion was made to remove, and the shape IN-02 in
`21-REVIEW.md` flags elsewhere in `dry_run.rs`. So the degenerate payloads are
enumerated where they are **production-reachable**: on argv, through
`command_source`, which is the single production constructor of the type.

That reduction is only sound if "single production constructor" is a checked
property rather than a grep result. **It is checked — by Task 2 of
`21-12-PLAN.md`**, which asserts tree-wide that the three variant spellings
appear only in `command_source` (constructing) and `preview_text` (matching).
The two plans are one argument; `21-12` is wave 2 for that reason among others.

## Why the matrix makes a fourth recurrence a certainty to catch

Stable Rust cannot enumerate an enum's variants without a derive macro, and this
project adds no dependency for this. What it *can* do is force a total
classification. The mechanism is three parts, and each is load-bearing:

1. **A no-wildcard classifier inside the test module** (`variant_name`). A fourth
   `CommandSource` variant is a **compile error in the test file itself**. Nobody
   can add a fourth command source without opening this test — which is precisely
   what did not happen when `--goal` was added beside `--command` and
   `--target-phase`.
2. **The enumeration axis is payloads on argv, not variants in an array.** CR-01
   and review-CR-02 are both *degenerate-payload* defects, not missing-variant
   defects. A matrix of `{empty, spaces, tab, newline, realistic}` × `{--command,
   --target-phase, --goal}` fed through `command_source` covers the failure mode
   directly, and cannot be satisfied by picking a payload that avoids it.
3. **Both-directions non-vacuity**, in the register `src/driver/router.rs:1068`
   and `tests/spawn_seam_guard.rs` already use: the set of variant names the
   matrix's `Ok` cells produced must be exactly the three the classifier names,
   and each position's realistic payload must resolve to `Ok`. A matrix that
   quietly stopped covering a variant, or one where everything was refused, fails
   loudly instead of passing narrowly.

**What this does not make certain, stated rather than glossed:** a fourth *argv
field* that resolves to an **existing** variant (say a `--goal-file` that becomes
`CommandSource::Goal`) adds a column the matrix would not have. The classifier
does not fire, because no variant was added. The doc comment on the test must say
so in those words, because this repository has already paid once for a guard that
read as exact and was quietly approximate.

## Reversibility of the ordering change

Moving `parse_approval_token` above the dry-run branch changes observable CLI
behaviour: `--dry-run` with a malformed `--approved-plan` currently exits 0 and
will exit non-zero. Rated **`reversible`**, on an objective basis rather than a
feeling: `--approved-plan` and the whole goal layer are **unreleased**.
`git cat-file -e v1.6.0:src/driver/goal.rs` reports *"exists on disk, but not in
'v1.6.0'"*, and `git show v1.6.0:src/cli.rs | grep -c approved` returns 0, so no
user holds a build in which the flag exists at all. Nothing persists, no format
moves, and reversing is moving one block back. **No `checkpoint:decision` is
warranted**, because a `one-way` rating would require a released surface and
there is none.
</design_decision>
