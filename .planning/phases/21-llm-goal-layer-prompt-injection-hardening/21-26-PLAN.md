<objective>
**Round 9, wave 3. The two mechanism defects that CANNOT fall out of a carrier — said plainly —
and the record.**

21-23, 21-24 and 21-25 close CR-01, CR-02, CR-04 and pass-9's render findings as consequences
of one carrier type. **CR-05 and WR-05 are not that shape and this plan does not pretend they
are.** CR-05 is a defect in the mechanism that decides *which screens get checked at all*, and
WR-05 is a defect in the needle of a source census. Neither is a value crossing a trust
boundary, so no newtype reaches them. They get their own tasks, tightly scoped, and the
reason is stated rather than smuggled.

**What the census becomes, and it is not a better regex.** The round-8 review's proposed repair
was to join lines before scanning and to report an unnameable `impl` rather than skipping it.
That narrows the residual and it is worth doing — it is Task 2 — but it leaves the
deny-by-default property resting on **source formatting**, which is one level below where
anybody was looking and is exactly the level CR-05 found. So Task 1 moves the property into the
type system:

```
pub trait Screen: RenderAdjudicated { … }        // RenderAdjudicated is sealed
```

An `impl Screen for X` where `X` carries no adjudication does not compile. Verified by the
planner in a scratch crate on this toolchain:

```text
error[E0277]: the trait bound `UnadjudicatedScreen: RenderAdjudicated` is not satisfied
  --> src/main.rs:57:17
   |
57 | impl Screen for UnadjudicatedScreen {
   |                 ^^^^^^^^^^^^^^^^^^^ unsatisfied trait bound
```

Both of the reviewer's plants are covered by that one bound. The **macro-generated** implementor
must expand an adjudication or it does not compile (the planner built one that does, and it
works). The **wrapped `impl` header** is not a text pattern at all under a type bound. And a
third spelling nobody has invented is covered too, because there is no spelling to be short of.

**Two things this must not break, both verified before the plan was written.** `Screen` is used
as `Box<dyn Screen>` throughout the UI and inside `ScreenAction::Push`, so `RenderAdjudicated`
must stay object-safe: it uses **methods** returning `&'static str`, never associated consts,
because an associated const makes the trait dyn-incompatible. The planner constructed
`Vec<Box<dyn Screen>>`, stored two implementors in it, and called both supertrait methods
through `&dyn Screen`. And the adjudication must not be publicly implementable, so
`RenderAdjudicated` sits above a crate-private `Sealed` marker and the `adjudicate_screen!`
macro is the only route.

**What that buys beyond CR-05.** The disposition stops being a row in another file that
*restates* what a screen does and becomes something the screen *carries*, beside the
`Screen::render` it describes. The probe then reads `screen.disposition()` off the constructed
instance, so the disposition it checks and the disposition the screen declares cannot drift —
a class of defect the both-ways `assert_eq!` could only catch for *membership*, never for
*content*.

**And one number corrected by measuring.** The standing brief and the round-8 review both speak
of "13 `Screen` impls". At HEAD, `rtk proxy grep -rn "impl.*Screen for " src/ --include=*.rs`
returns **11**. The thirteen was eleven real implementors plus the reviewer's own two plants,
counted while the plants were in the tree. The new mechanism is measured against eleven, and
the SUMMARY says so, because a plan that chased a phantom twelfth and thirteenth screen would
have spent the round looking for something that is not there.
</objective>
